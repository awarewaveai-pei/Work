# ADR-023 — Capability resolution is fail-closed, like method resolution (closes OQ-P5-1)

Status: ACCEPTED (2026-09-03); spec-root follow-ups 1–5 landed and the plan-level BLOCKED transition wired 2026-09-04 (§Required implementation gates); follow-up 6 open
Date: 2026-09-03
Decision authority: Operator-delegated — the same standing delegation ADR-022 quotes verbatim in its header (2026-09-02), plus today's instruction naming this exact item: "接著挑 OQ-P5-1（capability contract fail-closed）…繼續，全部在 `ai_lego/*` 底下動工" (2026-09-03). Scope: the runtime. The only spec-root files this ADR touches are itself, `ADR_INDEX.md`, and the OQ-P5-1 row of ADR-022's gate table. ## Context

The Phase 5 runtime (ADR-022) resolves every `method_node` of the compiled Workflow IR against the real `methods/contracts/` catalog and blocks with `METHOD_RESOLUTION_BLOCKED` when a contract is missing or not `ACTIVE` — the Master Plan L45 / EC §14 red line, exercised by MVP §5 criterion 6. Its `capability_node`s were never resolved at all: the IR was compiled and validated, and the slice then ran its one real capability implementation (`run_statistics` → `compute/statistics/reliability.py`) with no check that a contract existed. That is fail-open, and it is the opposite of what the same mother documents say for capabilities:

- MP §7: "所有 AI 呼叫統一經過 AI Gateway" — `Capability Request → Capability Resolver → Policy Engine → AI Gateway`. Resolution is a stage every capability request passes, before execution.
- MP §8.4: "每個能力與 Method 都必須具有 Input / Output type … **不合法組合在執行前拒絕**". A capability with no contract has no declared I/O type, no `security`/`rollback`/`entitlement` block, and therefore nothing the Policy Engine could validate. It is an illegal combination by construction.

The spec root's actual state (2026-09-03): `capabilities/contracts/` holds exactly one file, `run_statistics.capability.yaml` (ACTIVE, 1.0.0). The Recipe's other three capability refs — `transcribe` (RECOMMENDED), `literature_search` (RECOMMENDED), `artifact.generate_research_paper` (REQUIRED_BY_RISK) — have no contract. OQ-P5-1 asked whether capability resolution should fail-closed anyway, given that answering "yes" makes the current Recipe unexecutable as written.

## Decision

1. **Capability resolution is fail-closed, with the same "registered" definition as methods.** A capability ref resolves iff a `capabilities/contracts/<ref>.capability.yaml` exists under the read-only spec root, declares that `id`, and carries `status: ACTIVE`. One shared scan (`ai_lego/platform/ai_execution/contract_catalog.py`) now backs both `MethodCatalog` and `CapabilityCatalog`, so the two resolvers cannot drift on what counts as a live contract. The blocking signal is `CAPABILITY_RESOLUTION_BLOCKED`, named per the existing `<Domain>_RESOLUTION_BLOCKED` family (`METHOD_`, `DOCUMENT_`).
2. **Two enforcement points, both in `ai_lego/platform/ai_execution/capability_resolver.py`:**
   - **Invocation (enforced now, structurally).** `CapabilityCatalog.invoke(ref, implementation, …)` is the only sanctioned way for runtime code to call a capability implementation; it calls `require(ref)` first and never reaches the implementation on an unresolved ref. The slice's single real capability invocation (`run_statistics`) goes through it. An empty catalog aborts the run *before* `StatisticsCalculated` is emitted and before any result/manifest file exists (`test_uncontracted_capability_invocation_aborts_before_statistics_or_any_manifest_is_written`, both adapter modes).
   - **Plan (recorded from 2026-09-03; the state transition was deferred that day and wired 2026-09-04 — §Consequences 4).** After `METHODS_RESOLVED`, the slice resolves all of the IR's capability refs against the live catalog — all-or-nothing, like methods — and records the verdict as a ledger event (`CapabilityResolutionBlocked` today, `CapabilitiesResolved` once every ref has a contract), in `result["capability_resolution"]`, in the manifest's `results` block (`capability_plan_executable`, `capability_plan_fully_resolved`, `unresolved_capabilities` — additive fields; the schema's `results` has no `additionalProperties: false`) and as a `WARN:` line in the CLI output, so the verdict reaches the records of record rather than only a nested field. `plan_executability()` refuses a resolution that does not cover every capability node of the IR (`CAPABILITY_PLAN_COVERAGE_MISMATCH` — an empty resolution must never read as "fully resolved") and classifies each unresolved node by the Recipe's own `necessity` (Atlas §14.3: `REQUIRED_*` blocks are policy-mandated and cannot be removed; `RECOMMENDED`/`OPTIONAL` may be omitted): `executable` is false iff a `REQUIRED_*` node is unresolved; `fully_resolved` is false iff any node is. Today's honest record: `fully_resolved: false`, `executable: false` (`artifact.generate_research_paper` is REQUIRED_BY_RISK with no contract).
3. **The plan-level `BLOCKED` state transition is decided (wired 2026-09-04 — see §Consequences 4; the rest of this item is the 2026-09-03 sequencing record).** The rule is: a plan whose `plan_executability.executable` is false must not reach `PLAN_COMPILED`. Wiring it today would stop the exit-gate run at `PLAN_COMPILED` on every machine until the three contracts are authored — a regression of a passed gate that only the spec-root pass can lift, not the runtime. The deferral is visible, not silent: the ledger event, the result record, `docs/PHASE5_RESEARCH_SLICE.md`, `TASKS.md` and this ADR all say so, and the acceptance test computes its expectation from the contract files actually on disk, so the day the contracts land the recorded verdict flips and the block is the next thing to wire.
4. **What the slice did not gate on 2026-09-03, stated plainly (both paths were re-homed behind `invoke` on 2026-09-04 when their contracts landed; `OUTSIDE_CAPABILITY_PLANE` is now empty, the mechanism stays).** Two things in the slice look like capabilities but are not routed through `invoke`: (a) audio → transcript ingestion via the `Transcriber` port (fixture or offline faster-whisper), which happens at ledger offsets 2–5, before the goal is compiled to a Workflow IR at 11.5 — it is ingest, not an execution of the IR's `transcribe` node; (b) the synthetic research memo the harness writes so that criterion 5's trace has an artifact to point at — it is not an execution of `artifact.generate_research_paper`. Both are declared in code (`OUTSIDE_CAPABILITY_PLANE` in the slice) and recorded per run under `capability_resolution.performed_outside_capability_plane`, distinct from `not_performed` (`literature_search`, which nothing performs) and from `invoked` (the catalog's own observation log of what actually passed `invoke`, not a literal the slice writes); the memo's `ArtifactPublished` event carries `contract_backed: false`. The declaration is self-expiring: the run refuses to start (`CAPABILITY_BYPASS_NO_LONGER_JUSTIFIED`) the moment one of those refs gains an ACTIVE contract, so the bypass cannot outlive its reason — re-homing that path behind `invoke` becomes the prerequisite for the next run. "Refuses to start" is literal: the catalog is loaded and the check made immediately after the spec root is resolved, before the runtime directory is prepared, before any adapter is selected and before ingest, so nothing reaches the append-only ledger first (the same early load also makes a corrupt or duplicate-id catalog abort the run before any artefact exists).
5. **Runtime-side shapes that the spec root did not yet define (historical as of 2026-09-03; both registered 2026-09-04, see §Consequences 2–3).** `CAPABILITY_RESOLUTION_BLOCKED` is not registered in `status-codes.schema.yaml`; the state machine's `trigger_signal` is a bare string by that schema's own design, so the runtime can emit it without a schema change. The `resolve()` result mirrors `method_resolution_result` field-for-field (`candidate_capabilities`/`blocked`, plus a machine-readable `blocked.unresolved`/`blocked.resolvable` split) and is deliberately not validated against any schema, because none exists. Both are `NEW_DESIGN` runtime records pending spec-root registration (§Consequences).

## Alternatives rejected

- **Wire the plan-level BLOCKED transition now.** The slice would fail at `PLAN_COMPILED` on the live spec root; the whole suite → red; the Program Plan §11 Phase 5 gate would flip back to blocked by a runtime commit, without the operator deciding to accept that. The runtime cannot lift the block (the contracts are spec-root content). Rejected for sequencing, not for principle — the rule itself is accepted in Decision 3.
- **Author the three capability contracts in this change.** They are spec-root instances validated by golden test 2c against `capability-contract.schema.yaml`, each with grounding, `compilation_decisions`, `verification` and (for `transcribe`) the MP §8.4 `AudioVideo → Transcript` typing — the "next Phase 3 capability-contract pass" OQ-P5-1 already names, with its own owner. Out of this change's stated scope (`ai_lego/*`).
- **Route ingest transcription through the invocation gate now.** It would block on `transcribe` for the same missing-contract reason and take the whole slice with it; deferred together with the contracts (Decision 4), and recorded rather than hidden.
- **Skip unresolved nodes silently and let the plan proceed as "executable".** That is the "detector fires but nobody reads it" pattern round 2 of ADR-022 removed for gates; rejected outright. The plan verdict is recorded as not executable, not massaged.
- **Resolve capabilities only at invocation (never at plan time).** MP §7 places the resolver in the request pipeline, but MP §8.4's "在執行前拒絕" plus EC §10's `PLAN_COMPILED` state mean an unexecutable plan must be knowable before execution starts; invocation-only gating would discover a missing REQUIRED_BY_RISK contract only after upstream steps had already run.

## Independent review (same day, one critic agent): 0 critical / 2 major / 8 minor / 6 nit — every major and minor fixed

- **(major)** The plan verdict never reached the records of record: the manifest's `results` said `PASS` unconditionally and the CLI printed `PASS` with no qualifier while the nested record said `executable: false`. Fixed: the three additive `results` fields and the CLI `WARN:` line above.
- **(major)** The record could not distinguish "not performed" from "performed outside the capability plane", the module docstring claimed more than `invoke` can guarantee, and `transcribe`'s status as ingest existed only in the author's head. Fixed: Decision 4 as now written (declaration in code, per-run record, `contract_backed: false`, bounded docstring, self-expiring guard).
- **(minor)** `plan_executability` trusted any resolution — an empty one read as fully resolved, and a method-shaped one raised a bare `KeyError`. Fixed: `CAPABILITY_PLAN_COVERAGE_MISMATCH`.
- **(minor)** Duplicate contract ids silently last-wins; an unreadable contract file escaped as a parser exception with no domain meaning. Fixed in the shared scan for both catalogs: `CONTRACT_ID_DUPLICATE`, `CONTRACT_CATALOG_UNREADABLE`.
- **(minor)** Test oracles used "file exists" where the rule is "exists and ACTIVE" (a DRAFT contract would have turned a correct block into a red test); `invoked` was a literal the slice wrote about itself. Fixed: independent on-disk oracle in both test modules; `invoked` is the catalog's observation log.
- **(minor)** Audit/manifest `capability_version` carried the package version although the contract version had just been resolved; both catalogs' labels copied the host's absolute spec-root path into the append-only ledger. Fixed: contract version and path in the audit/log entries; fingerprint labels (`live:capabilities/contracts@<sha256[:12]>`) over each entry's id, path, status, version and the file's own `content_sha256`.
- **(minor, follow-up)** the method-side per-invocation gap — Consequences 5.
- Nits fixed: node-without-ref domain error, one `capability_record` built once for event and result, count-free comments, import order. Not changed: `frozen=True` with a mutable `contracts` dict (nothing hashes or mutates a catalog; noted, not worth the indirection).

### Second pass (same day, a second critic agent on the fixed code): 0 critical / 2 major / 5 minor / 3 nit — all fixed, after an invariant analysis

The same code drawing findings twice in a row triggers this repo's rule: name the class before fixing the instance. Four classes, each closed as a class:

- **Guarantee sentences stronger than the code** — the "refuses to start" guard ran *after* ingest had already written ~9 events to the append-only ledger; the "content fingerprint" hashed only id/path/status/version; a gate-table evidence pointer named a test that did not exist. Invariant: a guarantee is enforced before the thing it guards, and every evidence pointer resolves by grep. Closed: the catalog is loaded and the bypass check made first thing after the spec root resolves; the fingerprint now includes each file's `content_sha256`; the pointer was corrected.
- **Records of record with borrowed semantics** — the `run_statistics` log entry claimed a method that does not exist, at the package version, under the top-level execution id. Invariant: every field carries the semantics its schema defines. Closed: own invocation id, contract version in every version field, `contract_sha256`, an in-code note that the entry is a capability invocation homed on the method log, and Consequences 6.
- **Declarations gated on unrelated conditions** — the bypass declaration was filtered by plan membership while the bypass itself is unconditional. Closed: declared unconditionally.
- **Property tests that pin one side or a literal** — the no-host-path property was asserted for the capability catalog only; the invocation-log test assumed `literature_search` is uncontracted (the very assumption the spec-root follow-up will change); the on-disk oracle existed twice. Closed: both catalog labels asserted; an impossible ref; one shared `tests/support.py` oracle.
- Nits closed: the scan ignores case-insensitive glob hits on Windows (a catalog must not depend on the host OS); a `capability_refs()` helper is the single place that walks the IR for capability refs, so a malformed node has one domain error instead of a caller's bare `KeyError`.

Mutation evidence on the final code: forcing `contract_catalog.is_active` to return true turns the empty-catalog, live-catalog and acceptance mutation tests red; disabling the coverage guard turns `test_a_resolution_that_does_not_cover_every_ir_capability_node_is_refused` red; both restored → suite green (count in the gate table).
