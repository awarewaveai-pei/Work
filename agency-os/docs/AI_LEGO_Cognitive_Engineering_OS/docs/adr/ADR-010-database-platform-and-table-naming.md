## Context

This ADR resolves two related, previously-undecided questions surfaced in direct conversation with the operator (not a Phase 1 register finding — no `P1-CONFLICT`/`P1-DUP`/`P1-GAP` ID applies), which is why the "解決的 findings" column in `ADR_INDEX.md` reads differently from ADR-001~009's Phase-1-lineage entries.

**(a) Where does AI LEGO's database live?** The operator asked whether AI LEGO's database should be "unified" with the existing Lobster Factory / AwareWave production Supabase instance (the one this repo's other work already operates against — see the existing `mcp__supabase-awarewave-postgres` tool, which is a Supabase-hosted Lobster Factory production instance, confirming Supabase is already this team's operational vendor of choice, not a new tool to learn). Verified by full-text grep: `docs/architecture/DATA_ARCHITECTURE_PLAN.md` and every file under `docs/architecture/` contain **zero** occurrences of "Supabase" (also verified zero across all three ~268KB mother documents). `DATA_ARCHITECTURE_PLAN.md` §1 (L17-33) already made the storage-*engine* decision — single PostgreSQL instance + `pgvector`/Apache AGE/TimescaleDB/GIN extensions, no separate Vector/Graph/Search/TSDB products at MVP scale (L33: *"MVP 階段 8 類需求可用 1 個 PostgreSQL 實例...+ 1 個 Object Storage + 1 個 Key Vault 全部滿足"*) — but that decision is vendor-agnostic: it says "a Postgres instance," not "whose Postgres instance" or "hosted where." This ADR closes that specific gap: which hosting *platform*, and — the part directly relevant to blast radius — is it the *same physical project/instance* as an unrelated internal tool.

**(b) How should tables be named?** The operator's explicit requirement, given after accepting the platform-separation recommendation: *"table 命名要有邏輯，相同類似的可以擺在一起"* (table naming must be logical; similar/related tables should be grouped together). AI LEGO's Domain Model has 23 objects (22 from Master Plan §3, `MP:330-357`, plus `Tenant` as object #23 per ADR-003) and no existing document assigns any of them a concrete SQL table name — `REPOSITORY_ARCHITECTURE.md`'s Bounded Context Analysis table (L22-46) assigns each object a *directory* path (e.g. `/core/domain/tenant`), and `specs/domain/tenant.schema.yaml` (Phase 3, commit `9d8ab2e3`) defines JSON-Schema *fields*, but neither commits to a relational table name. This ADR is the first document in the project to do so — verified by grep across the project for `table_name`/`naming convention`/`prefix scheme`: zero pre-existing hits outside Phase-0 findings about unrelated document-registry tables.

## Decision Drivers

1. **Reuse ADR-003's already-settled Tenant Isolation reasoning, don't re-litigate it.** ADR-003 (Decision Driver #2, `ADR-003:28`) already established: *"Security/Privacy is non-negotiable — the corpus's own stated ambition... makes cross-tenant leakage the single most damaging failure mode available to this system."* Sub-decision (a) below is a direct application of that same driver to a boundary ADR-003 didn't originally consider (an unrelated *internal tool*, not a customer tenant, sharing infrastructure).
2. **Do not manufacture a false unification for the sake of convenience.** Lobster Factory and AI LEGO have disjoint customer bases, disjoint compliance postures, and disjoint lifecycles; sharing a database project because both happen to use Postgres would be the same category of error ADR-009 rejected for Plane/Workspace/Module (forcing three different abstraction layers into one name because they share surface similarity).
3. **Vendor familiarity is a legitimate driver, vendor *sharing* is not.** Same principle as `DATA_ARCHITECTURE_PLAN.md` §XXII discipline (avoid premature distributed architecture, but also avoid premature *convenience* coupling) — reusing a known vendor's tooling is good; reusing a known vendor's *specific project* for an unrelated product is a blast-radius decision, not a tooling decision.
4. **Table naming must derive from groupings the project has already made, not a freshly invented taxonomy.** `REPOSITORY_ARCHITECTURE.md`'s Bounded Context Analysis (L22-46) already annotated every one of the 23 objects with its Shared-Kernel role, Control-Plane/Trust-Fabric tag, or bounded-context cluster membership — this ADR's prefix scheme is a direct read-off of those existing annotations, not a new classification pass.
5. **30-year survivability**: table names should be legible independent of which directory layout iteration is current (`REPOSITORY_ARCHITECTURE.md` is itself still `PROPOSED`), so the scheme groups by stable semantic clusters (tenancy, provenance, control-plane, trust, canvas, data-science) rather than by literal current directory strings that may still move.

## Sub-decision (a): Database Hosting Platform — Options Considered

**Option A — Shared Supabase instance/schema with Lobster Factory.** AI LEGO's tables live inside the same Supabase project already used by Lobster Factory / AwareWave production (the project behind `mcp__supabase-awarewave-postgres`), either in the same schema or a separate Postgres schema within that one project.

**Option B — Separate Supabase project, same vendor (RECOMMENDED).** A new, independent Supabase project — its own project ref, its own connection string, its own service-role key, its own `auth.users` table, its own region pin — provisioned specifically for AI LEGO. Same vendor as Lobster Factory (reuses team tooling/muscle memory), but a genuinely separate instance.

**Option C — Fully different vendor / self-hosted PostgreSQL.** Either a different managed-Postgres vendor (Neon, RDS, Cloud SQL, etc.) or a self-hosted instance (e.g. on `ks-aw-01` or a dedicated box), independent of Supabase entirely.

| Dimension | Option A — shared w/ Lobster Factory | Option B — separate Supabase project (RECOMMENDED) | Option C — different vendor / self-hosted |
|---|---|---|---|
| Tenant-Isolation / blast-radius conformance (ADR-003) | **Fails** — Lobster Factory becomes an implicit "super-tenant" with infra-level (project-owner) access to AI LEGO data, a privilege level *outside* and *above* the outermost isolation boundary ADR-003 declares (`Tenant Isolation → Workspace Isolation → ...`, `ADR-003:12`). ADR-003's own words for the CAS case apply directly here by analogy: sharing infrastructure with an unrelated system "cannot simultaneously be the thing whose isolation is claimed as the platform's most fundamental fault/security boundary" (`ADR-003:13`). | **Passes** — physically separate project; AI LEGO's own `DATA_ARCHITECTURE_PLAN.md` §6 shared-schema+RLS tenant-isolation model (`DATA_ARCHITECTURE_PLAN.md:141`) remains the *only* isolation boundary inside AI LEGO's own data, with no unrelated internal tool sitting above or outside it. | **Passes** — same isolation property as B; vendor identity is orthogonal to this dimension. |
| Security / access-boundary | A Lobster Factory operator credential, service-role key, or an over-broad grant issued for Lobster Factory work implicitly reaches AI LEGO rows (or vice versa) — a bug or incident in one system's access control leaks into the other's. | Two independent project-level credential boundaries. A Lobster Factory incident (e.g. a leaked service-role key) cannot touch AI LEGO by construction — different connection string, different key, different `auth.users`. | Same isolation property as B; additionally removes Supabase's own control-plane as a shared failure domain between the two products, at the cost noted below. |
| Cost | Lowest marginal cost — reuses existing project's compute/storage tier, no new billing line. | Small incremental cost — one new Supabase project. `DATA_ARCHITECTURE_PLAN.md` §1's MVP posture (single Postgres, no premature distributed infra) keeps this at Supabase's lowest paid/free tier initially. | Similar-to-higher — self-hosted Postgres needs its own backup/PITR/HA operations that Supabase already packages; a different managed vendor adds a second vendor relationship. |
| Complexity / team familiarity | Lowest — zero new tooling. | Low — same client libraries, same migration/RLS tooling, same operator muscle memory already exercised via `mcp__supabase-awarewave-postgres` and the `supabase-engineer` agent, just pointed at a new project ref. | Highest — no existing team familiarity with a second vendor or self-hosted stack; would need new backup/DR runbooks distinct from the Hetzner-VPS-specific patterns already built (`runbooks/HETZNER-SERVER-MIGRATION-AND-DISASTER-RECOVERY-RUNBOOK.md`), which target VPS/container infra, not a Postgres-as-a-service replacement. |
| Migration cost (Day 1 / greenfield) | N/A — AI LEGO has zero rows and zero code today (same "cheapest point in the system's 30-year life to fix this" framing ADR-003 used, `ADR-003:23`). | N/A — a fresh project is provisioned once; nothing to migrate away from. | N/A — same as B on this dimension alone. |
| Reversibility | **Poor once tenants exist** — unwinding a shared instance later means re-provisioning a new project and migrating live data under the same conditions ADR-003 already flagged for shared CAS storage: `ADR-003:118` describes reversing a shared-blob decision after tenants exist as *"explicitly NOT safe post-launch"* — the same logic applies to un-sharing a database instance after real rows exist in both products. | Easy at any time before launch (nothing to unwind); after launch, standard `pg_dump`/restore migration to a different vendor remains possible if ever needed — never trapped by a prior sharing decision. | Same as B on reversibility; the discriminator against B is the Complexity row, not this one. |
| Data residency / compliance fit (ADR-003's `Tenant.data_residency_region` field, `ADR-003:48`) | Weakened — Lobster Factory's own regional footprint and AwareWave-client contractual constraints become entangled with whatever residency guarantee an AI LEGO tenant is promised. | Clean — AI LEGO's project can be region-pinned entirely independent of Lobster Factory's existing region choice. | Clean — same as B, with full control over physical region, at the operational cost already noted above. |
| 30-year survivability | **Low** — ties two unrelated products' lifecycles together at the infrastructure layer; decommissioning, migrating, or selling off either product becomes entangled with the other. Same failure shape as the CAS Option-B elimination in ADR-003 (`ADR-003:81`: eliminated "rather than merely disfavored" once the sensitivity point was identified). | **High** — structural separation mirrors ADR-003's own core argument: a physical/instance-level boundary survives personnel, vendor-contract, and reorg changes better than a policy-level promise ("we'll keep the schemas separate") ever could. | **High** — same structural strength as B; the only discriminator vs. B is operational maturity/familiarity, not the isolation property itself. |

**Sensitivity point** (ATAM term, reused from ADR-003's own Method Used section, `ADR-003:98`): Option A's viability hinges entirely on whether "shared project, separate schema" can be trusted to stay separate forever under future engineers, future migrations, and future incident response — i.e. it depends on *policy discipline sustained for decades*, which is exactly the failure mode Decision Driver #1 (30-year survivability) exists to distrust. This is why Option A is rejected outright rather than merely disfavored, mirroring how ADR-003 eliminated its own Option B for the same reason (`ADR-003:81`).

**Tradeoff point**: Option B vs. Option C is the real tradeoff — C has zero shared-vendor control-plane risk with Lobster Factory (an even stronger isolation posture than B), but at a real, immediate operational cost (no existing team tooling/runbooks for it) that buys no additional benefit at AI LEGO's current zero-tenant, zero-row stage. Per `DATA_ARCHITECTURE_PLAN.md`'s own discipline of not pre-building for scale that hasn't materialized (Program Directive §XXII, `DATA_ARCHITECTURE_PLAN.md:7-9`), paying that cost now is premature. C remains a legitimate future escape hatch (see Consequences) if AI LEGO later needs a Postgres capability Supabase doesn't expose, or a residency requirement no Supabase region satisfies.

### Full mapping table (23 of 23 objects, each with a real citation)

Naming convention: `<prefix>_<object_name_snake_case_plural>`, all lowercase. Pluralization: **plural**, following the common Postgres/Rails convention that a table name denotes the *set of rows* it holds (one row = one instance of the Domain Model object), which is a distinct naming layer from `REPOSITORY_ARCHITECTURE.md`'s directory names (singular, e.g. `/core/domain/tenant`) — a directory holds *one* schema/module definition, a table holds *many* rows; the two layers are allowed to differ in number without contradicting each other. Two objects (`Evidence`, `Knowledge`) are mass nouns with no natural plural in English (same class as "data"); these are kept in their base form rather than an invented plural (`evidences`/`knowledges` are not standard English), consistent with not inventing new terminology per Decision Driver #4.

### Postgres identifier constraints — spot-checked

- **63-byte identifier limit**: the longest proposed name, `canvas_human_contributions`, is 26 bytes (7-byte prefix + 19-byte base); the next longest, `data_analysis_plans`, is 20 bytes. Every one of the 23 names is under half the limit — no truncation risk even after adding standard suffixes for join/index tables later (e.g. `_id`, `_v2`, a future `data_analysis_plans_archive` would still be well under 63).
- **Reserved-word collision**: spot-checked every proposed base name (`tenants`, `workspaces`, `projects`, `sources`, `evidence`, `claims`, `knowledge`, `capabilities`, `workflows`, `executions`, `policies`, `identities`, `decisions`, `human_contributions`, `annotations`, `ideas`, `artifacts`, `datasets`, `analysis_plans`, `analysis_runs`, `simulations`, `experiments`, `outcomes`) against PostgreSQL's reserved-keyword list (`user`, `order`, `group`, `table`, `column`, `check`, `select`, `from`, `where`, `primary`, `references`, etc.). **Zero collisions.** Two names border SQL-adjacent *non-reserved* keywords worth flagging even though they don't require quoting: `identities` is adjacent to the non-reserved keyword `IDENTITY` (used in `GENERATED ... AS IDENTITY` column syntax, PostgreSQL 10+) and `policies` is adjacent to the `CREATE POLICY` statement — both are documented as *non-reserved* in PostgreSQL's own keyword appendix, meaning they are safe to use unquoted as table names, but this ADR flags them explicitly so a future engineer doesn't need to re-derive that safety judgment from scratch. Because every table name in this scheme is always prefixed (`trust_identities`, `trust_policies`, never bare `identities`/`policies`), the question is moot in practice regardless.
- **Case/quoting**: all names are already lowercase snake_case, so no quoting is ever required for Postgres's default case-folding behavior.

## Method Used

- **Direct application of an already-decided principle** (ADR-003's Tenant Isolation / blast-radius reasoning) to a new boundary case, rather than re-running ATAM from scratch — the tradeoff structure (Correctness/Security/Cost/Complexity/Migration/Reversibility/Cross-border/30-year survivability) is reused verbatim from ADR-003's own comparison-matrix dimensions (`ADR-003:69-79`) because the underlying question (does sharing infrastructure with an entity outside the isolation model break the model) is structurally identical.
- **Evidence Triangulation** (same method ADR-005/ADR-009 used, `ADR-009:162`): Sub-decision (b)'s grouping was cross-checked against three independent sources that had to agree before a cluster was accepted — `REPOSITORY_ARCHITECTURE.md`'s Bounded Context Analysis table annotations, its own Proposed Directory Tree groupings, and (for the Canvas cluster specifically) ADR-009's independently-derived Plane/Workspace/Module cross-layer table.
- **R4 聲稱即驗證**: the "zero Supabase mentions" and "zero pre-existing table-naming convention" claims were both verified by actual grep runs (not assumed), documented in the Evidence section below with exit codes.

## Recommendation

1. **(a)** Adopt **Option B — a separate Supabase project for AI LEGO**, same vendor as Lobster Factory for team tooling familiarity, but a genuinely distinct project (own project ref, connection string, service-role key, `auth.users`, region pin). Reject Option A outright — it makes Lobster Factory an implicit super-tenant outside ADR-003's own outermost isolation boundary, the same category of structural failure ADR-003 already eliminated Option B for in the CAS decision. Option C is not rejected but deferred — it remains the fallback if a future, concrete requirement (a Postgres capability Supabase doesn't expose, or a residency constraint no Supabase region satisfies) actually materializes; adopting it now would be premature infrastructure cost with no corresponding benefit at zero-tenant scale.
2. **(b)** Adopt the seven-prefix scheme above (`platform_`, `prov_`, `control_`, `trust_`, `canvas_`, `core_`, `data_`) and the full 23-row mapping table as the table-naming convention for AI LEGO's relational schema. All 23 tables live in the single PostgreSQL instance `DATA_ARCHITECTURE_PLAN.md` §1 already decided on (shared-schema + RLS per `DATA_ARCHITECTURE_PLAN.md:141`), inside the separate Supabase project from (a) — the two sub-decisions compose without conflict: (a) decides *which physical project*, (b) decides *what the tables inside it are called*.

## Consequences

- **Positive**: AI LEGO gets a clean, structurally-isolated data boundary from Day 1, before any tenant or row exists — the cheapest point in its lifecycle to get this right (same framing ADR-003 used, `ADR-003:23`). Table names are immediately legible by cluster without needing to consult the (still-`PROPOSED`) directory tree, and the scheme survives that document's eventual directory reshuffling because it's grounded in semantic clusters, not literal current paths.
- **Negative / accepted cost**: one additional Supabase project to provision and pay for (small, per the Cost row above); the operator/team must remember AI LEGO and Lobster Factory are two separate Supabase dashboards, connection strings, and credential sets going forward — a minor cognitive-overhead cost, not a technical one.
- **Follow-up surfaced, not solved here**:
  1. This ADR does not design the actual SQL migrations, column-level schemas, foreign-key graph, or RLS policies for these 23 tables — only the platform choice and the naming convention. That is downstream implementation work (Phase 3/5 per `MACHINE_READABLE_SPEC_PLAN.md`'s wave structure) which should consume this table's `table name` column directly.
  2. The `prov_` cluster's mass-noun tables (`prov_evidence`, `prov_knowledge`) may eventually need companion junction/version tables (e.g. `prov_evidence_versions`) — this ADR does not design those, it only confirms the base names are safe to build on.
  3. If Option C is ever triggered later (per the Recommendation's fallback condition), the table-naming convention in (b) does not need to change — it is vendor-agnostic by design.

## Migration / Rollback

- **Migration**: zero-cost at this moment — AI LEGO has no code, no data, and no provisioned database of any kind yet (same greenfield state ADR-003 and ADR-009 operated under). "Migration" here means: (1) provision a new, separate Supabase project; (2) apply the 23 tables using the names in the mapping table above, inside that project, under the shared-schema + RLS model `DATA_ARCHITECTURE_PLAN.md` §6/§7 already committed to.
- **Pre-launch gate**: before any AI LEGO tenant is onboarded, verify by real test that (1) the AI LEGO Supabase project's credentials cannot read or write any Lobster Factory table (trivially true if it's a separate project, but worth a real connectivity test rather than an assumption), and (2) RLS policies on every `platform_`/`prov_`/`control_`/`trust_`/`canvas_`/`core_`/`data_` table correctly scope by `tenant_id` before the first real tenant's data is written — mirroring ADR-003's own pre-launch-gate discipline (`ADR-003:117`).
- **Rollback**: reversing Sub-decision (a) after tenants exist (i.e., later deciding to merge into Lobster Factory's project) is explicitly **not safe post-launch** — same logic as ADR-003's CAS Option A/B rollback asymmetry (`ADR-003:118`). Reversing *before* launch is a zero-cost do-over (drop the project, provision differently). Sub-decision (b)'s naming scheme can be renamed at any time pre-launch via a simple `ALTER TABLE ... RENAME TO` per row; post-launch renames are a standard, low-risk `ADR-005` 15-step Expand-Contract migration (add new name as a view/alias, migrate readers, drop old name) — nothing about this naming scheme creates an irreversible post-launch dependency the way the hosting-platform decision does.
