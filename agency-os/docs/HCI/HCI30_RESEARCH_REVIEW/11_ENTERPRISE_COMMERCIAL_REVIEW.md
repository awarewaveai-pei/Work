## Narrative Analysis

## Central question

Can HCI-30 actually grow from a single Personal user to a Group/Enterprise tenant without a rewrite, or does it only look that way on paper? And is HCI-30 commercially independent from AI LEGO / Cognitive OS, or is there hidden coupling?

Short answer to both: **the paper design is directionally sound and better than most greenfield SaaS plans I have reviewed, but it is currently 100% unimplemented prose with zero schema, zero API, zero billing hook, and zero migration mechanics** — and the one piece of *real, shipped, production* commercial-tenancy code that exists in this repo today (`portal.aware-wave.com`, commit `83277d80`, 2026-08-29) was built by **reusing a different, older "organizations" model that predates and does not match the blueprint's Tenant→Organization→Workspace→Project hierarchy at all.** That is not a hypothetical risk — it already happened, in this exact codebase, three weeks before this review. It is the single most important fact for this lens, and I lead with it because it turns "will this architecture survive contact with a second product?" from a speculative question into an already-observed case study.

## Evidence: the blueprint's tier/tenancy model is pure narrative

`08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md` (08:1-196) defines six editions (Personal/Professional/Team/Enterprise/Group/Private), a `Tenant → Organization → Workspace → Project` hierarchy (08:86-104), an "Entitlement architecture" (`Product/Plan/Feature/Entitlement/Limit/Subscription/License`, 08:106-128), white-label (08:154-163), an upgrade path (08:165-175), a Personal→company transfer wizard (08:177-181), and Group/M&A support (`Tenant Merge/Split/Organization Transfer/Workspace Transfer`, 08:183-195). `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md` adds isolation Tiers A-D (12:41-53), data-residency fields (12:55-65), a control-plane/data-plane split (12:67-88), offline licensing (12:90-102), export and account-termination lifecycle (12:131-161).

None of this has a single field name, endpoint, migration, or state machine attached anywhere in the pack. This is not my inference — the blueprint's own self-audit says so: `21_HCI_TOP_TIER_GAP_ANALYSIS.md:16` scores "Commercial edition strategy" 8.0/10 as *vision* but scores "Executable domain specification" 4.5/10 and "API/event contract completeness" 4.5/10 (21:18-24), and `16_OPEN_DECISIONS_AND_NEXT_ARTIFACTS.md:117-118` explicitly lists "Paid plan packaging/pricing" and "Enterprise licensing" as still-open items 16 and 17. I confirmed independently: `Glob D:\Work\agency-os\systems\**` returns zero results — the `systems/hci30/` tree that 17_REPOSITORY_LAYOUT_AND_PATHS.md and 22_MASTER_PLAN.md both point at does not exist. There is no domain ERD, no `tenant_id` column defined anywhere for HCI, no entitlement table, no plan/feature model, no billing webhook. Grepping the whole repo for "Tenant Merge", "Tenant Split", "Organization Transfer" (the Group/M&A bullets at 08:183-195) returns exactly one hit: the blueprint file itself. It is not designed anywhere else, and it is not scheduled in either the Phase roadmap (14_ROADMAP §Phase 9, 14:101-107, which just says "Implement: multi-organization hierarchy...") or the Wave implementation plan (22, which never reaches it in the portion covering Waves 0-5). A bullet point is not a plan.

This matters for the central question because "grow without a rewrite" is precisely the kind of claim that can only be tested against a concrete schema. With no schema, the honest answer is: **untested, unverifiable, and — based on what already happened with `portal` — actively contradicted by the one real data point available.**

## Evidence: the real implementation already diverged, and diverged in the specific way 08 warns against

`08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md:100-104` states, in bold-equivalent emphasis: *"Tenant is a security/customer boundary. Organization is a real-world legal/business entity. **Never conflate the two.**"*

`PORTAL_AWARE_WAVE_DESIGN_PROPOSAL.md` (agency-os/docs/operations/, v8, marked "已部署" / deployed 2026-08-29) documents exactly this conflation happening, deliberately and for good reasons, in production:

- The portal's customer-identity layer reuses `lib/tenant-guard.ts` and the `organizations` table from `lobster-factory/packages/db/migrations/0001_core.sql:3-5`, which I verified directly: `create table if not exists organizations (... type text not null check (type in ('agency', 'client')))`. This table's `type` enum was designed for the WordPress-maintenance agency/client relationship — the PORTAL_..._PROPOSAL.md document says so itself (§3 risk table, PORTAL doc line ~43): *"`organizations` 表原本是為 WP 代操客戶設計...這張表原生語境是「幫這個客戶代操網站」，不是「這個客戶訂閱了我們的 SaaS 產品」"* (this table was originally designed for WP-management clients, not SaaS subscribers).
- On top of that reused table, a single new table `organization_product_subscriptions` was bolted on (PORTAL doc §5, lines 76-88): `organization_id, product_key in ('cognitive','hci'), status in ('trial','active','past_due','canceled'), external_tenant_id uuid null`. This is the *entire* real, shipped commercial-edition data model as of this review — one flat status enum per product, no Plan, no Feature, no Entitlement, no Limit, no Workspace, no Project. It is far thinner than 08's "Entitlement architecture" (08:106-128) and does not implement the Tenant→Organization→Workspace→Project hierarchy at all — there is no Workspace or Project layer in the real schema, and `organizations` (not a Tenant object) is the outermost boundary.
- Independently, `agency-os/docs/AI_LEGO_Cognitive_Engineering_OS/docs/adr/ADR-003-tenant-model-and-cas-isolation.md` (ACCEPTED 2026-08-29, same day) defines a *third*, different "Tenant" concept — this one scoped specifically to Cognitive OS's own content-addressed storage and blast-radius chain, with a real schema (`tenant_id, legal_name, status, home_jurisdiction, data_residency_region, encryption_root_key_ref`, ADR-003 lines 42-51) and an explicit statement that *"Tenant is the outermost billing/legal/deployment entity... not a sub-unit within an organization"* (ADR-003:55). This is the object `organization_product_subscriptions.external_tenant_id` is meant to eventually reference — but there is no FK (correctly, per the no-cross-system-DB-coupling rule at 01:113-116 and 18:216-231), no version compatibility statement, and as of this review Cognitive OS has "no code, no provisioning API" (PORTAL doc §2.2, line 34), so the field has never been populated.

So today, inside one repository, there are **three non-identical definitions of "the outermost customer/tenant boundary"**: (1) blueprint 08/12's `Tenant`, pure prose, unowned by any code; (2) ADR-003's `Tenant`, real spec but scoped to Cognitive OS internals and unbuilt; (3) the real, live, shipped `organizations` table, which is neither of the above and was originally built for a third business (WP agency management) entirely. `external_tenant_id` is the single thread meant to eventually stitch these together, and it is a nullable, unenforced, un-typed UUID column with no contract about which of the two competing Tenant definitions it will resolve to. This is the textbook "hidden coupling that only surfaces at the second product" failure mode this review was asked to hunt for, and it is not hypothetical — it is dated, committed, and deployed.

To be fair to the operator: this was a *reasoned* trade-off, not an oversight. The v1→v2 correction recorded in the PORTAL doc (§0) shows the implementer initially planned to build a fresh `portal` schema and caught themselves, citing the zero-rework principle, and chose to reuse `organizations` specifically to avoid building a second parallel "who is an external customer" system. That is the *right instinct* under the given constraints (solo operator, no funded engineering team, real product not yet built). But it means the blueprint's Tenant/Organization separation was the casualty, not `organizations`. The 30-year risk is not that reuse happened — reuse was correct — it's that nobody has yet reconciled the three Tenant definitions, and nothing in the governance layer (ADRs, doc-sync, CHANGE_IMPACT_MATRIX) currently forces that reconciliation before a second real tenant boundary gets built on top of the mismatch.

## Tracing a concrete account through the tiers

Walking a hypothetical "Personal → Enterprise" account exactly as specified surfaces where the paper model breaks even on its own terms, independent of the portal divergence above:

1. **Personal** (08:16-24): "single user, private vault... optional local-first mode." No schema exists for a vault, no definition of what "local-first" persistence looks like relative to the (also undesigned) cloud sync path. 16_OPEN_DECISIONS item 14 lists "Local-first Personal architecture" as still open. There is no way to verify today whether a Personal user's data model is even a strict subset of the Team/Enterprise data model, which is the entire premise of "grows without rewrite."
2. **Professional → Team** (08:26-44): "Adds workspaces, collaboration, RBAC." The real schema has no `workspaces` table scoped to HCI at all (07's table list, 07:144-179, has no workspace/project columns on `evidence`, `assessments`, etc. — only an implied `tenant_id` per 07:84 and 11:75-78). Tenant-context propagation (P0-07 in 21:161-183) is explicitly still an open P0 item, meaning even the *shared-schema-plus-RLS* baseline case has no confirmed field list yet.
3. **Enterprise** (08:45-59): SSO/SCIM/ABAC/DLP/data residency/BYOK/"dedicated DB option." 12's Tier B/C/D (dedicated DB / dedicated app / dedicated region, 12:41-53) are named but have no migration mechanism specified for moving an existing Tier-A (shared DB) tenant to Tier B/C without downtime or data loss — and 13's Expand/Contract migration discipline (13:97-111) is a general principle, never applied to the specific tenant-isolation-tier-upgrade case. This is the single highest-value migration this product will ever need to execute correctly (an existing paying customer demanding dedicated infrastructure, or a compliance-driven forced move) and it currently has a name and no procedure.
4. **Group** (08:60-70): "multi-organization hierarchy, delegated administration... internal chargeback." Zero design anywhere (checked above); not present in the Phase/Wave roadmaps either.
5. **Private / on-prem / air-gapped** (08:72-84): "All deployment modes must share the same HCI core. No customer-specific forks." Good invariant, correctly stated — but nothing describes how air-gapped licensing (12:90-102, offline-verifiable signed licenses) reconciles with a system whose AI LEGO integration (10) is built around live cross-model API calls and whose Public Intelligence layer (06) assumes live internet search. An air-gapped HCI deployment cannot use 06 or most of 10 as specified; the blueprint does not flag this as a deployment-mode-dependent capability matrix anywhere, which means a sales conversation with an air-gapped government buyer will discover the gap live rather than the architecture having pre-declared it.

**Where it would concretely break, in one sentence per tier boundary:** Personal→Team breaks because there is no workspace/project schema to receive the "multiple projects" (08:29) and "workspaces" (08:38) features being added; Team→Enterprise breaks because there is no isolation-tier upgrade migration procedure; Enterprise→Group breaks because the entire tier has zero design; and Private/air-gapped breaks silently because the product's own AI-integration and Public-Intelligence capabilities are incompatible with the deployment mode's threat model without anyone having said so explicitly.

## Commercial independence between HCI-30 and AI LEGO/Cognitive OS

On the specific sub-question of whether the two products can be priced, licensed, and sold completely separately: the *domain* separation is genuinely strong. `09:104-111` and `02:110-116` both explicitly forbid HCI owning AI LEGO's Method Atlas or vice versa, `13:27-28` specifies architecture tests ("HCI core may not import billing provider," "HCI core may not import AI vendor," "no direct DB dependency between HCI and Cognitive OS") that — if actually enforced by CI once code exists — would make the domain cores independently sellable. `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md` is the strongest document in the whole pack for this question: it specifies a bounded case-package request/response contract (10:42-77), an HCI admission gate that never auto-trusts AI LEGO output (10:81-93), version compatibility declarations (10:191-205), and graceful degradation (13:159-176, "If AI LEGO is down, HCI should still support historical reads, manual evidence..."). This is good, disciplined peer-system design and I have no changes to recommend to the *contract shape* itself.

The gap is entirely on the commercial/metering side, which this document does not address at all: nowhere in 08, 10, or 12 is there a mechanism for metering an HCI tenant's calls into `POST /cognitive/v1/workflows/execute` (10:118) against that tenant's *own* entitlements, cost budget, or billing — there is no answer to "if HCI Enterprise customer X calls Cognitive OS 50,000 times this month, whose invoice does that show up on, and does Cognitive OS need X's own subscription/API key to even accept the call, or does it trust whatever `tenant_context` HCI hands it?" The `Request package` schema at 10:45-59 includes `tenant_context` as a bare field with no defined contents, and the control-plane/data-plane split (12:67-88) puts "Usage Metering" in the shared control plane (12:82) but never states whether that metering is unified across products (which would itself be a form of hidden coupling — a shared billing/usage substrate both products depend on) or genuinely per-product (which is unspecified and unbuilt). Given the confirmed real precedent above — that when something is left underspecified, the actual implementation reaches for the nearest existing mechanism regardless of product boundary — I'd bet without a written usage-metering contract, a future implementer reuses whatever billing table `organizations`/`organization_product_subscriptions` ends up growing, which would make HCI and Cognitive OS commercially *coupled through the portal's shared subscription table* even while remaining architecturally decoupled at the domain-DB level. That's a real, foreseeable risk worth flagging now while it's a one-line ADR instead of a migration later.

## What I'd change (with 30-year / migration reasoning per item)

I organize the change items below. The overriding theme: **stop writing more prose about tiers people can't yet build, and instead spend the very next unit of work reconciling the three competing "Tenant" definitions that already exist in this repo** — that is the one item genuinely urgent (it compounds with every day the portal ships more surface area on top of `organizations`), everything else in 08/12 can and should stay exactly as unbuilt prose until Phase 6/7 as the roadmap already says, because building tier machinery now against zero real customers would itself be the overengineering this review is instructed to flag.

I also want to be explicit about what I am *not* recommending: I am not recommending 08/12 be thrown out, and I am not recommending Kubernetes-style multi-tenancy infrastructure be built now. The single-OVH-box reality (verified: `145.239.195.47`, all services in one docker-compose + nginx stack, confirmed in 23_CURRENT_INFRASTRUCTURE_SOURCE_OF_TRUTH.md and independently by the operator's own AGENTS.md baseline) means Tier B/C/D dedicated-DB/dedicated-region isolation (12:47-53) is 3+ years of runway away from being a real question, and the current portal's "shared app, one Postgres, RLS via `organization_id`" shape (Tier A) is exactly right for where this business actually is. The problem is not that Tier A was chosen — Tier A was the correct, minimal, non-overengineered choice. The problem is that it was built as `organizations`, not as a properly-named `Tenant`/`Organization` pair with the isolation boundary in the right place, so the day a real Tier-B upgrade is needed there will be a rename-and-reconcile migration that didn't have to exist if the naming had been fixed while the table was still empty of real customers (it is — signup is still closed, per `ca7037cf`, TASKS.md).

Bottom line for the human architect: HCI-30's commercial-edition story is a credible narrative with good invariants (never conflate Tenant/Organization; no code fork per white-label; upgrade path stated) and a self-honest gap analysis that already knows it isn't built. The one thing that needs a decision now, before more surface area accumulates, is which of the two competing "Tenant" definitions (08/12's HCI-scoped one, or ADR-003's Cognitive-OS-scoped one) becomes the actual platform-wide Tenant, and how `organizations` either becomes that object or is explicitly demoted to a legacy WP-agency table that the new Tenant object supersedes for portal purposes. Everything else in 08/12 is correctly sequenced as future-phase work and should stay that way.
