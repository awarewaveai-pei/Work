# ADR-0028 — Bulk-Export Prevention Control for RESTRICTED Data

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: Export path for RESTRICTED-classified HCI data only (step-up gate, delayed-release window, audit event); this ADR builds no export API, provisions no infrastructure, and authorizes no production deploy or real-person data processing.

## Context

`11_SECURITY_PRIVACY_GOVERNANCE.md:129-131,137` flags bulk export as 🔴 `DECISION PENDING (HD-18)`: V1 lists bulk export only as a "high-risk audit alert" — an after-the-fact notice, not a control. `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:84-88` independently requires customer self-service export ("JSON, CSV, PDF/A, Attachments, Audit export") and already annotates that same requirement as "the highest-value insider/compromised-account exfiltration path for RESTRICTED dossiers." `HCI30_RESEARCH_REVIEW/12_RED_TEAM_FAILURE_ANALYSIS.md:246-265` (RT-08) states the mechanism gap directly: "an alert firing after the export has already completed does not prevent same-day silent exfiltration," rating confidence Medium and `requires_human_decision=true`. The same file's cross-check (`12:466,492,513-521`) confirms zero KEEP item from any of the three independent domain reviewers (schema, security, infrastructure) mitigates RT-08 — it is one of eight security/privacy-territory attacks the security reviewer's own empty KEEP list left standing. `HCI30_RESEARCH_REVIEW/22_OPEN_HUMAN_DECISIONS.md:114-117` (HD-18) records the recommendation: add step-up auth / size threshold / delayed-release, "for Enterprise-tier exports specifically, to avoid adding friction to the low-risk majority of usage."

`08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md` (Product editions, `Personal…Private`) and `11_SECURITY_PRIVACY_GOVERNANCE.md:66` ("Isolation tier … is a formal `Entitlement` mapped by edition, not an ad hoc option") already establish that per-edition configuration is the system's existing pattern for tier-varying controls — a per-tier export threshold fits that pattern rather than introducing a new one. `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:63` already lists "high-risk export audited" as a Wave 2 acceptance criterion (the detective half only); `22:49` requires insert-only ledger enforcement (`REVOKE`+trigger) in Wave 1, which the audit event this ADR requires must reuse rather than duplicate; `22:67` opens Wave 3 as "Contract-first API/events," the Wave where the export endpoint itself is specified. No export code exists anywhere in the repository today: `Projects/internal/hci30/` contains no `export` path (checked 2026-09-02, directory search against `packages/`, `runtime/`, `database/`, `tests/`), and `database/migrations/` contains only `0001_wave1_synthetic_up.sql`/`_down.sql` — no audit-event or export-request table exists yet.

## Decision

**HD-18 = yes.** Exports of RESTRICTED-classified data above a **per-tier row threshold** require, in order: (1) step-up authentication (re-assertion of the existing MFA factor per `11_SECURITY_PRIVACY_GOVERNANCE.md:29`, not a new auth mechanism), (2) a delayed-release window during which the requester may cancel, and (3) an immutable audit event recorded **before** the artifact becomes downloadable. Exports at or below the threshold keep the existing Wave 2 audit-only path (`22:63`). The threshold is **configuration data, not code** — one row-count value per commercial edition (`08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md` §Product editions), editable by policy change, not by a code change or new deploy.

Why the alternatives lose:

- **B — status quo (detective-only, audit alert after completion)**: rejected. This is RT-08's exact finding — the alert fires after the artifact already exists, so it cannot stop same-day silent exfiltration by an insider or compromised account; it only shortens time-to-discovery, not blast radius.
- **C — uniform step-up/delay on every export regardless of size**: rejected. HD-18's own recommendation warns this "add[s] friction to the low-risk majority of usage" — most exports are a tenant retrieving their own small working set, not a bulk dossier pull. Gating on data volume/sensitivity rather than the act of exporting keeps the control proportionate to the harm RT-08 names (third-party legal exposure from a large RESTRICTED disclosure), not to export as a category.
- **D — hard block above threshold with no release path**: rejected. Customer data ownership (`11_SECURITY_PRIVACY_GOVERNANCE.md:82-86`) and the "avoid data hostage" requirement (`12:86`) mean a legitimate large export must still complete. A delayed-release window with cancellation gives the same detection/interdiction value as a block — a window in which anomalous access can be reviewed and stopped — without permanently refusing a tenant its own data.
- **A (chosen) — threshold-gated step-up + delayed-release + pre-release audit, threshold as per-tier config**: matches RT-08's own recommended shape and HD-18's friction constraint simultaneously; the per-tier threshold means Personal/Professional accounts can be configured with a threshold high enough to rarely trigger while Enterprise (holding the largest RESTRICTED dossiers) is configured tighter — without forking the code path per tier.

This ADR does not decide the step-up authentication *mechanism* beyond reusing existing MFA, does not decide HD-13's BYOK/dedicated-DB sales-claim gating (`ADR-0023`), does not decide HD-12's key-rotation runbook (`ADR-0022`), and does not authorize real-person data processing or a production deploy.

## Required implementation gates

Runtime gates are **OPEN**. Each gate names the artifact and the test that must fail before it exists.

1. **Per-tier threshold policy — Wave 2.** `D:\Work\Projects\internal\hci30\governance\export-threshold-policy.yaml`: one `restricted_row_threshold` integer and one `release_delay_minutes` integer per edition (`PERSONAL, PROFESSIONAL, TEAM, ENTERPRISE, GROUP, PRIVATE`, matching `08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md` §Product editions). Test `EXPORT-THRESHOLD-CONFIG-01` (`Projects/internal/hci30/tests/claims/` sibling under `tests/unit/policy/`): fails if the file is missing, is missing an edition row, or if a `grep` of the export code path for a bare numeric threshold literal (outside the policy loader) finds a hit — the threshold must load from this file, not be hardcoded.
2. **Export-release schema — Wave 2, same migration series as the audit schema already planned at `22:59`.** Migration under `D:\Work\Projects\internal\hci30\database\migrations\` adds `export_release_requests` (`id`, `tenant_id NOT NULL`, `requested_by`, `restricted_row_count`, `threshold_at_request`, `status` [`PENDING_STEP_UP`|`STEP_UP_VERIFIED`|`RELEASE_SCHEDULED`|`CANCELED`|`RELEASED`], `release_at`, `canceled_at`, `released_at`, `audit_event_id`), `tenant_id` `NOT NULL` and RLS-covered per `ADR-0016-mandatory-tenant-rls.md`. Test `SCHEMA-EXPORT-RELEASE-01`: migration test asserting the table, the status enum, and the `tenant_id NOT NULL` + RLS-policy pair exist.
3. **Threshold-enforcement test — Wave 3 (Contract-first API, `22:67`), where the export endpoint is specified.** `Projects/internal/hci30/tests/unit/api/test_export_threshold_gate.*` asserts: an export whose `restricted_row_count` exceeds the requesting tenant's configured threshold, attempted without a verified step-up factor, is rejected (HTTP 428/403) and produces **no downloadable artifact**; an export at or below threshold proceeds directly to the existing Wave 2 audit-only path with no step-up prompt. Test id `EXPORT-THRESHOLD-ENFORCE-01`, CI-blocking — this is the failing-test HD-18 explicitly asked for ("a threshold-exceeding export without step-up is rejected").
4. **Delayed-release + cancel test — Wave 3.** `Projects/internal/hci30/tests/unit/api/test_export_delayed_release.*` asserts: after step-up verification, `export_release_requests.status` becomes `STEP_UP_VERIFIED` with `release_at = now() + release_delay_minutes` (from gate 1's config) and the artifact is **not** generated at that point; a cancel call before `release_at` sets `status = CANCELED` and the artifact is never produced; the artifact is generated only when a scheduled job observes `release_at` reached and `status != CANCELED`. Test id `EXPORT-DELAYED-RELEASE-01`, CI-blocking.
5. **Immutable pre-release audit event — Wave 2/3, reusing the Wave 1 insert-only ledger control (`22:49`, `REVOKE`+trigger).** `Projects/internal/hci30/tests/unit/api/test_export_audit_before_release.*` asserts an audit event of type `BULK_EXPORT_RELEASE` (`tenant_id`, `request_id`, `restricted_row_count`, `actor`, `step_up_method`, `requested_at`, `release_at`) is committed and referenced by `export_release_requests.audit_event_id` **before** artifact generation is permitted, and that an `UPDATE`/`DELETE` attempt against that audit row fails under the same ledger trigger already required in Wave 1. Test id `EXPORT-AUDIT-IMMUTABLE-01`, CI-blocking.
6. **Mutation check — same commit as gates 3-5, following `Projects/internal/hci30/README.md:11`'s existing pattern.** `Projects/internal/hci30/scripts/mutation-check-export-threshold.ps1` deletes, in turn: the threshold comparison, the release-delay wait, and the audit-before-release ordering. Each deletion must independently turn `EXPORT-THRESHOLD-ENFORCE-01`, `EXPORT-DELAYED-RELEASE-01`, or `EXPORT-AUDIT-IMMUTABLE-01` red. A version that stays green under any one deletion is not a gate.
7. **Wave-gate blocking precondition.** A future edit to `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md` §Wave 3 (not made by this ADR) must add a 🔴 BLOCKING PRECONDITION line naming `EXPORT-THRESHOLD-ENFORCE-01`, `EXPORT-DELAYED-RELEASE-01`, and `EXPORT-AUDIT-IMMUTABLE-01` green as a prerequisite before the export endpoint ships in any environment, following the precondition pattern already used at `22:79` (P0-10 restore drill) and in `ADR-0022`'s gate 5.

## Consequences

- The audit-only path for exports at or below the per-tier threshold is unchanged; this ADR adds a preventive layer above it, it does not replace `22:63`'s existing detective requirement.
- Low-risk/small exports (the stated majority of usage) see no added friction; only exports large or sensitive enough to cross the configured threshold hit step-up and delay, matching HD-18's explicit friction constraint.
- A tenant on a lower edition with a high configured threshold receives weaker prevention by design, not by oversight — that is the per-tier config working as intended; raising or lowering any tier's threshold is a policy-file change under normal review, not a code change.
- This ADR does not itself build the step-up authentication mechanism, the scheduled release job, or the export API — it specifies the gates those Wave 2/3 deliverables must satisfy.
- A later change to the threshold mechanism, delay window, or audit-event shape requires a new HCI change proposal and an explicit superseding ADR; narrowing a threshold (making the control stricter) is always permitted without one.
