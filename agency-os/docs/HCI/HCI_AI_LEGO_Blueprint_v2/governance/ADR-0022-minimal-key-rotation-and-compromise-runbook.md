# ADR-0022 — Minimal Key-Rotation and Compromise-Response Runbook

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI-30 field-level encryption key lifecycle (rotation + compromise response) for Wave 2 onward; this ADR builds no KMS/HSM/BYOK infrastructure and authorizes no production deploy, real-person data processing, or Enterprise sales claim.

## Context

`11_SECURITY_PRIVACY_GOVERNANCE.md:54-58` requires field-level encryption for RESTRICTED evidence/notes starting immediately (Wave 1/2), while `21_HCI_TOP_TIER_GAP_ANALYSIS.md:134-136` (P1-04) defers `KEY_HIERARCHY.md`, `ENVELOPE_ENCRYPTION.md`, `KEY_ROTATION.md`, `BYOK_MODEL.md`, `CRYPTO_ERASURE.md` to the enterprise-readiness tier. `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md:140` already designs a per-record `encryption_key_ref` column on Evidence/Claim for the still-pending HD-07 crypto-shredding mechanism, but no wrapping hierarchy, rotation procedure, or compromise-response path is specified anywhere. `HCI30_RESEARCH_REVIEW/12_RED_TEAM_FAILURE_ANALYSIS.md:52-58,225-240` (RT-07) names the resulting contradiction directly: "encrypting data with no rotation/compromise plan is security theater," and confirms no reviewer's KEEP list mitigates it (`12:490`, `12:513-515` — the security reviewer's KEEP list is empty). `HCI30_RESEARCH_REVIEW/07_SECURITY_PRIVACY_REVIEW.md:225-240` (SEC-08) and `HCI30_RESEARCH_REVIEW/22_OPEN_HUMAN_DECISIONS.md:85-88` (HD-12) both recommend pulling a *minimal* runbook forward while leaving the full key hierarchy at P1-04.

The master plan already half-anticipates this: `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:55-59` (Wave 2 — Policy + security boundary) lists "key hierarchy" as a Wave 2 deliverable and separately notes "minimal key-rotation/compromise-response runbook (full BYOK stays P1)" as pulled forward; `21_HCI_TOP_TIER_GAP_ANALYSIS.md:104` (P0-11) states the same narrow scope. `D:\Work\Projects\internal\hci30\security\` does not exist (checked 2026-09-02). HD-13 (Enterprise BYOK/dedicated-DB sales-claim gating) is separately resolved by `ADR-0023-block-byok-dedicated-db-sales-claims.md` and is not re-decided here.

**HD-07 is resolved, by `ADR-0018` (same batch), not left open here.** `ADR-0018` gate 2 (`ADR-0018-crypto-shredding-for-erasure.md:33`) already lands a Wave 1 `encryption_key_ref uuid` column and `hci.data_encryption_keys(key_material bytea)` — a per-record key held raw inside Postgres, with gate 6 (`CRYPTO-NOEXTERNAL-01`) explicitly asserting no network-capable extension exists that could reach an external key store. This ADR's DEK→KEK→master hierarchy (below) is a **Wave 2 amendment to that Wave 1 shape**, not an independent or competing design — see §Amendment to ADR-0018 below for the explicit reconciliation, added after an adversarial cross-check (2026-09-02) found the two ADRs specified irreconcilable column shapes with no cross-reference between them.

## Amendment to ADR-0018 *(added 2026-09-02, after adversarial review)*

`ADR-0018` gate 2 lands `encryption_key_ref` referencing an unwrapped `key_material bytea` at Wave 1 — deliberately simple, so HD-07's core guarantee (destroy the key, keep the tombstoned row) is provable before any rotation machinery exists. This ADR's Wave 2 hierarchy **wraps** that same per-record key rather than replacing the mechanism: `hci.data_encryption_keys.key_material` becomes the *DEK*, still per-record, still unreadable by the application role; what changes is that the DEK itself is now stored **wrapped** (encrypted) under a tenant `KEK`, rather than stored raw. Gate 2 below therefore does not delete `encryption_key_ref` — it adds `wrapped_by_kek_version` alongside it and changes what `key_material` *contains* (ciphertext of the DEK, not the DEK itself) in the same migration that creates `tenant_keks`. `ADR-0018`'s erasure mechanism (`hci.tombstone_evidence()`, `hci.record_erasure()`) is unchanged: destroying the (now-wrapped) DEK still makes the row's content permanently unrecoverable, because unwrapping requires both the KEK and the master key.

**Reconciling "key material never leaves PostgreSQL" (`ADR-0018` gate 6) with "master key held outside the database" (this ADR):** the master key is supplied to PostgreSQL as a runtime parameter at connection time (application-layer secret, per `11_SECURITY_PRIVACY_GOVERNANCE.md:56`'s "no production secrets in repository" rule) and used only in-memory by the unwrapping function for the duration of one call — it is never written to a table, and no network-capable extension (`dblink`/`postgres_fdw`/`http`) is used to fetch it, so `CRYPTO-NOEXTERNAL-01` still holds: no *database-initiated* network call exists. The master key living outside the database is a statement about where it is *generated and stored long-term* (a secret manager, per this ADR's own rule), not a claim that the database process never sees it. Compromise of the master key is exactly gate 4's compromise drill below.

## Decision

**HD-12 = yes.** A minimal `KEY_ROTATION_AND_COMPROMISE.md` runbook and a runnable rotation/compromise procedure land in **Wave 2**, before any real (non-synthetic) tenant data exists, using a three-tier key hierarchy: a **per-record Data Encryption Key (DEK)** encrypts each RESTRICTED Evidence/Claim payload; each DEK is wrapped by its tenant's active **Key Encryption Key (KEK)**; each KEK is wrapped by a single **master key** held outside the database (secret manager / environment, per the existing "no production secrets in repository" rule at `11_SECURITY_PRIVACY_GOVERNANCE.md:56`). Rotation re-wraps DEKs under a new KEK version — it never re-encrypts payload ciphertext. Compromise response is revoke the affected KEK version, re-wrap every DEK under it to a fresh KEK version, and emit an audit event; a synthetic drill proves the procedure runs end-to-end before Wave 4 (Evidence/Claim/Assessment core, `22:75-79`) may accept its first row. The full BYOK / customer-managed-key / HSM / envelope-encryption architecture (P1-04) stays P1 and is unaffected — this ADR narrows what ships early, it does not pull the enterprise tier forward.

Why the alternatives lose:

- **B — leave rotation/compromise entirely P1 (current default sequencing)**: rejected. `RT-07` is exact — Wave 1/2 already require field-level encryption for RESTRICTED data; shipping the lock with no way to change it or recover from a leaked key is not a smaller version of the control, it is the control's failure mode arriving on schedule, during the lowest-operational-maturity build phase (`12:231`).
- **C — pull the full P1-04 key hierarchy (BYOK/HSM/envelope encryption) forward to Wave 2**: rejected. No real tenant data exists before Wave 4, and Enterprise BYOK claims are already blocked from being sold until acceptance-tested (ADR-0023). Building HSM/BYOK integration now is engineering cost against a customer that cannot exist yet under this ADR's own precondition; it conflates "can we survive a compromised master key during synthetic testing" (cheap, needed now) with "can a customer supply their own key" (expensive, correctly gated by ADR-0023 until P1-04 lands).
- **A (chosen) — minimal runbook + DEK/KEK/master hierarchy in Wave 2, drilled before Wave 4**: matches the recommendation in `07_SECURITY_PRIVACY_REVIEW.md:237` and `RT-07:237-240` ("write a minimal key-rotation and compromise-response runbook as part of P0... no schema change" beyond what `07:140` already plans) at the point in the schedule (before Wave 4 admits any Evidence row) where it is cheapest to verify and most needed.

## Consequences

- HCI ships field-level encryption in Wave 1/2 with a matching, testable answer to "what happens when a key leaks" instead of a documented gap; RT-07 and SEC-08's "sold-vs-actual" contradiction is closed for the rotation/compromise slice specifically.
- The full P1-04 key architecture (BYOK, HSM, customer-managed keys, envelope encryption at enterprise scale) is unchanged and still gated by ADR-0023's claims register — this ADR adds no evidence toward `CLM-BYOK-01`/`CLM-CMK-01`/`CLM-DEDDB-01`.
- HD-07 (crypto-shredding as the erasure mechanism) remains a separate open decision; this ADR's DEK/KEK/master hierarchy is designed to be compatible with it but does not itself authorize destroying a key as an erasure act.
- `ADR-0018`'s `encryption_key_ref`/`data_encryption_keys` design is not superseded — it is wrapped. `data_encryption_keys.key_material` changes meaning (wrapped DEK, not raw DEK) starting Wave 2; Wave 1 code that assumed a raw DEK must be updated when this ADR's migration lands, but no Wave 1 ERD or column-name change is required.
- A later change to the key hierarchy, rotation cadence, or compromise procedure requires a new HCI change proposal and an explicit superseding ADR — it may not be edited ad hoc in the runbook alone.
