# ADR-0025 — AI Agent Credentials for Restricted HCI Data

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: AI coding agent (Claude/Codex) credential and connection-path boundary for the HCI production database and its encryption key material only; this ADR does not change agent access to any other AwareWave production system, does not authorize processing real-person HCI data, does not authorize a production deploy of HCI, and makes no legal/regulatory claim.

## Context

The present-day pattern at AwareWave is real and not in question: AI coding agents (Claude Code, Codex) hold routine SSH/DB access to the single production box `ks-aw-01`, credentials are named centrally in `mcp/SERVICE_CREDENTIALS_MAP.md` and `mcp/user-env.template.ps1` and consumed via `mcp/user-env.ps1`/env (`AGENTS.md:189`, forbids hardcoding), and deploys/SSH targets are chosen by whichever agent is running under that governance (`AGENTS.md:192-193`). No HCI-specific credential exists in that map today: `mcp/registry.template.json` (423 lines) and `mcp/SERVICE_CREDENTIALS_MAP.md` (108 lines) contain zero references to `hci` (checked 2026-09-02); the closest existing entry is the unrelated `supabase-awarewave-postgres` DSN for the general shared Postgres instance.

`11_SECURITY_PRIVACY_GOVERNANCE.md:35-39` already names the specific technical gap this ADR resolves: on the verified single-box baseline, "direct Postgres/superuser access bypasses RLS and the application layer entirely — a live, present-tense gap given the currently solo-operator-plus-AI-agents operating reality, not a future-hire hypothetical," and commits (not proposes) mandatory session-level `pgaudit` logging plus a minimal `BREAK_GLASS_ACCESS.md` to **Wave 2**, reusing the audit schema `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:55-61` already scopes there ("time-bound elevation + justification + audit event"). What Wave 2's text does not yet say is whether an AI agent session is a class the break-glass and audit-tagging mechanisms must distinguish from a human session — `11_SECURITY_PRIVACY_GOVERNANCE.md:41` carries this open as a DECISION PENDING block naming `HD-15`, sourced from `07_SECURITY_PRIVACY_REVIEW.md:307-320` (SEC-12: "AI coding agents … are not addressed as an access-control actor anywhere in the blueprint") and `22_OPEN_HUMAN_DECISIONS.md:99-102`. `16_ASSUMPTION_REGISTER.md:31-35` (ASM-05) marks the extrapolation `UNVERIFIED`: the present-day general pattern is confirmed, but its unmodified extension to RESTRICTED HCI Person data was never operator-ratified anywhere in the document set. HD-15 itself is filed as "no urgency — decide when convenient" and suggests revisiting "once RESTRICTED HCI data is actually about to go live (Wave 4)" (`11:41`); this ADR resolves it now, ahead of that suggested timing, because the operator's 2026-09-02 delegation covers exactly this class of decision and Wave 1 schema work benefits from the boundary being fixed before any HCI-scoped credential is first minted.

This sits alongside three already-ACCEPTED constraints this ADR must not loosen: ADR-0016 requires forced RLS plus a CI-blocking non-owner cross-tenant test on every tenant-owned table, and carries its own open decision that "until [the tenancy-principal question] is decided, no non-synthetic tenant data may be admitted" (`ADR-0016-mandatory-tenant-rls.md`) — a superuser or `SET ROLE`-capable session (exactly what a standing agent DB credential would be) is the concrete mechanism that open decision warns about. ADR-0014 and ADR-0015 are both `SYNTHETIC RUNTIME GATE VERIFIED … NOT production-authorized`. In other words: no HCI production database exists yet for any actor, human or agent, to hold a credential to — this ADR fixes the boundary *before* one is provisioned, which is the cheapest point to fix it (`22_OPEN_HUMAN_DECISIONS.md:9`, Section A framing: "cheap now, expensive after real data exists").

## Decision

**HD-15 resolved: the standing-credential pattern does not extend to the HCI production instance.** Concretely:

1. **Synthetic/dev HCI instances** (`Projects/internal/hci30/database/`, `infra/local/compose.test.yml`, and any future non-production HCI environment) are unaffected — AI agents keep full, routine access, exactly as today, because no RESTRICTED real-person data can exist there by construction (ADR-0014/0015/0016 are synthetic-gate-only).
2. **No AI agent holds a standing credential to the HCI production database, its host, or its key-management material.** No `HCI_PROD_*`-class DSN, service-role key, SSH key, or KMS/BYOK credential (P1-04, `07_SECURITY_PRIVACY_REVIEW.md` SEC-08 lineage, ADR-0023) may be placed in `mcp/user-env.template.ps1`, `mcp/registry.template.json`, `mcp/SERVICE_CREDENTIALS_MAP.md`, `.mcp.json`, `.claude/`, `hooks/`, or any other path an agent reads at session start or tool-call time.
3. **The only path to HCI production data or keys, for a human or an agent, is the Wave 2 break-glass procedure already committed at `11_SECURITY_PRIVACY_GOVERNANCE.md:39` and `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:59`** — extended here to name the agent actor class it was silent on: a human-authorized ticket precedes the session, the resulting credential is time-bound and scoped to that ticket, the session is justified in writing, and the audit event distinguishes `actor_class = agent` from `human` so SEC-07's pgaudit alerting can treat them differently if a future decision requires it.

**Why the alternatives lose, in engineering terms:**

- **Extend the current pattern unmodified (do nothing)** — the pattern most obviously available since it costs zero new engineering. Loses because a standing agent DB credential is, by definition, a superuser-or-application-role session that exists outside any single ticket window; `11:37` already establishes that such a session bypasses RLS entirely, which makes ADR-0016's forced-RLS control provably incomplete the moment the credential is minted — not a residual risk, a direct negation of an already-ACCEPTED gate. It also collides with ADR-0016's own open question: a standing credential is exactly the kind of long-lived, `SET ROLE`-capable session that ADR blocks non-synthetic data admission until resolved.
- **Physically air-gap HCI production from every agent path, including the human operator's own agent-mediated tooling** — over-corrects. The solo-operator-plus-AI-agent operating model is how this repo's own governance (`AGENTS.md`) runs every other production system, and Wave 2's break-glass mechanism was written assuming a controlled agent-capable path exists, not a hard air gap; building a second, fully isolated operational toolchain duplicates infrastructure this team cannot yet justify pre-revenue and contradicts the already-planned Wave 2 deliverable rather than extending it.
- **Leave it to the pgaudit alert alone (detect, don't prevent)** — `11:37` already commits pgaudit as a Wave 2 deliverable regardless; treating it as sufficient on its own repeats the exact pattern HD-18/SEC-08 (bulk export, BYOK claims) rejected elsewhere in this same document set: a detective control after the fact does not stop the read, and a leaked or session-scoped standing key is indistinguishable from a legitimate one to a log line that only records "non-application-role session," not "was this pre-authorized."

This decision does not authorize provisioning an HCI production database, processing any real person's data, a production deploy, BYOK/dedicated-DB sales claims (governed separately by ADR-0023), or any legal representation about compliance readiness.

## Required implementation gates

Runtime gates are **OPEN**. Each names the artifact and the test that must fail before it exists, and the Wave it lands in per `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`.

1. **Reserved-name convention — Wave 1.** Add a row to `mcp/SERVICE_CREDENTIALS_MAP.md` (format matches existing rows, e.g. `Supabase Postgres` at line 15) marking `HCI Production Postgres` / `HCI Production KMS` as env vars `HCI_PROD_POSTGRES_DSN` / `HCI_PROD_KMS_*`, annotated **"NEVER agent-readable — break-glass only, see ADR-0025"**, with no value populated anywhere in `mcp/`. This makes the forbidden names a single documented list a scanner can consume, rather than an unwritten convention.
2. **CI credential-absence scan — Wave 2 (same Wave as the pgaudit/break-glass deliverables it depends on, `22:59`).** `scripts/check-no-hci-prod-credential-in-agent-paths.ps1`, run by `.github/workflows/hci-agent-credential-scan.yml` on every push touching `mcp/**`, `.claude/**`, `.mcp.json`, `hooks/**`. It reads the reserved-name list from gate 1 and fails (non-zero exit) if any reserved `HCI_PROD_*` name, or a literal DSN/host matching the HCI production host once one is assigned, appears in an agent-readable path. Tests: `HCI-CRED-SCAN-01` (reserved name present in `mcp/user-env.template.ps1` → exit non-zero), `HCI-CRED-SCAN-02` (absent, current state → exit 0, already verifiable today against the 423-line/108-line baseline cited in Context), `HCI-CRED-SCAN-03` (mutation: delete the reserved-name list from the script → `HCI-CRED-SCAN-01` must be observed to flip from red to incorrectly-green, following the mutation-check pattern already used by `ADR-0023` gate 3 and `Projects/internal/hci30/README.md:11`).
3. **Break-glass artifact, agent clause — Wave 2.** `Projects/internal/hci30/governance/BREAK_GLASS_ACCESS.md` (the file already committed at `11:39`/`22:59`) must include a `§Agent Access` section with a required record shape: `ticket_id | authorized_by(human, non-agent identity) | agent_session_id | justification | ttl | issued_at | revoked_at`. Test `BREAKGLASS-AGENT-01` (synthetic harness under `Projects/internal/hci30/database/tests/`): issuing an HCI-prod-scoped credential without a resolvable `ticket_id` whose `authorized_by` is a human identity must be rejected; a credential issued must carry a `ttl` and be unusable after expiry.
4. **Session actor-class tagging — Wave 2, extending the pgaudit deliverable already scoped at `11:37-39`.** Every non-application-role HCI DB session sets `application_name`/session GUC to `actor_class=agent|human` at connect time; the pgaudit alert rule added for RESTRICTED-table reads outside normal app patterns (`11:37`) additionally fires when `actor_class=agent` and no matching open `ticket_id` from gate 3 covers the session window. Test `PGAUDIT-AGENT-TAG-01`.
5. **Production-admission gate — Wave 4, as an additional clause alongside the existing BLOCKING PRECONDITION at `22:81`.** Before Wave 4 admits any real, non-synthetic HCI data, gates 1–4 above must all be green in the same sense `22:81` already requires for the cross-box restore drill: this ADR's gates are a second, independent blocking precondition, not a substitute for it.

## Consequences

- No engineering work is required today to comply — the forbidden state (an `HCI_PROD_*` credential in an agent-readable path) does not yet exist, verified in Context. This ADR fixes the boundary before Wave 1/2 work would otherwise create the temptation to add one as a shortcut.
- Debugging a future HCI production issue costs more than debugging today's shared-box services: an agent cannot open an ad hoc production session the way it can today against `ks-aw-01`'s other services. That added friction is the point — it is the compensating control for RESTRICTED-classification data that `11_SECURITY_PRIVACY_GOVERNANCE.md`'s Admin Principle already calls for.
- This ADR does not change agent access to any non-HCI AwareWave production system; the general SSH/root pattern at `AGENTS.md:189-193` continues unmodified for everything outside HCI's production database and key material.
- A later change (e.g. granting agents a narrower, still-standing HCI-prod read scope) requires a superseding ADR, not a quiet edit to `mcp/user-env.template.ps1` or the CI scanner's reserved-name list.

## Verification and rollback

- Verification recorded here is documentation-only: the decision and gate identifiers are cross-linked to `11_SECURITY_PRIVACY_GOVERNANCE.md` (Admin Principle, `HD-15`), `07_SECURITY_PRIVACY_REVIEW.md` SEC-12, `22_OPEN_HUMAN_DECISIONS.md` HD-15, `16_ASSUMPTION_REGISTER.md` ASM-05, and `ADR_INDEX.md`. The current absence of any `hci`-named credential in `mcp/registry.template.json` and `mcp/SERVICE_CREDENTIALS_MAP.md` was checked directly (2026-09-02); gates 1–5 above have not been implemented and remain open.
- Before implementation, rollback is to supersede this ADR with a later explicit operator decision. After gate 2's CI scanner exists, rollback (loosening the boundary) requires a superseding ADR — it may not be done by editing the reserved-name list or the scanner alone, since gate 2's own mutation test (`HCI-CRED-SCAN-03`) exists precisely to catch that.
- No data, schema, or production system is touched by this ADR; there is no migration or data-rollback path because no HCI production database exists yet.
