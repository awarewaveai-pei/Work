# ADR-0007 — Modular Monolith First

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI-30 deployment/runtime architecture (app topology, DB tenancy, event/integration transport) only; this ADR does not authorize production deployment, real tenant data, or any change to the tenancy/consent/subject-type/RLS ADRs (0009–0011, 0014–0016).

## Context

HCI-30 has not shipped any *application/API* code yet — no `apps/`, no deployable service, nothing `sg-deploy.sh` could target. It does already have real runtime artifacts of a narrower kind: a Wave 1 synthetic PostgreSQL schema, migration, and negative-test suite under `Projects\internal\hci30\database\`, an isolated local-only test harness (`infra\local\compose.test.yml`, `scripts\test-wave1-local.ps1`), and `packages\contracts\validate-request.mjs` (confirmed present 2026-09-02) — none of it a deployable application, all of it explicitly synthetic-only and never pointed at a shared database (`Projects\internal\hci30\README.md:7,9`). The application-code gap this section originally described is what this ADR's Decision addresses; the schema/test-harness code above is orthogonal to it and unaffected. The blueprint already states a directional preference — "Start with a modular monolith unless real scaling constraints require distributed services. Maintain internal bounded contexts so later extraction is possible. Avoid premature microservices." (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:5`) — and V2 marks this "load-bearing" (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:7`). At drafting time, `17_REPOSITORY_LAYOUT_AND_PATHS.md:186` listed `ADR-0007-modular-monolith-first.md` as a required, un-created ADR, and `governance/ADR_INDEX.md:25` recorded it `PLANNED`; both are now filed/`ACCEPTED` in the same batch as this ADR. A directional sentence in a narrative doc is not a decision record: it carries no accept/reject rationale against alternatives, no gates, and nothing a future implementer or CI check can point to when someone proposes splitting HCI-30 into services or standing up a broker. This ADR closes that gap using the option analysis and infrastructure baseline that already exist.

The verified current infrastructure (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:124`) is one OVHcloud dedicated server (`ks-aw-01`, `145.239.195.47`) running WordPress, next-admin, node-api, oracle-web, MainWP, n8n, Postiz, self-hosted Supabase, self-hosted Trigger.dev, and Uptime Kuma via docker-compose + host-nginx + `lobster-nginx`, operated by one person plus AI agents. There is no Kubernetes, no multi-region, no managed cloud DB, no service mesh, and no message broker anywhere in the stack today (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:124`). A production-proven deploy pipeline (`sg-deploy.sh` — pre-build snapshot, Docker healthcheck wait, HTTP smoke-check gate, automatic rollback) and backup/observability tooling already exist and are load-bearing for the other services on this box (`17_REPOSITORY_LAYOUT_AND_PATHS.md:173`, `HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md` §5).

Two independent reviewers converged on the same option analysis:
- Reviewer B compared PostgreSQL modular monolith vs. PostgreSQL + dedicated event store vs. PostgreSQL + graph DB and recommended the modular-monolith option (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:21`).
- Reviewer D compared single-container-in-existing-compose vs. 3-container Web/API/Worker split Day-1 vs. separate Kubernetes namespace/cluster, and recommended the single-container option, deferring the Worker split to a named trigger and rejecting Kubernetes "for NOW" (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:49`).
- Reviewer D also compared sync REST vs. sync+async-callback vs. full event-driven/message-bus integration between HCI-30 and AI LEGO, recommending sync+async-callback and rejecting a broker for V1 (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:58`).

## Decision

Adopt **the modular-monolith option**: HCI-30 ships as **one deployable service** — a schema-per-bounded-context PostgreSQL modular monolith inside the already-running self-hosted Supabase Postgres instance, added as one more service block to the existing repo-root docker-compose stack and deployed through the existing `sg-deploy.sh` pipeline (host-nginx + `lobster-nginx` routing, same as `next-admin` today). No new microservice topology, no message broker, and no Kubernetes cluster/namespace until a named, measured trigger from `HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md` §4 fires.

Why the alternatives lose, in engineering terms:

- **3-container Web/API/Worker split Day-1** loses on operational cost without a corresponding correctness or isolation win: it triples the healthcheck/rollback/nginx-routing surface for a solo operator with no measured load justifying the split (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:49`, column "Operational cost (solo operator)"). Internal module boundaries inside one process already give the same later-extraction option at zero present cost — the same reasoning V1 already applied to defer graph-DB adoption (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:21`, migration-cost row).
- **Kubernetes namespace/cluster** loses on fit and proportionality: it would be the first K8s deployment anywhere in this stack, introducing a new control plane, new failure modes, and a skill requirement this org does not have, to run a single new bounded context on a single physical box that already has a working orchestration answer (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:49`, "Fits current baseline" / "Operational cost" rows).
- **Message broker (Kafka/NATS/RabbitMQ) for HCI↔AI LEGO integration** loses because the broker itself becomes a new single point of shared fate with no HA on a one-box deployment, while the sync-request + async-callback shape is already implicit in the AI LEGO contract and costs no new infrastructure (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:58`).
- **Dedicated event store / full event-sourcing-CQRS** for the domain core loses on maintainability for this team (solo operator + AI agents) and on blast radius — a bad replay can corrupt every downstream read model at once, worse than a modular monolith's contained blast radius (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:21`, rows "Maintainability" and "Blast radius"). Insert-only ledgers already capture most of event-sourcing's value without its operational cost.

This decision does not choose or alter DB tenancy tier defaults (Tier A shared-DB-with-RLS remains governed by `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:50` and ADR-0016), does not change the Tenant/Organization model (ADR-0009), and does not authorize processing real person or organization data (ADR-0010, ADR-0011).

## Required implementation gates

Wave 1 may not close, and no HCI-30 service may be deployed, until the following are implemented and reviewed. Each gate names the concrete artifact a CI check or test can verify — a gate with no such artifact is not accepted as satisfying this ADR.

1. **Single orchestration surface (Wave 1).** HCI-30's *deployed application* service definition lives as an additional service block inside the existing repo-root docker-compose file already driven by `sg-deploy.sh` (`lobster-factory/infra/hetzner-phase1-core/`) — not a second `docker-compose*.yml` under `Projects\internal\hci30\`. This gate exempts by name `Projects\internal\hci30\infra\local\compose.test.yml` (already exists — an isolated, ephemeral, `ports:`-mapping-free test-only Postgres fixture required by `ADR-0001` gate 3 and `ADR-0002` gate 3, never a deployed application stack) — the rule this gate enforces is "no second *deployment* orchestration surface," not "no compose file of any kind." Machine-testable: `tests/architecture/no-parallel-deploy-stack.test.*` (implemented 2026-09-18, `Projects/internal/hci30/tests/architecture/no-parallel-deploy-stack.test.mjs`) fails the build if a `docker-compose*.yml` file exists anywhere under `Projects/internal/hci30/` **other than `infra/local/compose.test.yml`, `infra/local/compose.dev.yml`, or `infra/local/compose.fetch-runner.yml`** (exemption list corrected 2026-09-18 from this gate's original single-file text — the other two pre-existing files already satisfy this gate's own stated reasoning, each self-declaring "local/test only, never deployed to ks-aw-01" in their own file headers, same as `compose.test.yml`), or if any exempt file's `ports:` mapping publishes a `0.0.0.0` host binding (which would turn it into a de facto second deployed stack). HCI-30's actual deployed `hci-app`/`hci-postgres`/`hci-fetch-runner`/`hci-network-guard`/`hci-object-storage` service blocks live in `lobster-factory/infra/hetzner-phase1-core/docker-compose.yml` (added 2026-09-18, `ADR-0021` gate 1 + `ADR-0029` gate 1).
2. **Single database, no second DSN (Wave 1) — superseded on this one point by `ADR-0021` (ACCEPTED, 2026-09-02).** This gate originally required HCI-30's schema to live inside the shared self-hosted Supabase instance. `ADR-0021` decided the opposite — a dedicated `hci-postgres` instance, for RLS blast-radius isolation from n8n's workflow secrets sharing that same cluster — and this gate is read, from `ADR-0021`'s Date forward, as satisfied by "exactly one additional, explicitly-named-`hci-postgres` database surface," not by "no second database at all." Machine-testable: `tests/architecture/no-second-db-dsn.test.*` (implemented 2026-09-18, `Projects/internal/hci30/tests/architecture/no-second-db-dsn.test.mjs`) asserts no DSN/connection-string surface under `Projects/internal/hci30/` exists **other than** the one carrying an `hci-postgres`/`HCI_DB_*`/`hci_owner` marker (`ADR-0021`'s own decided shape) — a second, unexplained DSN beyond that one would still fail this gate. No edit to `ADR-0021` is made or authorized by this note; this is a citation obligation only, per the same pattern `ADR-0029` gate 7 already uses for its own `ADR-0007` gate 4 reference update.
3. **No broker dependency (Wave 2–3).** HCI-30's and its `packages/contracts` dependency manifests must not declare a message-broker client (kafka, nats, amqplib/rabbitmq, or a Redis-backed distributed queue) per the event/integration-bus NOW row (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md:80`). Machine-testable: `tests/architecture/no-broker-deps.test.*` fails the build if any denylisted package name appears in a resolved lockfile under `Projects/internal/hci30/`.
4. **Worker reuses Trigger.dev, gated on HD-19 (Wave 6).** The Public Intelligence fetch/scan Worker must call the already-running self-hosted Trigger.dev instance, not a hand-rolled queue (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:21`), and this Worker code may not be written until the `HD-19` network-isolation verification test (already recorded as a blocking precondition, `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md` Wave 6) has a passing, dated test artifact. Machine-testable: presence of a dated `HD-19` isolation-test result artifact is a required file check before the Wave 6 Worker container/job is merged.
5. **Deploy path reuse (Wave 1, first deploy).** HCI-30's first deployment adds exactly one new smoke-check line to the existing `sg-deploy.sh`/CI deploy workflow, per the six-item new-deploy-path checklist already in force for this workspace (`CLAUDE.md` §AwareWave Stack / `AGENTS.md` §新部署路徑強制清單) — unit-test gate, Docker healthcheck, HTTP smoke check, rollback runbook entry, notification coverage, typecheck gate. Machine-testable: the existing `sg-deploy.sh` smoke-check function and `.github/workflows/*-typecheck.yml` pattern must show an HCI-30 entry before Gate A (Prototype, Waves 0–3, `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`) is declared closed.
6. **Extraction trigger is named, not vibes (any Wave, ongoing).** A proposal to split HCI-30 into multiple services, add a broker, or move to Kubernetes is valid only if it cites one of the named FUTURE triggers in `HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md` §4 — e.g. sustained >70% box memory/CPU attributable to HCI-30 scan jobs against the existing 60%/60% capacity thresholds (`reports/status/capacity-LATEST.md`), a second physical box, a second paying enterprise tenant requiring isolated blast radius, or a signed contract with a residency clause the current single EU box cannot satisfy. A proposal without a cited, measured trigger does not satisfy this gate and requires a superseding ADR before any extraction work begins.

## Consequences

- HCI-30 has zero new infrastructure classes to operate at Wave 1–5: no second orchestrator, no second stateful service, no broker. This keeps the operational surface matched to the actual team (solo operator + AI agents), consistent with `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:124`.
- Internal bounded contexts (per `17_REPOSITORY_LAYOUT_AND_PATHS.md` HCI-30 domain-directory layout) are still required inside the single deployable, so a later, trigger-justified extraction remains cheap — this ADR defers physical service separation, it does not forbid the module boundaries that make separation possible later.
- The Worker for Wave 6's Public Intelligence pipeline is *contingent*, not unconditional: it may not be built until `HD-19` has a verified isolation-test result, independent of this ADR's own gates.
- This ADR does not decide DB tenancy tiering (Tier A/B/C/D, `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:44`), the Tenant/Organization boundary (ADR-0009), consent scope (ADR-0010), subject-type scope (ADR-0011), data-subject rights (ADR-0014), identity confirmation (ADR-0015), or RLS enforcement (ADR-0016); those remain governed entirely by their own ADRs.
- This ADR does not authorize production deployment, processing of real person/organization data, or a live customer-facing HCI-30 instance — those require their own Wave-gate records and, where noted above, human ratification of the operator-delegated authority this ADR was written under.

## Verification and rollback

- Verification recorded here is documentation-only: this ADR formalizes an already-converged, twice-independently-reviewed recommendation (`HCI30_RESEARCH_REVIEW/13_ARCHITECTURE_OPTIONS_MATRIX.md` §1, §3a, §3b) and the already-verified infrastructure baseline (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:124`). No code exists yet to run the machine tests named in gates 1–5; those tests are specified, not yet implemented or executed.
- Before Wave 1 lands any HCI-30 application/API code, this ADR's six implementation gates are OPEN and block Wave 1 / Gate A closure per `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`'s Wave-gate record requirement (research evidence or a `PROPOSED` recommendation alone never unlocks a Wave).
- Rollback before implementation: supersede this ADR with a new explicit decision (operator or, under the same delegation, a documented Claude decision that the operator has not revoked).
- Rollback after implementation: any deviation toward multiple services/broker/Kubernetes must cite one of the named FUTURE triggers in gate 6 and land as a superseding ADR before extraction work begins — it must not be done as an undocumented refactor.
