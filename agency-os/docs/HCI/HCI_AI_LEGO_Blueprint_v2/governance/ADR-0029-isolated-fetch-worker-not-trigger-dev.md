# ADR-0029 — Isolated Fetch Worker, Not Trigger.dev, Executes the Wave 6 Fetch Step

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: Wave 6 Public Intelligence fetch/scan pipeline — which component performs the outbound HTTP fetch of Subject-related public content — only; this ADR does not authorize production deployment, real Subject data, or any change to the tenancy/consent/subject-type/RLS ADRs (0009–0011, 0014–0016).

## Context

`06_HCI30_PUBLIC_INTELLIGENCE.md:101` records a V2 blocking precondition on Wave 6: "the Trigger.dev-reuse-vs-isolated-runner network-isolation question must be resolved with an actual verification test before this Wave builds the fetch/scan pipeline on top of an unverified isolation assumption — this is not resolvable by further architecture review, it requires someone to run the test" (`HD-19`). `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:21` currently states the `Worker` component "reuses the already-running self-hosted Trigger.dev instance rather than standing up a new job-queue system — pending the network-isolation verification in `06`'s `HD-19`," and ADR-0007's gate 4 (`governance/ADR-0007-modular-monolith-first.md`) explicitly conditions that reuse on "a passing, dated test artifact" for HD-19 — it does not itself resolve HD-19.

`22_OPEN_HUMAN_DECISIONS.md:120-122` (HD-19) records this as a genuine, unresolved **DISAGREEMENT** between two independently-verified reviewer positions, not a converged recommendation:

- Reviewer D (`HCI30_RESEARCH_REVIEW/08_DEVOPS_SRE_REVIEW.md:187-203`, D-05) recommends implementing Wave 6 as Trigger.dev tasks on the already-running self-hosted instance to avoid duplicating queue/retry/dashboard machinery, but states the caveat explicitly at `08:199-203`: "unless a specific limitation of Trigger.dev... forces a dedicated sandboxed runner for just that step," and lists at `08:403` that Trigger.dev's actual sandboxing model was never verified against Wave 6's SSRF/malware threat list by either reviewer.
- Reviewer C (`HCI30_RESEARCH_REVIEW/07_SECURITY_PRIVACY_REVIEW.md:160-172`, SEC-05) independently specifies that the fetch step needs its own network-isolated, egress-only container — "no route to the docker-internal bridge network, DNS pinning to prevent rebind attacks, and an explicit blocklist of RFC1918/loopback/link-local ranges and cloud metadata IPs" (`07:172`) — because the verified single-box baseline (`12:124`, corroborated firsthand) means an SSRF-capable fetch job can reach Supabase's admin API, Trigger.dev's own internal endpoints, and n8n's webhook-management surface on the same docker network, "not just the public internet" (`07:166`). SEC-05's stated blast radius is "every service on ks-aw-01, not just HCI" (`07:174`).

`HCI30_RESEARCH_REVIEW/14_CONVERGENCE_MATRIX.md:139-144` (CM-18) independently re-derives and confirms this is a true disagreement, not two findings about different things: "reuse existing infra" and "network-isolate the highest-risk single step" point to different implementations unless someone verifies Trigger.dev can run tasks inside a network-restricted container that satisfies SEC-05 — and no reviewer performed that verification.

## Decision

**Build a dedicated, network-isolated fetch runner container for Wave 6's fetch step; do not reuse Trigger.dev to execute the fetch.** Trigger.dev may still orchestrate Wave 6 — enqueue fetch jobs, track status, retry, and surface the pipeline in its dashboard — but the actual outbound HTTP request to a Subject-related or search-result URL executes only inside the dedicated isolated runner, never as Trigger.dev worker code with the docker network access that role currently has.

Why the alternatives lose, in engineering terms:

- **Reuse Trigger.dev to execute the fetch (Reviewer D's D-05 recommendation as stated)** loses because network isolation is a hard security property, not a soft one: it must be provably true (no route to the docker bridge, egress-only, DNS-rebind-resistant, metadata-blocked) and stay true across every future Trigger.dev upgrade, config change, or added integration. Proving and *maintaining* that property against Trigger.dev's general-purpose worker sandboxing model — a sandbox built for arbitrary application tasks, not specifically hardened as an egress-only network boundary — is ongoing unverified risk with no test artifact anyone has produced (`08:403`), while a minimal dedicated container with an explicit egress policy is a bounded control whose isolation properties can be asserted once and tested on every build.
- **Do nothing until Trigger.dev's isolation is verified, ship Wave 6 on the current assumption** loses because `06:101` already states this cannot be resolved by more architecture review, and Wave 6's own acceptance line (`06:103`) already requires "a network-isolation test against the resolved `HD-19` decision" before Wave 6 can close — shipping without resolving HD-19 first violates that Wave's own acceptance criterion, not just a preference.
- **Reject Trigger.dev entirely for Wave 6, hand-roll a new queue/retry/dashboard system** loses because it duplicates already-proven, load-bearing infrastructure (`08:193`, `12:21`) for no isolation benefit — the disagreement was never about orchestration, only about which component executes the one step (the fetch itself) that touches attacker-influenced input against the shared docker network. Keeping Trigger.dev as orchestrator preserves ADR-0007's anti-duplication principle (`governance/ADR-0007-modular-monolith-first.md` gate 3, "no broker dependency") while still closing the isolation gap.

This decision resolves `HD-19` and supersedes the premise of ADR-0007's gate 4 to the extent that gate assumed the Worker's Trigger.dev reuse would extend to fetch execution once HD-19 cleared — it does not. ADR-0007 gate 4's "passing, dated test artifact" requirement is satisfied by this ADR's implementation gates below, once implemented; it is not satisfied by this decision text alone.

## Required implementation gates

Wave 6 may not build the fetch/scan pipeline, and Gate C (`22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md` §Gate C, "hardened public intelligence") may not close, until all of the following are implemented and reviewed. Each gate names the concrete artifact a test or CI check can verify — a gate with no such artifact does not satisfy this ADR.

1. **Fetch execution lives in a separate compose service, not the Trigger.dev worker process (Wave 6).** The isolated fetch runner is its own container/service definition (e.g. `hci-fetch-runner`) inside the existing docker-compose stack, distinct from the `trigger` service. Machine-testable: `tests/architecture/fetch-runner-is-separate-service.test.*` fails if no such distinct service exists, or if the Trigger.dev service definition is granted the runner's egress-only network.
2. **No route to the docker-internal bridge network (Wave 6).** The fetch runner's container network configuration excludes the default/shared docker bridge network carrying Supabase, Trigger.dev-internal, n8n, and the other AwareWave services named in `07:166`. Test id: `wave6-no-bridge-route` — attempts a connection from inside the runner to the internal Supabase admin endpoint, the Trigger.dev internal endpoint, and the n8n webhook-management endpoint; all three must be unreachable (connection refused/timeout), per `06:103`'s "network-isolation test."
3. **Cloud-metadata and private-range egress blocked (Wave 6).** An egress policy (iptables/network-policy) on the fetch runner blocks RFC1918, loopback, link-local, and cloud-metadata ranges (e.g. `169.254.169.254`), per `07:172`'s explicit blocklist requirement. Test id: `wave6-metadata-and-rfc1918-blocked` — fetch attempts to each blocked range/address must fail closed.
4. **DNS-rebind protection (Wave 6).** The runner resolves and pins the destination IP before connecting and re-validates that the connection target matches the pinned IP, rejecting any DNS response that rebinds an already-resolved public hostname to a blocked range. Test id: `wave6-dns-rebind-rejected` — a controlled test domain that flips its DNS answer between a public IP and an RFC1918/loopback address between resolution and connection must be rejected.
5. **SSRF payload corpus (Wave 6).** A named corpus of known SSRF techniques (open redirects, decimal/octal/hex IP encoding, IPv4-mapped IPv6 addresses, protocol-smuggling URLs) is run against the fetch runner as part of the Wave 6 acceptance suite already required at `06:103` ("SSRF... tests"). Test id: `wave6-ssrf-payload-corpus`. This is the concrete artifact that satisfies `06:103`'s acceptance line and the "Wave 6 acceptance test spec" this ADR is written against.
6. **Trigger.dev is orchestration-only for this step (Wave 6).** A static-analysis/architecture check confirms no Trigger.dev task definition under `Projects/internal/hci30/public-intelligence/` performs an outbound HTTP request to a Subject-supplied or search-result URL; Trigger.dev task code may only call the isolated runner's own internal API to enqueue a fetch and read back its result/status. Test id: `wave6-trigger-no-direct-fetch` — fails the build if an HTTP-client call to a non-allowlisted external target appears in Trigger.dev task source under that path. Extended 2026-09-18 (Task 10) to also scan `Projects/internal/hci30/app/` in zero-tolerance mode (no allowlisted file at all, unlike `public-intelligence/`'s one): `app/server.mjs` became this call graph's second real caller, and may reach an HCI target only through the orchestration layer's `orchestrateDiscoveredFetch`, never a fetch of its own.
7. **ADR-0007 gate 4 reference update (Wave 1 documentation, immediate).** `governance/ADR-0007-modular-monolith-first.md` gate 4's text ("Worker reuses Trigger.dev, gated on HD-19") is read, from this ADR's Date forward, as satisfied by "Trigger.dev orchestrates, the isolated fetch runner executes the fetch" — not by unconditional Trigger.dev execution. No edit to ADR-0007's file is made or authorized by this ADR; this gate is a citation obligation for any future reader or CI check that resolves ADR-0007 gate 4 against this ADR's text, not a rewrite of ADR-0007.

None of these gates authorize a live fetch of real-world content, processing of real Subject data, or a production deployment — gates 2–5 are executed against controlled/synthetic targets only until Gate C's own broader production-authorization requirements (backups, security baseline, incident response, restore test per `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md` §Gate C) are separately satisfied.

## Consequences

- Wave 6's fetch step gets a bounded, directly testable network-isolation control (gates 1–5) instead of an inherited, unverified assumption about a general-purpose job runner's sandboxing.
- Trigger.dev's existing queue/retry/dashboard value is preserved for Wave 6 orchestration (enqueue, status, retry, observability) — this ADR narrows *who executes the fetch*, it does not remove Trigger.dev from the pipeline or reopen ADR-0007's "no second queue/retry/dashboard system" gate.
- `HD-19` closes as **RESOLVED** by this ADR; `06_HCI30_PUBLIC_INTELLIGENCE.md:101`'s blocking precondition is satisfied in decision terms, but Wave 6 still cannot build until gates 1–6 above are implemented and their tests pass — a decision record is not a passing test.
- This is explicitly reversible: if a later, dated test artifact (gate 5's SSRF corpus and gates 2–4's isolation tests, run instead against a proposed Trigger.dev-native isolation mechanism) proves Trigger.dev's own sandboxing satisfies SEC-05's requirements, a superseding ADR may reverse this decision and fold fetch execution back into Trigger.dev. Until that artifact exists, the dedicated runner is authoritative.
- This ADR does not alter DB tenancy, the Tenant/Organization boundary, consent scope, subject-type scope, data-subject rights, identity confirmation, or RLS enforcement (ADR-0009, ADR-0010, ADR-0011, ADR-0014, ADR-0015, ADR-0016) and does not authorize processing real person or organization data.

## Verification and rollback

- Verification recorded here is documentation-only: this ADR formalizes a resolution to a reviewer-flagged DISAGREEMENT (`22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`, `22_OPEN_HUMAN_DECISIONS.md:119-122`, `14_CONVERGENCE_MATRIX.md:139-144`) using the two reviewers' own evidence; no fetch-runner code exists yet, and gates 1–6's tests are specified, not implemented or executed.
- Before Wave 6 builds the fetch/scan pipeline, gates 1–6 are OPEN and block that build per `06:101`'s blocking precondition and `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`'s Wave-gate record requirement (research evidence or a decision record alone never unlocks a Wave).
- Rollback before implementation: supersede this ADR with a new explicit decision (operator, or under the same delegation, a documented Claude decision the operator has not revoked).
- Rollback after implementation: only a superseding ADR, backed by the passing test artifact described in Consequences above (Trigger.dev proven to satisfy gates 2–5's isolation tests), may fold fetch execution back into Trigger.dev. It must not be done as an undocumented refactor or a config change to the runner's network policy alone.
