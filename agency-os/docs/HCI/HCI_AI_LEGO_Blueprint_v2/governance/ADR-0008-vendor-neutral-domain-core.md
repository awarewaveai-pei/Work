# ADR-0008 — Vendor-Neutral Domain Core

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI-30 domain-core/vendor-adapter boundary and its replacement-test obligation only; this ADR builds no adapter code, selects no payment provider, does not re-decide `HD-09` (AI LEGO Shared Kernel extraction, resolved separately by `ADR-0013`, `ACCEPTED` same batch), and authorizes no production deploy or real-person data processing.

## Context

`01_SYSTEM_CONSTITUTION.md:61-68` (Invariant 4) forbids the domain core depending directly on a single LLM provider, cloud, payment vendor, vector database, or frontend framework — and the same invariant already admits at `01:70` that this is "a stated principle, not yet a tested property." `01:113-117` (Invariant 8) generalizes the failure mode this ADR closes: "a stated principle is not a control until it is enforced," added specifically because an independent Red Team review found zero of 16 attack scenarios blocked by anything actually enforced, not because the principles were wrong.

`18_LEGO_CONTRACT_AND_COMPONENT_TAXONOMY.md:76-80` (§Vendor Replaceability) names the concrete gap and the concrete fix: "capability-registry abstraction existing in the architecture diagram" does not prove neutrality; the recommended minimum is "a CI job that runs the same eval suite against two different LLM providers behind the `llm.reason` capability and asserts equivalent-shape output." The same section's Supabase-specific note requires all Supabase-specific client calls to be routed through "an explicitly isolated adapter module, never imported directly by domain logic," while confirming PostgreSQL itself is the low-risk part of that dependency. `18:82-94` (§Provider adapter rule) states the general shape — `HCI → capability → Router → Provider Adapter` — and the good/bad example at `18:73-74` (`requestCapability("llm.reason", ...)` vs `callOpenAI(...)`).

`HCI30_RESEARCH_REVIEW/18_30_YEAR_REPLACEMENT_ANALYSIS.md:9-17` scores replaceability confidence as Medium for LLM providers ("Yes, if V1's Invariant 4 is actually enforced in code") and Medium for Supabase specifically (High for Postgres alone); `:38-39` records that no payment provider has been named anywhere in the 24-file blueprint, which the file itself calls "not evidence of good vendor-neutrality — it is evidence the question has not been reached yet"; `:36` records the same open risk for a frontend framework, recommending decision-relevant computation (evidence-quality, risk-tier, confidence) stay server-side so a framework swap never becomes a domain-logic rewrite.

This is currently the cheapest point at which to enforce the boundary: a grep across `Projects/internal/hci30/**/*.{mjs,ts,js}` for `supabase|openai|anthropic|createClient|stripe` returns zero matches (verified 2026-09-02) — the only runtime code that exists today is `packages/contracts/validate-request.mjs`, a plain-object validator with no vendor import. `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:43-45` places DB schema delivery in Wave 1 (in progress now, per `Projects/internal/hci30/README.md:1-3`, "Wave 1 local skeleton"), `:57` already establishes an `adapters/auth/` path convention for Wave 2, `:85-87` places the first real intelligence/LLM compute in Wave 5, and `:109` places the first UI code (`apps/web/`) in Wave 7 — so the adapter boundary can be built alongside each capability's first real code, not retrofitted after vendor calls are already scattered through domain files. `ADR_INDEX.md:26` recorded this ADR as `PLANNED` at drafting time (since updated to `ACCEPTED` in the same batch), sourced from `01_SYSTEM_CONSTITUTION.md` and `09_AI_LEGO_COGNITIVE_OS_BOUNDARY.md`, with no prior recorded approval.

## Decision

**Adopt the stated option**: the domain core depends only on standard PostgreSQL and the language runtime. Every vendor — LLM provider, Supabase-specific client, payment processor, object storage, or any other external service — sits behind an adapter interface reached only through a named capability (`requestCapability("llm.reason", …)`, never `callOpenAI(...)`), and vendor-neutrality for each capability category is proven by a documented, executable replacement test before that category is relied on for a real decision, not asserted by architecture-diagram abstraction alone.

Why the alternatives lose:

- **Keep Invariant 4 as a stated principle, enforce nothing** (status quo): this is the exact condition Invariant 8 (`01:113-117`) was written to end, and the exact condition `18:78` already flags as unverified. A principle with no CI-blocking mechanism degrades under normal engineering pressure — the next agent under deadline pressure imports the vendor SDK directly because nothing stops it, and by Wave 5 the cost of separating LLM calls from domain logic is a rewrite, not a boundary.
- **Rely on code-review convention instead of a machine gate**: fails for the same reason R4 (`AGENTS.md` — claims require verification, not narrative) exists — this repo's own governance already treats "we reviewed it" as insufficient without a Grep-confirmed, re-runnable check. A convention has no mutation test; nothing proves it would catch a violation before it ships.
- **Defer the boundary decision until Wave 5, when LLM calls first become real**: loses on cost-of-delay. The grep above shows the domain core is empty today — zero vendor imports to migrate. Waiting until Wave 5 means Waves 1-4 (domain schema, policy/security, contracts, Evidence/Claim/Assessment core) get built first, and any of those layers that reached for a vendor client directly (most plausibly the DB layer, since Wave 1 delivers the schema against a live Supabase-backed Postgres) would need to be unwound later — precisely the "rewrite the Domain Core" failure `01_SYSTEM_CONSTITUTION.md`'s Definition of architecture failure (`01:125-132`) already names as disqualifying.

## Required implementation gates

Runtime gates are **OPEN**. Each gate names the artifact, the CI-blocking test, and the Wave (per `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md`) it must land in before that Wave's acceptance criteria can be called met.

1. **Vendor-import boundary lint — Wave 1, same commit as the first DB-touching code.** `Projects/internal/hci30/scripts/check-domain-vendor-imports.ps1`, run in CI on every push touching `domain/**`, `packages/contracts/**`, or `runtime/**`. Forbidden-import list (case-insensitive, matched against `import`/`require` specifiers): `@supabase/*`, `openai`, `@anthropic-ai/*`, `stripe`, `@trigger.dev/*`. Only `adapters/**` may import them. Test `VENDOR-BOUNDARY-01`: a domain file importing a forbidden specifier → runner exits non-zero. Mutation check (same pattern as `Projects/internal/hci30/README.md:11`): temporarily add a forbidden import to a domain file — `VENDOR-BOUNDARY-01` must go red, or the gate is not constraining anything.
2. **Postgres/Supabase repository isolation — Wave 1, paired with the Wave 1 DB schema delivery (`22:45`).** `Projects/internal/hci30/adapters/db/repository.contract.mjs` defines the read/write interface the domain layer calls; `Projects/internal/hci30/adapters/db/supabase.adapter.mjs` is the *only* file in the repository permitted to import `@supabase/supabase-js` (enforced by gate 1's allow-list). Test `DB-BOUNDARY-01`: instantiate the repository contract against a plain-`pg`-backed fake and against the Supabase adapter and assert both satisfy the same contract shape — proves the domain layer is not calling Supabase-specific methods (RLS-via-Supabase-Auth-JWT, Storage API, Realtime) that a plain-Postgres backend could not also satisfy.
3. **LLM capability adapter — Wave 5, before `intelligence/` (`22:87`) makes its first real model call.** `Projects/internal/hci30/adapters/llm/capability.contract.mjs` implements `requestCapability("llm.reason", requirements)` per `18:73`; at least two concrete provider adapters (e.g. `adapters/llm/providers/anthropic.adapter.mjs`, `adapters/llm/providers/openai.adapter.mjs`) satisfy the same output contract. Test `LLM-ADAPTER-SHAPE-01`: both adapters, given the same fixture input, return output that validates against one fixed output schema (fields/types match; content need not match).
4. **Cross-provider vendor-swap CI eval job — Wave 5, same commit as gate 3.** `.github/workflows/hci-llm-vendor-swap.yml` runs a fixed eval-prompt suite (`Projects/internal/hci30/intelligence/eval/vendor-swap-suite/`) against both configured LLM providers behind `llm.reason` and asserts equivalent-shape output per `18:78`'s recommended minimum. This is the actual tested property Invariant 4 demands — until this job is green, LLM vendor-neutrality is an unverified claim, not a guarantee, and no HCI documentation may assert otherwise (a claim to that effect is a `CLAIM-*` row candidate under `ADR-0023`'s register, not an assumption this ADR grants for free).
5. **Frontend compute-boundary lint — Wave 7, before `apps/web/` (`22:109`) ships its first evidence/risk-tier view.** `Projects/internal/hci30/scripts/check-frontend-compute-boundary.ps1`: forbids evidence-quality, confidence, or risk-tier calculation logic inside `apps/web/**` (the frontend renders values computed server-side; it does not compute them, per `18_30_YEAR_REPLACEMENT_ANALYSIS.md:36`). Test `FRONTEND-COMPUTE-01`: a component file containing a risk-tier or confidence formula (matched against a maintained list of scoring function names shared with `intelligence/`) → runner exits non-zero.

## Consequences

- No HCI-30 domain file may import a vendor SDK directly once gate 1 lands; every such call routes through `adapters/**` behind a named capability.
- This ADR does not choose Supabase's replacement, select a payment vendor, or decide `HD-09` (Shared Kernel extraction, `ADR-0013`) — it only requires that whichever vendor is chosen for each category sits behind the adapter boundary and, for LLM providers specifically, behind an executed swap test before that category is trusted for a real decision.
- `18_30_YEAR_REPLACEMENT_ANALYSIS.md`'s payment-provider gap (`:38-39`) is closed structurally, not by naming a provider: gate 1's forbidden-import list already includes `stripe` before any payment vendor is chosen, so the first payment integration is adapter-shaped by construction rather than retrofitted.
- Passing gates 1-5 is evidence the *boundary* exists and is enforced; it is not evidence that switching vendors is operationally rehearsed (the same gap `18_30_YEAR_REPLACEMENT_ANALYSIS.md:41-42` records for OVH) — a rehearsed cutover remains separate follow-through work, not claimed here.
- Adding a vendor category to the forbidden-import list is a routine gate edit; narrowing the list or exempting a domain path requires a superseding ADR.

## Verification and rollback

- Verification recorded here is documentation-only: the decision and gate identifiers are cross-linked to `01_SYSTEM_CONSTITUTION.md` Invariants 4 and 8, `18_LEGO_CONTRACT_AND_COMPONENT_TAXONOMY.md` §Vendor Replaceability and §Provider adapter rule, `HCI30_RESEARCH_REVIEW/18_30_YEAR_REPLACEMENT_ANALYSIS.md`, and `governance/ADR_INDEX.md`. `Projects/internal/hci30/adapters/`, `scripts/check-domain-vendor-imports.ps1`, `scripts/check-frontend-compute-boundary.ps1`, and `.github/workflows/hci-llm-vendor-swap.yml` do not yet exist (checked 2026-09-02); gates 1-5 are open.
- Before implementation, rollback is to supersede this ADR with a new explicit human decision.
- After implementation, rollback must not remove an adapter boundary in place of a domain-layer vendor import; a gate may only be loosened by a superseding ADR, mirroring the rollback discipline in `ADR-0016` and `ADR-0023`.
