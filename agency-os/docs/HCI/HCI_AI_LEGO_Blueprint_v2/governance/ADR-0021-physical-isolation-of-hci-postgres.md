# ADR-0021 — Physical Isolation of HCI's PostgreSQL Instance

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: Physical placement of HCI-30's own Postgres data (RESTRICTED-classified Evidence/Claim/Assessment/Decision and any crypto-shredding key material) on `ks-aw-01`, relative to the shared Supabase/n8n automation cluster. Does not decide tenant-level isolation tiers (Tier A–D, unaffected), crypto-shredding adoption (`HD-07`, still open), or HCI's application-topology/broker/Kubernetes decisions (`ADR-0007`, unaffected outside the one conflict named below).

## Context

`07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md:148` carries HD-11 as 🔴 DECISION PENDING: does HCI's RESTRICTED-classified data (`11_SECURITY_PRIVACY_GOVERNANCE.md:49,52` defaults HCI person-analysis data to `RESTRICTED`) live in the same physical Postgres cluster as unrelated, lower-sensitivity automation data, or is it physically isolated as a compensating control. `HCI30_RESEARCH_REVIEW/06_DATABASE_ARCHITECTURE_REVIEW.md:317-336` (CI-9, `Requires human decision: YES`) supplies the evidence: the verified infrastructure baseline (`23_CURRENT_INFRASTRUCTURE_SOURCE_OF_TRUTH.md:20`) is one OVH dedicated server; `agency-os/docs/operations/AWAREWAVE_STACK_QUICKREF.md:86` confirms n8n already runs on network `supabase_default` against `supabase-db:5432` database `n8n` — the same Postgres process (`lobster-factory/infra/supabase/docker-compose.yml:577-578`, image `supabase/postgres:15.8.1.085`) that would host HCI's schema absent this decision. `11_SECURITY_PRIVACY_GOVERNANCE.md:39` independently confirms direct Postgres/superuser access on this box bypasses RLS and the application layer entirely — a live, present-tense gap, not a hypothetical. CI-9's own recommendation text (`06:329`) explicitly asks for this to be "document[ed] as an explicit ADR alongside the DB architecture ADR (CI-10)" — CI-10 is `ADR-0007`.

The evidence schema already carries the hook this ADR protects: `encryption_key_ref`/`tombstoned_at` (`07:126-127`), the per-record key material for the crypto-shredding design `ADR-0018` (same batch) already adopted as Option A (`07:140` now ✅ RESOLVED, not pending) for reconciling Invariant 6 with erasure rights. Wherever that key table lives is exactly the table CI-9 is worried about. `agency-os/AGENTS.md:233` confirms the host has real headroom for a second container: `ks-aw-01` is "64GB 買來裝 128GB 規劃" (64GB bought for a 128GB-provisioned target), and its capacity thresholds (`scripts/check-capacity-health.ps1:93`: memory warn 60%/fail 85%, disk warn 60%/fail 80%) are deliberately strict, not tight.

**Conflict discovered while writing this ADR**: `governance/ADR-0007-modular-monolith-first.md` (ACCEPTED, same date, edited concurrently during this session) §Decision and §Required implementation gates item 2 commit HCI's schema to live "inside the already-running self-hosted Supabase Postgres instance... not a second database container," backed by an architecture test `no-second-db-dsn.test.*`. That is the literal opposite of HD-11's chosen option. This is resolved explicitly below, not silently.

## Decision

Adopt the recommended option (`06:329`): HCI-30 runs its **own PostgreSQL instance** — a dedicated `docker-compose` service, dedicated named Docker volume, dedicated backup stream, dedicated credentials, and dedicated resource limits — on `ks-aw-01`, physically separate from the self-hosted Supabase Postgres instance that already serves `n8n` and other automation tooling. No foreign key or `dblink`/`postgres_fdw` link crosses the two instances; portal and AI LEGO integration remain adapters over the existing API boundary, unaffected by where HCI's own data physically sits.

Why the alternatives lose, in engineering terms:

- **Schema-in-shared-Supabase-instance** (the status quo, and what `ADR-0007` gate 2 currently states) loses because it makes RLS the *sole* isolation control between RESTRICTED person data and a much larger blast-radius surface. `ADR-0016`'s tenancy-principal mechanism — the `SET ROLE`-escalation gap it flagged is resolved as a *decision* by `ADR-0033` (Option B-signed, same batch), but that ADR's own implementation gates are still `OPEN` — already means RLS is not yet a *closed, implemented* control even for HCI's internal tenants; stacking that on a host where a leaked `service_role` key, a missed policy, or the superuser-bypass gap at `11:39` also reaches `n8n`'s workflow secrets removes defense-in-depth entirely. `06:330` calls this exactly: "defense in depth is reduced to a single control."
- **A second physical host / managed cloud DB** loses on proportionality: the verified baseline is one non-elastic dedicated server with "no Kubernetes, no multi-region, no managed cloud DB" (`ADR-0007:12`, citing `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:124`); a second box is a disproportionate cost for a control a second container fully satisfies, and would itself need a new `ADR-0007`-style topology justification this decision does not attempt.
- **Do nothing / defer (HD-11's own "Section B, no urgency" framing)** loses on timing, not principle: `06:332` ("Migration impact") states plainly that separating an already-shared cluster later, once real data exists, is "disruptive and risky," while `06:331` ("Blast radius") confirms deciding now is "infra provisioning... no application-code impact." The cost of this control only grows the longer HCI's schema shares Supabase's instance.

**Resolving the ADR-0007 conflict**: this ADR **supersedes ADR-0007 §Decision's "inside the already-running self-hosted Supabase Postgres instance" clause and §Required implementation gates item 2** ("Single database, no second DSN") on this one point. Every other ADR-0007 commitment — one deployable app service, no broker, no Kubernetes, the named extraction triggers, gate 1's "one more service block to the existing repo-root docker-compose stack" — is unaffected: a second Postgres *data* service in that same compose file is not a second *application* deploy unit, so ADR-0007's Consequences bullet "no second stateful service" must be read, from this ADR forward, as "no second stateful *automation/app* service" — the app-topology principle it actually protects, not a database-instance count. `ADR-0007` gate 6 (named-trigger requirement) does not apply here: this is a data-isolation decision under CI-9, not an app-topology extraction under `13_ARCHITECTURE_OPTIONS_MATRIX.md` §4.

This decision does not authorize real-person data processing, production deployment, or a change to `ADR-0009`, `ADR-0010`, `ADR-0011`, `ADR-0014`, `ADR-0015`, or `ADR-0016` — RLS remains mandatory inside HCI's own instance regardless of physical host separation.

## Required implementation gates

Each gate names its artifact and failing test. Gates 1–2 land in the same compose/test paths `ADR-0007` already established.

1. **Dedicated compose service + volume — Wave 1 artifact, required before Wave 4 real-data admission (`22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:75`).** `lobster-factory/infra/hetzner-phase1-core/docker-compose.yml` gains a service block `container_name: hci-postgres` (engine pinned to match the Wave 1 skeleton, `PostgreSQL 15.8` per `Projects/internal/hci30/README.md:7`) with its own named volume prefixed `hci_`, never a bind-mount under `lobster-factory/infra/supabase/volumes/`. Test `tests/architecture/hci-db-isolation.test.*`: parses the compose file, fails if any `hci-postgres` volume path resolves under `lobster-factory/infra/supabase/`, or if any non-`hci`-prefixed service holds a connection string pointing at host `hci-postgres`. Fixture: point HCI's `DB_HOST` at `supabase-db` → red.
2. **No cross-instance links — Wave 1.** `database/tests/wave1-negative-tests.sql` adds `ARCH-DB-03`: `SELECT count(*) FROM pg_extension WHERE extname IN ('postgres_fdw','dblink')` on `hci-postgres` must be `0`. Companion `tests/architecture/no-cross-instance-fk.test.*` fails the build if any migration under `Projects/internal/hci30/database/` `REFERENCES` a table not created in that same migration tree. Mutation: install `dblink` or add a stray cross-schema FK in a fixture migration → both red.
3. **Separate credentials — Wave 2 (`22:55`, policy/security boundary).** `hci-postgres` uses its own superuser secret, distinct from the shared `${POSTGRES_PASSWORD}` already reused across every Supabase-instance service (`lobster-factory/infra/supabase/docker-compose.yml:44,167,291,337,403,479,510`), registered under its own key name in `mcp/user-env.template.ps1` (`CLAUDE.md` §MCP 治理). Test: a pre-deploy check fails if the HCI DB secret resolves to the same vault entry as the Supabase Postgres secret.
4. **Dedicated backup stream — Wave 2, blocking Wave 4 real-data admission (mirrors ADR-0014's cross-box-restore-drill precondition, `22:75`).** `/etc/cron.d/ks-stack-backup` (`AWAREWAVE_STACK_QUICKREF.md:14`), which already runs Supabase's weekly restart/backup, gains an independent `hci-postgres` backup line with its own target path. Test: two consecutive scheduled runs must produce an `hci-postgres` backup artifact whose mtime is independent of the Supabase backup artifact's mtime.
5. **Own resource limits — Wave 1.** `hci-postgres`'s compose block sets `mem_limit`/`cpus` (pattern: `supabase-db`'s `mem_limit: 768m`, `cpus: "1.0"`, same file `:584-585`) so it cannot starve `n8n`/Supabase on the shared 64GB host (`agency-os/AGENTS.md:233`); the existing ks-aw-01 60%/85% memory and 60%/80% disk thresholds (`scripts/check-capacity-health.ps1:93`) keep covering the host in aggregate. Test: pre-deploy check fails if the service block omits `mem_limit`.
6. **ADR-0007 reconciliation — Wave 1, blocks either ADR's gate closure until landed.** The same commit that adds `hci-postgres` must also edit `ADR-0007` §Required implementation gates item 2 and its `no-second-db-dsn.test.*` to exempt a service literally named `hci-postgres`, so the two tests stop permanently contradicting each other.

## Consequences

- HCI provisions one additional container, one additional named volume, and one additional backup line on `ks-aw-01` — the only new operational cost CI-9 identified (`06:330`: "still one box, still Postgres, still self-hosted").
- RLS remains mandatory and unweakened inside HCI's own instance (`ADR-0016`); this ADR is a compensating control layered on top of RLS, not a substitute for it, and does not touch `ADR-0016`'s tenancy-principal mechanism (resolved by `ADR-0033`; implementation gates still `OPEN`).
- The Tier A/B/C/D tenant-isolation model (`12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:44-50`, `ADR-0023`'s dedicated-DB claim gates) is unaffected: this ADR governs HCI-the-product versus n8n-the-automation-tool, not tenant-versus-tenant inside HCI. A future Tier B+ Enterprise dedicated-DB entitlement is a further split inside HCI's already-isolated instance, not a replacement for it.
- `ADR-0007` is amended by gate 6, in the narrow scope stated in the Decision section; its app-topology, no-broker, no-Kubernetes, and extraction-trigger commitments stand unchanged.
- This ADR does not itself decide `HD-07` (`ADR-0018`, same batch, does); it only fixes where the `encryption_key_ref`/`tombstoned_at` table physically lives.
- Does not authorize: real-person data processing, production deployment, or any BYOK/dedicated-DB customer-facing claim (still gated by `ADR-0023`).

## Verification and rollback

- Verification recorded here is documentation-only: every cited line was read on 2026-09-02; the `ADR-0007` conflict was discovered by reading it in full during this ADR's drafting, not inferred. No `hci-postgres` service, volume, credential, or backup line exists yet — all six gates are `OPEN`. Live state on `ks-aw-01` (e.g., whether any `hci-postgres`-named container already exists) was not independently SSH-verified for this ADR; treat that as unconfirmed until gate 1 lands.
- Rollback before implementation: supersede this ADR with a later explicit decision (operator, or a documented delegated Claude decision the operator has not revoked).
- Rollback after implementation: per `06:333`, a live split is "straightforward pre-implementation" but a later *consolidation* back into the shared instance requires a maintenance window and careful cutover, following the same expand/contract discipline `ADR-0017` uses for schema changes; it must not be an undocumented refactor and requires a superseding ADR.
