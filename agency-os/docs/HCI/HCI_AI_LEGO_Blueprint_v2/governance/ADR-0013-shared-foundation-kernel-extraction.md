# ADR-0013 — Shared Foundation-Kernel Extraction

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI AI LEGO Blueprint v2 architecture only; resolves `HD-09`. Authorizes a minimally-scoped, vendored/pinned shared kernel package — no runtime kernel code, database schema, migration, or production behavior is created by this ADR itself.

## Context

`22_OPEN_HUMAN_DECISIONS.md:65-69` (`HD-09`) frames the central "should HCI-30 and AI LEGO share anything" question and records that the independence-verdict synthesis wants the top-level domain split to stay independent while one specific Foundation-layer primitive should not — a scoped judgment call it says the operator must ratify explicitly. `09_AI_LEGO_COGNITIVE_OS_BOUNDARY.md:61-90` (§Shared Kernel) is marked `🔴 DECISION PENDING` and lists four candidate extractions: (1) thin reference types, (2) `epistemic_type` labeling, (3) the R0-R4 risk-tier ladder, and (4) the Tenant/entitlement/billing substrate. `18_LEGO_CONTRACT_AND_COMPONENT_TAXONOMY.md:9` already names "Foundation LEGO" (IAM, audit, secrets, event bus, tenant context) as the category this belongs in, and `18:124-128` records that the thin-reference mechanism "was already the intended home... V1 correctly named the category and never populated it" — `AI LEGO's evidence.schema.yaml` today embeds a full record where `EvidenceRef` was supposed to be a stub.

The two non-tenant primitives are not proposals: `specs/governance/epistemic-label.schema.yaml` and `specs/execution/risk-tier.schema.yaml` are both `status: ACTIVE`, `decided_by: ADR-004 (ACCEPTED 2026-08-29)` — an 11-value `epistemic_type` enum with a machine-checkable `UNKNOWN -> SOURCE_FACT` promotion redline, and an R0-R4 ladder with a `risk_tier IN [R3, R4]` mandatory-gate trigger. `09_AI_INTELLIGENCE_REVIEW.md:87-102` (C1) documents that HCI has begun independently re-deriving the same ground: `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md:78-98` defines HCI's own prose-only Fact/Observation/Interpretation/Hypothesis split, with no cross-reference to `epistemic_type` and no DB column yet — confirmed by grep: `Projects\internal\hci30\database\migrations\0001_wave1_synthetic_up.sql` has zero occurrences of `epistemic`, `risk_tier`, or `provenance` today. `09_AI_INTELLIGENCE_REVIEW.md:129-144` (C3) documents the same pattern for risk: `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md:161-176`'s ad hoc LOW/MEDIUM/HIGH/CRITICAL cross-model gate table does not reference the ACCEPTED R0-R4 ladder or `policies/ai-execution/mandatory-gates.yaml`'s `MGATE-R3-R4-HUMAN-REVIEW` rule.

Runtime state confirmed 2026-09-02: `D:\Work\Projects\shared\` does not exist; `D:\Work\Projects\internal\cognitive-engineering-os\` does not exist (per `17_REPOSITORY_LAYOUT_AND_PATHS.md:16`, its runtime root is created only when that product has runtime code); `hci30`'s only runtime package is `packages\contracts\validate-request.mjs`, which validates tenant-authorization/lawful-basis/source-terms records (ADR-0010's scope) and carries no epistemic or risk vocabulary. `17_REPOSITORY_LAYOUT_AND_PATHS.md:151-152` forbids pre-creating a `shared\` tree until an ADR records ownership, release, and rollback policy for a genuinely cross-product component, and reserves `Projects\shared\{platform,contracts,method-packs}\` as the only three named categories once one is created. `ADR-0001:16` already recorded that this document does not decide `HD-09` and named `ADR-0013` as `PLANNED` (this file, since filed, resolves it — `ADR_INDEX.md:31` updated to `ACCEPTED` in the same batch); `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:31` (Wave 0) lists resolving `HD-09` as a precondition of Wave 0 closing, and `22:67-71` (Wave 3) names "Shared Kernel thin-reference types built as actual code... not left as prose" as that Wave's deliverable, at `Projects\internal\hci30\packages\contracts\`.

## Decision

Adopt extraction, **minimally scoped**: a versioned kernel package at `Projects\shared\contracts\kernel\` (the `kernel` package inside `17:152`'s existing `contracts` category — this reconciles the operator's "Projects/shared/kernel" instruction with `17`'s three-category taxonomy without adding a fourth category to that document), semver-versioned, **vendored/pinned by each product — never a live service or shared database**. The package contains exactly three things and nothing else:

1. Thin reference types `EntityRef`, `PersonRef`, `OrganizationRef`, `EvidenceRef`, `TenantContext`, `ActorRef`, `SourceRef` — the seven identifier-shaped stubs from `18:126`. `18:126` also lists an eighth item, `Timestamp`; it is deliberately excluded from v1 kernel scope because it is a language/DB-native primitive with no cross-product ownership question attached, not a domain reference type — trivial to add in a later minor version if a real need appears, not worth bundling now. `TenantContext` here is an opaque identifier-and-product-scope stub only; it does not redefine or duplicate `ADR-0009`'s Tenant/Organization adapter mapping, which remains that ADR's exclusive territory with its own open gates.
2. The `epistemic_type` enum (11 values, `SOURCE_FACT`...`DECISION`) from `specs/governance/epistemic-label.schema.yaml#/definitions/epistemic_type`, per `ADR-004`. The kernel re-exports this single sub-definition only — **not** `authorship_state`, **not** the `locked` axis, and **not** the composite `provenance_record` object. Those stay product-specific extensions layered on top by whichever product needs them, consistent with "minimally scoped."
3. The R0-R4 risk-tier ladder (`risk_tier` enum plus its `tiers`/`required_actions` table) from `specs/execution/risk-tier.schema.yaml#/risk_tier`, per `ADR-004`.

Item 4 from `09:65-88`'s candidate list — Tenant/entitlement/billing substrate — is **not** part of this kernel; it is already governed by `ADR-0009` as a separate adapter-contract concern with its own open gates, and folding it into this package would contradict `ADR-0009`'s scoping, not extend it.

**Why this option and not the alternatives** (`09:63` names the same three; C1 at `09_AI_INTELLIGENCE_REVIEW.md:96-99` supplies a fourth):

- **Full C1-recommended kernel** (adds Evidence/Claim/Decision record shapes, `authorship_state`, `locked`) loses: `specs/decision/decision.schema.yaml`'s `Decision` shape and any Evidence/Claim record shape both depend on `HD-06` (bitemporal scope) and `HD-10` (Case/Engagement aggregate) — both now decided, by `ADR-0017` and `ADR-0020` respectively (same batch as this ADR), but neither is *implemented*: no migration carries `ADR-0017`'s `valid_from`/`valid_to`/`system_recorded_at`/`system_superseded_at` columns or `ADR-0020`'s `hci.cases` table yet (`22_OPEN_HUMAN_DECISIONS.md:47-51,71-75` — historical record of the question, now superseded by those two ADRs). Freezing those shapes into a versioned package now still risks a breaking major-version bump the moment either lands as real schema — the opposite of the "cheapest it will ever be" framing at `09:90` — the risk has moved from "undecided design" to "decided-but-unbuilt design," not disappeared.
- **CI contract test only, no extraction** (the "lighter middle option" at `09:63`, and Alternative C at `09_AI_INTELLIGENCE_REVIEW.md:98`) loses: it only detects drift after each side has already hand-built its own copy. `07:78-98` shows HCI has already started an independent prose vocabulary; a contract test with nothing canonical to test against still leaves two independently-evolving SSOTs a human must keep in sync, which is exactly the "split-brain SSOT... doubles the 30-year maintenance burden" risk `09:63` itself names. A pinned package removes the second hand-authored copy; the contract test (retained below, item 3 of the required gates) is strictly additive verification on top of a single source, not a substitute for having one.
- **Status quo / full duplication** loses per `09_AI_INTELLIGENCE_REVIEW.md:102`: deferred past the Wave-1 freeze, reconciliation requires reclassifying every historical Evidence/Claim/Assessment record against a taxonomy that has already diverged in production, compounded by `HD-06`'s bitemporal requirement — decided by `ADR-0017` (same batch), but a reclassification against real bitemporal columns that don't exist yet in any migration is exactly as costly as against an undecided one.

## Required implementation gates

Wave 0 (this ADR) only ratifies the decision; no runtime gate below is implemented yet. All land in **HCI Wave 3** (`22:67-71`) except gate 5, which is Wave 1.

1. **`KERNEL-PKG-SURFACE-01`** (Wave 3) — `Projects\shared\contracts\kernel\package.json` declares an exact semver `version` (no pre-release wildcard) and the package's public export surface is exactly `{refs, epistemicType, riskTier}` — nothing else. CI test `Projects\shared\contracts\kernel\tests\surface.test.mjs` asserts `Object.keys(kernel)` against that fixed allowlist. Mutation: add a fourth export (e.g. a `Decision` shape) → red. Proves "minimally scoped... nothing else."
2. **`KERNEL-VENDOR-PIN-01`** (Wave 3) — `Projects\internal\hci30\packages\contracts\package.json` depends on the kernel at an **exact** version (no `^`/`~`/`latest`, no workspace symlink into `Projects\shared\contracts\kernel\`). CI script `scripts\verify-pinned-deps.ps1` fails the build on a range operator, `latest`, or a resolved dependency path that is a symlink rather than an installed package copy. Proves "vendored/pinned... never a live service."
3. **`KERNEL-CONTRACT-HCI-01`** (Wave 3) — `Projects\internal\hci30\tests\contracts\epistemic-mapping.test.mjs` asserts every value HCI's own admission-state vocabulary (whatever Wave 1 froze from `07:78-98`'s Fact/Observation/Interpretation/Hypothesis model) maps to exactly one pinned-kernel `epistemic_type` value, with no two HCI states collapsing onto the same kernel value in a way that loses information a downstream consumer needs (lossless per the task's own wording). Mutation: introduce an HCI-only state with no injective target → red. This is the literal "CI contract test... asserts local enums map losslessly onto the pinned kernel version" requirement.
4. **`KERNEL-CONTRACT-COGOS-01`** (mirrors this pattern in `cognitive-engineering-os`'s own `tests\`, lands with that product's first runtime commit — not before, per `17:16`). Until that commit exists, recorded as **`OPEN — NOT APPLICABLE YET`** in `ADR_INDEX.md`, not as satisfied — the same convention `ADR-0001`'s gate 5 uses for its own reverse-direction check.
5. **`WAVE1-EPISTEMIC-ANNOTATION-01`** (Wave 1, precedes the kernel's own code) — any DB `CHECK` constraint or `CREATE TYPE ... AS ENUM` introduced in Wave 1 migrations for an evidence/claim/assessment epistemic or risk classification column must carry an inline SQL comment citing `ADR-0013` and marking the value set provisional pending gate 3. Script `scripts\verify-epistemic-annotation.ps1` greps `database\migrations\*.sql` for a column name matching `epistemic|risk_tier|admission_state|fact_type` lacking that comment and fails. Exists so Wave 1 does not silently freeze a vocabulary that Wave 3's lossless-mapping test then finds unmappable, forcing a breaking migration at the worst possible time.

This ADR does **not** authorize: creating `Projects\shared\contracts\kernel\` before Wave 3 begins; admitting non-synthetic or real-person data through any kernel-typed field; any production deployment; a live/network-reachable kernel service; bundling the Tenant/entitlement/billing substrate (`ADR-0009`'s territory) into this package; or extending the kernel's `epistemic_type` re-export to also carry `authorship_state`/`locked`/`Decision` without a superseding ADR.

## Consequences

- HCI's Wave 1 ERD may keep its own admission-state vocabulary and column names; it must be provably mappable onto the pinned kernel's `epistemic_type`, not identical to it.
- A later expansion, once `ADR-0017`'s (`HD-06`) and `ADR-0020`'s (`HD-10`) schemas actually land as real migrations, to bring Evidence/Claim/Decision record shapes into the shared layer requires a superseding ADR — this ADR deliberately does not pre-decide that expansion, and does not treat either HD's decision (already made) as equivalent to its schema being buildable-against yet.
- `17_REPOSITORY_LAYOUT_AND_PATHS.md:151-152`'s "do not pre-create `shared\`" rule is satisfied, not overridden: this ADR is the recording ADR that rule requires before the tree is created, and creation itself still waits for Wave 3.
- `ADR_INDEX.md:31`'s `ADR-0013` row has moved from `PLANNED` to `ACCEPTED` with this ADR's content, in the same batch.

## Verification and rollback

- Verification recorded here is documentation-only: every cited line was read on 2026-09-02. No gate above is implemented; `Projects\shared\`, `Projects\internal\cognitive-engineering-os\`, and any kernel test file are confirmed absent as of this date.
- Before implementation, rollback is to supersede this ADR with a new explicit decision (e.g., reverting to the CI-contract-test-only alternative). After implementation, rollback must not delete or weaken `KERNEL-CONTRACT-*` gates in place — mirroring `ADR-0016`'s "may not be weakened in place" rule — and any consuming product must re-pin to a prior kernel version through its own reviewed dependency change, never a live rewrite of the shared package's history.
