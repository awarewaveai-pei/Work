# ADR-0023 — Block BYOK / Customer-Managed-Key / Dedicated-DB Sales Claims Until Acceptance-Tested

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: External security claims for HCI-30 (sales, marketing, `trust.aware-wave.com`, procurement packages) only; this ADR builds no key architecture, provisions no database, and authorizes no production deploy or legal representation.

## Context

`08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md:36-38` routes Enterprise/Group/Private to the isolation tiers in `12_DEPLOYMENT_API_AND_MULTI_TENANCY.md:44-48` (Tier B–D = dedicated DB / app / region), and `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:129` lists "dedicated DB, BYOK … procurement/trust package" as Wave 9 deliverables. None of it exists: `08:45` records "zero schema, API, or migration mechanics in the repository today" for the commercial tiers, `21_HCI_TOP_TIER_GAP_ANALYSIS.md:134-136` keeps the key architecture (`KEY_HIERARCHY.md`, `ENVELOPE_ENCRYPTION.md`, `BYOK_MODEL.md`) at P1-04 as unwritten documents, and `12:50` fixes Tier A (shared DB + RLS on the single self-hosted Supabase box) as the stated default. The only runtime evidence in the register is synthetic and explicitly "NOT production-authorized" (`ADR-0016-mandatory-tenant-rls.md:3,13`; `ADR_INDEX.md:45-47`).

`HCI30_RESEARCH_REVIEW/07_SECURITY_PRIVACY_REVIEW.md:223-236` (SEC-08) names the failure: a sold-vs-actual posture gap where root/host access on the shared box reads any tenant's data regardless of what the sales material promised, turning a later security review or incident into a breach-of-contract event. `11_SECURITY_PRIVACY_GOVERNANCE.md:58` carries this as 🔴 `HD-13`; `HCI30_RESEARCH_REVIEW/22_OPEN_HUMAN_DECISIONS.md:90-92` asks whether such materials should be explicitly blocked until P1-04 is built and tested. `14_ROADMAP_AND_DEFINITION_OF_DONE.md:51` and `22:131` already state the block as prose preconditions, but prose is not a control: nothing in the repository detects the words appearing in a customer-facing artifact. `trust.aware-wave.com` is live as a DNS + nginx placeholder with no content (`03_AWARE_WAVE_DOMAIN_AND_SUBDOMAIN_MAP.md:99-103`; `20_VERIFIED_SUBDOMAIN_INVENTORY_AND_BRAND_IA.md:37`), so the first content written for it is exactly where an unevidenced claim would land. `15_BRAND_AND_GO_TO_MARKET_PRINCIPLES.md:70` already applies the same rule to one claim ("must not be marketed from a synthetic skeleton alone") without a general mechanism.

## Decision

**HD-13 = yes.** No sales, marketing, procurement, or trust-center material may state or imply that HCI-30 offers **BYOK**, **customer-managed keys**, or a **dedicated database** until the corresponding capability has a passing acceptance test recorded against its ADR in `governance/ADR_INDEX.md`. The invariant is *no external security claim without a linked, machine-resolvable evidence record* — it is enforced by a claims register (`D:\Work\agency-os\docs\trust\CLAIMS_REGISTER.md`) listing every external security claim with its evidence link, and a CI gate that fails on any gated term appearing in a claim surface without a register-backed annotation.

Why the SEC-08 alternatives lose (`07_SECURITY_PRIVACY_REVIEW.md:232-234`):

- **A — block Enterprise sales entirely**: blocks evidenced features (SSO/SCIM/RBAC, audit) that have nothing to do with key custody. The defect is the unevidenced *claim*, not the tier; gating the tier over-blocks and gives no control over the words themselves.
- **B — sell now with trust-center disclosure**: a disclosure paragraph is unchecked prose that drifts the first time a deck is copied; it also inverts the burden (customer must notice the caveat). This ADR keeps honest negative disclosure legal (see `nonclaim` below) but refuses to rely on it.
- **C — "Enterprise-lite" tier name**: renaming a SKU does not stop `BYOK` appearing in a slide. It addresses the tier axis; the risk lives on the claim axis. The register subsumes C: a lite tier is simply "all rows BLOCKED".

Synthetic verification (`SYNTHETIC GATE VERIFIED`, `ADR_INDEX.md:45-47`) is **not** sufficient evidence for an external claim; only an acceptance test executed against the environment the claim is made about qualifies. This ADR does not decide HD-12 (rotation runbook), HD-14 (residency trigger), or HD-20 (regulatory scope); it does not authorize processing real-person data, deploying to production, or making any compliance/legal representation.

## Required implementation gates

Runtime gates are **OPEN**. Each gate names the artifact and the test that must fail before it exists.

1. **`ADR_INDEX.md` registration — Wave 0, precondition for gate 2.** `governance/ADR_INDEX.md` must carry a Register row for ADR-0023 (`ADR_INDEX.md:17-34` table format: ADR id, planned topic, source, State=`ACCEPTED`, Explicit approval) and its Allowed lifecycle line (`ADR_INDEX.md:11`) must add `ACCEPTANCE VERIFIED` to the named gate-state vocabulary — gate 2's `CLAIM-REG-01` test resolves `evidence_adr` against exactly that ledger, so the ledger must have a row to resolve against. Test `INDEX-REG-01` (`Projects/internal/hci30/tests/claims/`): running `CLAIM-REG-01` while `ADR_INDEX.md` carries no ADR-0023 row, or while `ACCEPTANCE VERIFIED` is absent from its lifecycle vocabulary, must fail closed (ledger-row-not-found is a runner failure, not a silent skip). **Known gap, recorded honestly, not fabricated as done**: as of 2026-09-02 `ADR_INDEX.md`'s Register table (`ADR_INDEX.md:19-34`) and lifecycle-state line (`ADR_INDEX.md:11`) carry no entry for ADR-0023 (confirmed by grep, zero matches). This ADR does not itself edit `ADR_INDEX.md` — that is a separate, explicitly-scoped edit, due in the same batch/commit as ADR-0023's same-day siblings ADR-0022/0024/0026, and it is a precondition for gate 2 rather than a claim this ADR makes about itself.
2. **Claims register exists with a fixed schema — Wave 0.** `D:\Work\agency-os\docs\trust\CLAIMS_REGISTER.md` with a YAML front-matter `claim_surfaces:` path list and a table `claim_id | claim_text | gated_terms | status (BLOCKED \| EVIDENCED) | evidence_adr | acceptance_test_id | last_verified`. Seeded rows, all `BLOCKED`: `CLM-BYOK-01` (bring-your-own-key), `CLM-CMK-01` (customer-managed keys), `CLM-DEDDB-01` (dedicated database / Tier B+). Test `CLAIM-REG-01` (`Projects/internal/hci30/tests/claims/`): a row with `status=EVIDENCED` whose `evidence_adr` does not resolve to an `ADR_INDEX.md` gate row in state `ACCEPTANCE VERIFIED` naming the same `acceptance_test_id` → runner exits non-zero. `ACCEPTANCE VERIFIED` is a new, distinct gate state; `SYNTHETIC GATE VERIFIED` must not satisfy `CLAIM-REG-01`.
3. **CI grep gate on claim surfaces — Wave 0.** `.github/workflows/hci-claims-gate.yml` running `scripts/check-claims-register.ps1` on every push touching a `claim_surfaces` path. Gated term list (case-insensitive) lives only in the register's `gated_terms` column: `BYOK`, `bring your own key`, `customer-managed key`, `customer managed key`, `CMK`, `dedicated database`, `dedicated DB`, `dedicated-DB`, `HSM`. A line containing a gated term must carry `<!-- claim:CLM-… -->` (allowed only if that row is `EVIDENCED`) or `<!-- nonclaim:CLM-… -->` (honest negative disclosure, always allowed). Tests: `CLAIM-GATE-01` untagged term → red; `CLAIM-GATE-02` `claim:` tag on a `BLOCKED` row → red; `CLAIM-GATE-03` `nonclaim:` tag → green; `CLAIM-GATE-04` term in a non-surface path → not scanned (documented negative, prevents the gate from firing on this ADR and on `21`/`22`). Initial `claim_surfaces`: `agency-os/docs/trust/**`, `Projects/internal/hci30/enterprise/**`. The gate is fail-closed: a missing or unparsable register is red, not skipped.
4. **Mutation check — Wave 0, same commit as gate 3.** `Projects/internal/hci30/scripts/mutation-check-claims.ps1` following the pattern in `Projects/internal/hci30/README.md:11`: delete the term list, delete the status lookup, and delete the surface list in turn; each mutation must turn `CLAIM-GATE-01`/`-02` red. A gate that stays green under mutation is not a gate.
5. **Trust-center publication gate — before first content on `trust.aware-wave.com`.** `scripts/publish-trust-center.ps1` is the only path permitted to write content to `trust.aware-wave.com`'s deploy target, replacing the subdomain's current no-pipeline placeholder (`lobster-factory/infra/hetzner-phase1-core/nginx/system-sites/trust-aware-wave.conf:1-17` — static `coming-soon.conf` include; no publish/deploy script for this subdomain exists anywhere in the repo, confirmed by search on 2026-09-02). The script takes a source-root argument, must read its source root against `claim_surfaces`, and must exit non-zero without writing to the deploy target when that root is absent from the list. Test `CLAIM-PUB-01` (`Projects/internal/hci30/tests/claims/`): invoking the script with a source root not present in `claim_surfaces` must exit non-zero and leave the deploy target unwritten. Because the script does not exist today, this gate is failed by construction — no content may go live on `trust.aware-wave.com` until it exists and `CLAIM-PUB-01` passes.
6. **Row flip to `EVIDENCED` — Wave 9, per capability.** `CLM-BYOK-01`/`CLM-CMK-01` flip only when P1-04 lands with acceptance test `KEY-BYOK-ACC-01` (tenant-supplied key wraps the data-encryption key; revoking the tenant key makes that tenant's RESTRICTED field ciphertext undecryptable by the application role, executed against the target environment, not the synthetic skeleton) recorded in `ADR_INDEX.md` as `ACCEPTANCE VERIFIED`. `CLM-DEDDB-01` flips only on `ISO-DEDDB-ACC-01` (a Tier B tenant's rows live in a distinct database; the shared-DB application role cannot read them) plus the tier-upgrade migration runbook required by `08:44`. Each flip is a reviewed commit that updates `last_verified` and re-runs `CLAIM-REG-01`.

## Consequences

- Enterprise sales are not blocked; unevidenced *claims* are. SSO/SCIM/RBAC/audit claims are subject to the same register once their rows exist — the register scope is every external security claim, not only the three seeded rows (`15:70`'s data-subject-rights commitment becomes a fourth row when drafted).
- Honest negative disclosure ("dedicated database is not currently offered") remains possible via `nonclaim`, so Alternative B's transparency is retained without relying on it.
- `14:51` and `22:131` prose preconditions become enforced; those chapters should cross-reference this ADR rather than restate the rule.
- Adding a gated term, surface, or claim row is a register edit under normal review; weakening the term list or removing a surface requires a superseding ADR.
- This ADR does not change ADR-0009/0010/0011/0014/0015/0016; it consumes their `ADR_INDEX.md` gate states and adds one (`ACCEPTANCE VERIFIED`) above `SYNTHETIC GATE VERIFIED`.

## Verification and rollback

- Verification recorded here is documentation-only: the decision, its alternatives, and the gate/test identifiers are cross-linked to `11_SECURITY_PRIVACY_GOVERNANCE.md` §Encryption (`HD-13`), `08_HCI30_COMMERCIAL_EDITION_ARCHITECTURE.md`, and `ADR_INDEX.md`. `D:\Work\agency-os\docs\trust\` and `.github/workflows/hci-claims-gate.yml` do not yet exist (checked 2026-09-02); gates 1–5 are open.
- Rollback before implementation: supersede with a later explicit operator decision. Rollback after implementation: the register and workflow may be removed only by a superseding ADR; flipping a row back to `BLOCKED` is always permitted without one (it can only make claims more conservative) and must be followed by re-scanning all `claim_surfaces`.
- No data, schema, or production system is touched by this ADR, so no migration or data rollback path applies.
