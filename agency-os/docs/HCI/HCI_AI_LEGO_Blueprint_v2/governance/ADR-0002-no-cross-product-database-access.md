# ADR-0002 — No Cross-Product Database Access

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI AI LEGO Blueprint v2 architecture only; fixes the data-access boundary between HCI-30 and AI LEGO Cognitive Engineering OS and nothing else — no schema, deployment, real-person data, or legal claim is authorized by this ADR.

## Context

`02_PRODUCT_BOUNDARIES.md:71-73` re-derives the HCI/AI LEGO split against six independence criteria and finds data ownership the one criterion that does not cleanly support full separation, because both products independently reinvent Evidence/Claim vocabulary under the same names with different shapes. `09_AI_LEGO_COGNITIVE_OS_BOUNDARY.md:96-98` states AI LEGO must not own HCI Person records, relationships, trust scores, public claims, or cooperation decisions. `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md:5-11` states the two products interact only through "contract/API/event," never as a submodule of each other, and `:16` requires HCI to send "a bounded case package, not raw DB access." The same file's enforcement note (`:60-63`) says the two-ledger boundary "is not yet tamper-evident in schema" and that a cross-boundary reference must use the `EvidenceRef` thin reference from the Shared Kernel (`09:67-88`), "never a full record."

`ADR_INDEX.md:20` lists this exact topic as `ADR-0002 | No cross-product database access | PLANNED | Not recorded`, and `17_REPOSITORY_LAYOUT_AND_PATHS.md:180` names the file `ADR-0002-no-cross-product-database-access.md` as one still to be created. `ADR-0001-hci-and-cognitive-os-are-peer-products.md:26` records the peer relationship as the parent invariant and explicitly defers "the no-cross-DB rule (ADR-0002 `PLANNED`)" to this ADR, while its own gate 2 (`ARCH-PEER-02`, `:33`) and gate 4 (`PEER-REF-01`, `:35`) already specify the machine-testable database-level and reference-level assertions this decision requires — written under the same ADR-0001 in anticipation of this filing, not yet claimed here. `01_SYSTEM_CONSTITUTION.md:113-115` (Invariant 8) holds that a principle stated only in prose is an intention, not a control, until an ADR names the enforcing gate.

Current runtime state: HCI's synthetic skeleton at `D:\Work\Projects\internal\hci30\` runs an isolated PostgreSQL 15.8 container (`infra\local\compose.test.yml`) with no `ports:` mapping and a per-run, randomly generated password (`scripts\test-wave1-local.ps1:24-29`); `README.md:9` states the runner "must never be pointed at an existing database." AI LEGO Cognitive Engineering OS has specifications only — no database exists yet (`ADR-0001:14`, `17_REPOSITORY_LAYOUT_AND_PATHS.md:16`).

## Decision

No product may read or write another product's database, schema, or tables. HCI-30 and AI LEGO Cognitive Engineering OS integrate only through a versioned API or event contract (`10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md §Integration API contract`, `§Events`). No foreign key, view, database link, or shared connection may cross the product boundary; a stored cross-product pointer is an opaque, typed reference (`EvidenceRef`/run-id shape) only, never a join target.

Alternatives and why they lose:

- **Shared database, separate schemas, cross-schema FKs for convenience.** This is the fastest path to exactly the "same-named concept, two shapes" collision `02_PRODUCT_BOUNDARIES.md:73` already flags as the one weak criterion, turned from a vocabulary risk into a referential-integrity coupling: a migration or rename on either side now breaks the other product's constraints, and `01_SYSTEM_CONSTITUTION.md:132`'s architecture-failure bar (an undetected same-named-concept collision across a product boundary) is crossed at the schema level, not just the API level. It also defeats Invariant 3 (`01:57-59`) and `PEER-DEGRADE-01` (`ADR-0001:34`): a live FK means HCI cannot serve core use cases with AI LEGO's database absent, because the constraint itself would be unsatisfiable.
- **Read replica / reporting view of the other product's tables.** Still a live schema dependency: a column rename, type change, or RLS policy change on the source product silently breaks or silently under-filters the replica, and nothing in either product's migration process is obligated to check the other's view definitions. This is the "Shared God Platform" `02_PRODUCT_BOUNDARIES.md:73` and `09_AI_LEGO_COGNITIVE_OS_BOUNDARY.md:88` explicitly reject, wearing a read-only disguise.
- **`postgres_fdw` / `dblink` for ad hoc cross-product queries.** Grants network-level DB reachability between products by construction, which is strictly worse than a FK: it bypasses each product's own RLS and application-layer policy mapper (`10:57-58`) entirely, and a single misconfigured foreign server exposes the full remote schema, not one column. `ADR-0001` gate `ARCH-PEER-02` already names this the concrete failure mode to block.
- **Full record exchange ("send me your Evidence table") instead of `EvidenceRef`.** Rejected by `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md:60-63` directly: it re-collapses "Evidence" into meaning two differently-owned things depending on which side of the adapter one stands on, which is exactly the ambiguity the Shared Kernel's thin-reference types exist to prevent.

## Required implementation gates

This ADR is the decision-of-record for the database-access boundary; it does not re-specify new assertions where `ADR-0001` already named the correct one, and it does not weaken or duplicate them. Gates 1 and 2 below are `ADR-0001`'s `ARCH-PEER-02` and `PEER-REF-01`, cited here as the implementation of *this* decision; gate 3 is new and closes a control `ADR-0001` did not cover (credential/network isolation, distinct from schema/FK isolation — a shared login role or reachable host defeats the boundary even with zero foreign keys).

1. **`ARCH-PEER-02` — no database-level coupling (Wave 1, owned by `ADR-0001`, reused here).** `database\tests\wave1-negative-tests.sql`, via `hci_test.expect_true`: `pg_extension` contains neither `postgres_fdw` nor `dblink`; `pg_foreign_server` is empty; no `pg_constraint` of type `f` references a relation outside schema `hci`; no schema other than `hci`, `hci_test`, and PostgreSQL defaults exists. Run by `scripts\test-wave1-local.ps1` and covered by `scripts\mutation-check-wave1.ps1`. Mutation: `CREATE EXTENSION dblink` in the up migration → red.
2. **`PEER-REF-01` — cross-product pointers are opaque references only (Wave 10, owned by `ADR-0001`, reused here).** Assertion in the same SQL suite: every column matching `%cognitive_run%` or `%execution_ref%` is `text`/`uuid`, carries no foreign key, and no `CHECK` dereferences another product's identifier space — the only permitted coupling is `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md:70`'s "HCI assessment may store references to AI LEGO run IDs." Mutation: add a FK from an assessment row to any non-`hci` relation → red.
3. **`ARCH-PEER-02b` — credential and network isolation (Wave 1, new).** `infra\local\compose.test.yml` carries no `ports:` mapping and a per-run generated password (already true, `scripts\test-wave1-local.ps1:24-29`); add an assertion to that script — before teardown, `docker compose ... exec -T db psql -c "SELECT rolname FROM pg_roles"` must return only `hci_owner`, `hci_app`, and PostgreSQL built-in roles, none matching `%cognitive%` or `%lego%`, and the runner must abort (already does, `:22`) if `docker context` resolves to a non-local endpoint. This is the operational half of the rule: `ARCH-PEER-02` proves no FK crosses the boundary; this gate proves no shared login credential or reachable network path could bypass RLS to cross it even without one. Mutation: add a role granted `CONNECT` matching a future `cognitive-engineering-os` naming convention to the up migration → red.
4. **`ARCH-PEER-05` — reverse direction, database side (lands with the first runtime commit under `Projects\internal\cognitive-engineering-os\`; not before, per `17_REPOSITORY_LAYOUT_AND_PATHS.md:16`).** Mirror of gate 1 in that product's own test suite: no `postgres_fdw`/`dblink` extension, no foreign server, and no constraint referencing schema `hci`. Until that runtime commit exists, this is recorded as `OPEN — NOT APPLICABLE YET`, not as satisfied, matching `ADR-0001` gate 5's convention.

CI: gates 1-3 run in the existing Wave 1 job (`13_TESTING_REPLAY_ROLLBACK_AND_SRE.md:20-24` requires blocking, not illustrative, gates); no separate workflow file exists yet.

This ADR does **not** authorize: admitting non-synthetic or real-person data through any path, including a compliant API/event integration; any production deployment of either product; creating `D:\Work\Projects\shared\` or a live shared database service (needs its own ADR per `17_REPOSITORY_LAYOUT_AND_PATHS.md §Cross-product components` — a vendored, pinned package is not a shared database and remains permitted only per `ADR-0001:18,45` and the still-open `HD-09`/`ADR-0013`); or any claim of legal compliance.

## Consequences

- Every future HCI or AI LEGO migration that would add a foreign key, view, extension, or role crossing the product boundary is a build failure at gates 1, 3, and 4, not a review comment.
- The only sanctioned cross-product data path is the adapter under `hci30\integrations\cognitive-os\` (`17_REPOSITORY_LAYOUT_AND_PATHS.md:100-107`) calling the API/event contract in `10_HCI_AI_LEGO_INTEGRATION_CONTRACT.md`; `ARCH-PEER-01` (`ADR-0001` gate 1) already blocks any import/path/SQL reference to the other product's tree from outside that adapter, which is the code-level twin of this ADR's schema-level rule.
- `ADR-0009`'s tenant/organization adapter and `ADR-0016`'s per-tenant RLS remain the controls for cross-*tenant* access within one product's database; this ADR is the orthogonal cross-*product* control and does not substitute for either.
- The Shared Kernel extraction (`HD-09`, resolved by `ADR-0013`, `ACCEPTED` same batch) adds only a vendored, pinned shared package; it may not add a shared database, live query path, or cross-product FK without superseding this ADR.
