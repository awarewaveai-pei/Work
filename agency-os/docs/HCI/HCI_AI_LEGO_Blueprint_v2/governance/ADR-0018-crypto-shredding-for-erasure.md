# ADR-0018 — Crypto-Shredding for Erasure

Status: **ACCEPTED**
Date: 2026-09-02
Decision authority: Operator-delegated (2026-09-02, full delegation to Claude); operator may supersede with a later explicit decision
Scope: HCI AI LEGO Blueprint v2 data model and Wave 1 synthetic schema only; this ADR fixes the schema-level mechanism by which a lawful erasure request destroys Evidence/Claim content while preserving row metadata and lineage. It does not authorize real-person data processing, a production deploy, an external KMS/BYOK integration, or any legal representation that crypto-shredding satisfies "erasure" under a specific jurisdiction's law — that determination belongs to `HD-20`/`HD-21`, not this ADR.

## Context

- `HD-07` (`HCI30_RESEARCH_REVIEW/22_OPEN_HUMAN_DECISIONS.md:53-57`) names the tension directly: Invariant 6 requires history is never overwritten (`01_SYSTEM_CONSTITUTION.md:87,89` — "Do not overwrite history. Corrections create new versions and retain lineage"), while `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md` §Data Subject Rights (`:58-65`) and §Identity Correction (`:68-70`) describe HCI storing allegations, legal matters, and disputed claims about identifiable, non-consenting real people who hold statutory correction/erasure rights. CI-7 (`HCI30_RESEARCH_REVIEW/06_DATABASE_ARCHITECTURE_REVIEW.md:275-294`) states the consequence: if erasure is compelled, deleting the row breaks Invariant 6 and the audit trail behind every past Decision that cited it; refusing to delete risks a legal violation.
- The recommended mechanism is already sketched twice in the accepted document set, not invented here: `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md:126-127` lists `encryption_key_ref` and `tombstoned_at` as "new in V2" columns directly on the Evidence provenance schema, and `07:138-140` (§Immutability vs. Erasure) names crypto-shredding as the 🔴 DECISION PENDING recommended Option A, cross-referencing CI-7 Alternative B (`06:285-288`). `22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:49` already lists "crypto-shredding schema (`encryption_key_ref`/`tombstoned_at`)" as a Wave 1 deliverable that "must land in this Wave" — Wave 1 acceptance was written against this ADR's outcome before the ADR existed.
- The Wave 1 synthetic skeleton (`D:\Work\Projects\internal\hci30\database\migrations\0001_wave1_synthetic_up.sql`) was built anticipating this decision: `hci.data_subject_requests` already has a `DELETION` request_type (`:129`) with an enforced `RECEIVED → IN_REVIEW → RESOLVED|REJECTED` lifecycle (`hci.enforce_dsr_transition`, `:134-160`); `hci.data_subject_request_events.event_type` already permits `'ERASURE_RECORDED'` as a value (`:167`); `hci.data_subject_request_targets` already links a request to a specific `EVIDENCE`/`CLAIM`/`ASSESSMENT` row via a typed composite FK into `hci.subject_records(tenant_id, id, kind)` (`:171-176`). None of this fires anything yet — `hci.subject_records` (`:116-126`) carries no `encryption_key_ref`, no `tombstoned_at`, and no payload column; ADR-0014's gate covers only the request/event/target skeleton, not what an `ERASURE_RECORDED` event does to the target's content. No `pgcrypto` extension or key table exists in the migration today.
- ADR-0017 (`governance/ADR-0017-bitemporal-scope.md` §Consequences) left this open by name: "`HD-07` crypto-shredding sets `tombstoned_at` on an existing row... that is a second trigger-owned column write and must be reconciled with gate 2 when `HD-07` is decided — this ADR neither permits nor forbids it." This ADR is that reconciliation.
- The append-only enforcement this design must fit inside is already live: `hci.subject_records` is in the `append_only` array (`:300-314`) — the application roles hold `SELECT, INSERT` only; `UPDATE`/`DELETE` are revoked, and `hci.reject_update_delete` (`:179-183`) raises `H1003` on any attempted mutation. Any column this ADR must change post-insert (`tombstoned_at`) has to go through the same single-purpose, `SECURITY DEFINER`, function-owned exception ADR-0017 used for `system_superseded_at`, not a blanket re-grant of `UPDATE`.

## Decision

Adopt **HD-07 Option A**: every `EVIDENCE`/`CLAIM` row's content is stored as ciphertext under a per-record symmetric key, referenced by `encryption_key_ref`, held in a key table (`hci.data_encryption_keys`) the application roles cannot read directly — not encrypted-with-a-master-key envelope, literally no grant. Erasure never deletes the `hci.subject_records` row (Invariant 6 is preserved): it destroys the referenced key, sets `tombstoned_at`, and appends the already-provisioned `ERASURE_RECORDED` event (`:167`) — an immutable record that the erasure happened survives even though the content it erased does not. Key material never leaves PostgreSQL in Wave 1: generation (`pgcrypto.gen_random_bytes`), storage, and use happen entirely inside the database through `SECURITY DEFINER` functions; a BYOK/HSM/external-KMS adapter is deferred to a later Wave and is explicitly not authorized here, consistent with ADR-0023's block on claiming BYOK before an acceptance-tested capability exists.

Why the alternatives lose, in engineering terms:
- **CI-7 Alternative A (full row deletion on erasure)** breaks Invariant 6 directly: `hci.subject_records` rows are referenced by `hci.data_subject_request_targets` (`:171-176`) and, per ADR-0017, by a `supersedes_id` lineage chain — deleting one either fails on the foreign key or silently truncates a Decision's evidentiary trail, exactly what `H1003` exists to prevent.
- **CI-7 Alternative B (literal storage-level WORM)** requires S3-Object-Lock-class immutable storage; `07:139` confirms none exists in the verified single-box infrastructure. Not buildable at Wave 1 without adding an infrastructure dependency this ADR is not authorized to add.
- **CI-7 Alternative C (narrow WORM to non-personal metadata only, leave personal Evidence conventionally deletable)** reintroduces literal `DELETE` on exactly the rows Invariant 6 protects most, reopening the same audit-trail loss as Alternative A for the data class where the guarantee matters most.
- **Envelope encryption with a customer-supplied master key now (BYOK)** is out of scope by ADR-0023: no acceptance-tested key-custody capability exists yet, so building customer key custody now would be capability the product cannot yet honestly claim.

This ADR does not decide `HD-12` (key-rotation/compromise-response runbook — stays Wave 2, `22:61`) or `HD-13`/BYOK timing (governed by ADR-0023). It does not authorize processing real-person data or a production deploy.

## Required implementation gates

Runtime gates are **OPEN**. All land in `D:\Work\Projects\internal\hci30\database\`, run through `scripts/test-wave1-local.ps1`, and must be killed by `scripts/mutation-check-wave1.ps1` before a gate may be claimed working (the pattern already proven at 51 assertions / 15 mutations, `wave1/HCI_WAVE1_NEGATIVE_TEST_SPEC.md:46-58`):

1. **Wave 1 — key table, isolated by grant, not by encryption of the key.** Migration `0003` adds `CREATE EXTENSION IF NOT EXISTS pgcrypto` (absent from `0001_wave1_synthetic_up.sql` today) and creates `hci.data_encryption_keys` (`id uuid PK`, `tenant_id uuid NOT NULL REFERENCES hci.tenants(id)`, `key_material bytea NOT NULL DEFAULT gen_random_bytes(32)`, `created_at timestamptz NOT NULL DEFAULT now()`, `destroyed_at timestamptz`). No `GRANT` of any kind is issued to `hci_app_test_a`/`hci_app_test_b` on this table — the default-deny state is the control. Test `CRYPTO-KEYGRANT-01`: query `information_schema.role_table_grants` for either role against `hci.data_encryption_keys`, fail if any row returns. Mutation: adding a stray `GRANT SELECT` to the fixture must turn this test red. **Amended at Wave 2 by `ADR-0022`** (`ADR-0022-minimal-key-rotation-and-compromise-runbook.md` §Amendment to ADR-0018): `key_material` becomes ciphertext of this per-record key (wrapped under a tenant `KEK`) rather than the raw key itself, and a new `wrapped_by_kek_version` column is added alongside it — this Wave 1 gate's shape (raw `key_material`, zero grants) is the deliberately-simple base case ADR-0022 wraps, not replaces; see that ADR for the reconciliation.
2. **Wave 1 — reference columns and scope fence on `hci.subject_records`.** Adds `encryption_key_ref uuid` and `tombstoned_at timestamptz` (`:116-126`), `FOREIGN KEY (tenant_id, encryption_key_ref) REFERENCES hci.data_encryption_keys(tenant_id, id)`, and two symmetric `CHECK`s: `CHECK (kind NOT IN ('EVIDENCE','CLAIM') OR encryption_key_ref IS NOT NULL)` and `CHECK (kind IN ('EVIDENCE','CLAIM') OR encryption_key_ref IS NULL)`. Tests: `CRYPTO-KEYREQ-01` (Evidence/Claim insert with `encryption_key_ref` NULL → `23514`), `CRYPTO-SCOPE-01` (Assessment/TrustDomain insert with a non-null `encryption_key_ref` → `23514`), `CRYPTO-CROSSTENANT-KEYREF-01` (a tenant-B key attached to a tenant-A row, run as the non-owner `hci_app_test_a` role per ADR-0016's test-role pattern → `23503`).
3. **Wave 1 — tombstoning is a function-owned exception, not a re-grant.** `hci.subject_records` keeps `UPDATE` revoked from both application roles (unchanged, `:312-314`). A single `SECURITY DEFINER` function `hci.tombstone_evidence(record_id uuid)`, owned by the schema owner, performs `UPDATE ... SET tombstoned_at = now() WHERE id = record_id AND tombstoned_at IS NULL`, mirroring `mark_superseded()` (ADR-0017 gate 2). A second call on an already-tombstoned row raises a new SSOT code `H1009` ("record already erased"), added to the registry comment block (`:24-31`) as the next free code after ADR-0017's `H1008`. Tests: `CRYPTO-TOMBSTONE-01` (direct app-role `UPDATE ... tombstoned_at` → `H1003`, existing trigger, unchanged), `CRYPTO-TOMBSTONE-02` (two calls to `hci.tombstone_evidence()` on the same row → second call `H1009`).
4. **Wave 4 — mediated write/read; the key never reaches the app role.** When Evidence/Claim gain a real payload column at Wave 4 (`22_HCI_TOP_TIER_IMPLEMENTATION_MASTER_PLAN.md:75-84`, "Evidence/Claim/Assessment core"), that column is `bytea` ciphertext only, and application-role `INSERT` on `hci.subject_records` is narrowed to the restricted-column form already used for `data_subject_request_events.created_at` (`:340-344`), so `encryption_key_ref` and the ciphertext column can only be populated by `hci.write_evidence_payload(tenant_id, person_id, plaintext)` (generates the key row, encrypts via `pgcrypto.encrypt()` with that key, inserts both in one transaction) and read only through `hci.read_evidence_payload(record_id)` (raises `H1009` if `tombstoned_at IS NOT NULL`, else decrypts, tenant-scoped through `hci.current_tenant_id()`, `:274-278`). Tests: `CRYPTO-WRITE-01` (app role attempts `INSERT` supplying `encryption_key_ref` directly, bypassing the function → `42501`, no column privilege), `CRYPTO-ROUNDTRIP-01` (write then read on a non-tombstoned row returns the original plaintext), `CRYPTO-READ-TOMBSTONED-01` (read on a tombstoned row raises `H1009` — no code path may return ciphertext or plaintext as a fallback).
5. **Wave 4 — erasure is one function wired to the existing DSR lifecycle, not a manual admin action.** `hci.record_erasure(request_id uuid)` fires only when the linked `hci.data_subject_requests.request_type = 'DELETION'` transitions to `'RESOLVED'` (the existing `enforce_dsr_transition` trigger, `:134-160`, is unchanged and still owns that transition). For every `hci.data_subject_request_targets` row for that `request_id` whose `target_kind` is `EVIDENCE` or `CLAIM` (`:171-176`, already typed against `subject_records(tenant_id, id, kind)`): set the referenced `hci.data_encryption_keys.key_material = NULL, destroyed_at = now()`, call `hci.tombstone_evidence(target_id)` (gate 3), then insert one `hci.data_subject_request_events` row per target with `event_type = 'ERASURE_RECORDED'` (already an allowed value, `:167`) via the existing restricted-column `INSERT` grant (`:343-344`). Tests: `CRYPTO-ERASURE-01` (a `RESOLVED` `DELETION` request with one `EVIDENCE` target → key `key_material` NULL, `tombstoned_at` set, exactly one `ERASURE_RECORDED` event for that target), `CRYPTO-ERASURE-02` (calling `hci.record_erasure()` on a request not yet `RESOLVED` → rejected, no key or row touched — erasure cannot bypass DSR review), `CRYPTO-ERASURE-METADATA-01` (after erasure, the `subject_records` row, its `tenant_id`/`person_id`/`kind`/`created_at`/any ADR-0017 `supersedes_id` lineage, and its history in `data_subject_request_targets` all remain queryable — only content and key are gone).
6. **Wave 1 — no external key path (architecture test).** `CRYPTO-NOEXTERNAL-01`: `pg_extension` in the target database carries no network-capable extension (`dblink`, `postgres_fdw`, `http`, or equivalent), and `pg_proc.prosrc` for every function in the `hci` schema contains no call to one. This is the machine form of "key material never leaves PostgreSQL in Wave 1" and the fence a future KMS-adapter ADR would explicitly have to move.

## Consequences

- `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md` §Immutability vs. Erasure (`:138-140`) loses its 🔴 DECISION PENDING marker; the `encryption_key_ref`/`tombstoned_at` columns already sketched at `:126-127` are now a specified design, not a placeholder.
- `HD-07`'s "erasure event itself becomes an immutable, logged fact" is realized concretely as `ERASURE_RECORDED`, already provisioned by ADR-0014's schema (`:167`) — no new event type or DSR-lifecycle change is required, only the function that fires it.
- A future `PersonMergeLog`/`PersonSplitLog` correction (`07:68-70`) that re-attributes an Evidence row discovered to belong to the wrong Person still needs the originally-erased Person's erasure to remain enforceable against rows now correctly attributed elsewhere. Keying per-record (one key per Evidence/Claim row, not one key per Person) is what keeps a merge/split from having to re-key unrelated rows; that interaction is noted, not built, here.
- This ADR is a schema mechanism the operator has chosen to defend, not a legal determination that crypto-shredding satisfies "erasure" in any jurisdiction — `HD-20`/`HD-21` remain the governing decisions for that claim.
- A later move to envelope encryption or an external KMS requires a superseding ADR; `hci.data_encryption_keys` may gain columns for that, but the "application roles hold zero grants on this table" invariant from gate 1 may not be weakened without one.
- This move already happened, as an amendment rather than a superseding ADR: `ADR-0022` (Wave 2, `HD-12`) wraps gate 1's `key_material` under a tenant KEK instead of leaving it raw, adding `wrapped_by_kek_version` and a new `tenant_keks` table. It does not touch the zero-grant invariant, the erasure mechanism (`hci.tombstone_evidence()`, `hci.record_erasure()`), or gate 6's no-external-network-path fence — it only changes what `key_material` *contains*. Any future reader implementing gate 1 should implement the Wave 2 wrapped shape directly rather than building the raw-key version first and migrating; see `ADR-0022` §Amendment to ADR-0018 for the full reconciliation.

## Verification and rollback

- Verification recorded here is documentation-only: the chosen option is cross-linked to `07_HCI30_DOMAIN_MODEL_AND_DATA_OWNERSHIP.md` §Immutability vs. Erasure, `22_OPEN_HUMAN_DECISIONS.md` HD-07, and `governance/ADR-0017-bitemporal-scope.md` §Consequences (the open reconciliation this ADR closes). No migration, function, or test named above exists yet; every gate is open.
- Before implementation, rollback is to supersede this ADR with a later explicit decision (operator or delegated). After migration `0003` runs on a populated schema, rollback is a reviewed `0003_down` that may drop empty `encryption_key_ref`/`tombstoned_at` columns but must not resurrect a destroyed `key_material` value or un-tombstone a legitimately erased row — reversing a completed erasure is not a schema operation, it is a new incident.
