Combined with the original 8, total fine-grained coverage is now 39/50 modules (11 remain module-level fallback: `api`, `cli`, `core`, `desktop`, `hr`, `integrations`, `migration`, `mobile`, `offline`, `reliability`, `web`).
- `integrations` (4 docs: `29_Connector_Runtime_Standard`, `31_Commerce_Marketplace_Connectors`, `32_CRM_Marketing_Social_Connectors`, `33_Payment_Logistics_Finance_Connectors`) was attempted but deliberately excluded from `modules_fine_grained`: all 4 docs have zero itemized sections in `blueprint-architecture-items.json` upstream, so per-capability filtering would never activate for it -- it stays in `modules_fallback_full_content`, which is functionally identical (`filter_section_content` already falls back to full raw content whenever a section's item list is empty).
- Multi-doc module support: `covered_modules` values can now be a doc_id string (single-doc, unchanged for the original 8 + 27 of the 31 new modules) OR a list of doc_ids (`domain`: 6 docs, `workflow`: 3 docs, `analytics`: 3 docs, `ai`: 2 docs -- discovered during this pass, not called out by the original task spec but required by `blueprint-doc-mapping.json`'s existing shape). `scripts/foundry_generate.py`'s `blueprint_item_maps()` flattens both forms into one `covered_docs` set; `module_architecture_text()` already iterated per-doc correctly (no change needed there), verified with a real multi-doc generation test (`domain` module, single vs. all capabilities).
- 4 classes of cross-fragment attribution conflicts found and resolved (80 individually-conflicting `(doc_id,section,item_index)` triples total, detected by a mechanical cross-fragment ownership scan, not just the 3 flagged in the task brief):
  1. **Mechanical (specific-capability always wins over `_module_common`)**: any item independently claimed by a specific capability in one fragment but dumped into a *different* fragment's own `_module_common` bucket (e.g. `warranty`'s 5 items reported by `returns`' `module_common`, `inventory_ops`'s items reported by `domain`'s `module_common`, `content`'s items reported by `files`' `module_common`). Resolved by building the full set of every triple claimed by any specific capability across all fragments + the pre-existing live file, then filtering it out of every `_module_common` list before merging into one global bucket.
  2. **Broad domain-module capability 100%-subsumed by a dedicated sibling module** (manual judgment, "specific wins over generic catch-all"): `domain.CAP-UGC` (8 items) fully duplicated `reviews`' `CAP-REVIEWS`/`CAP-REVIEW-MODERATION`/`CAP-REVIEW-REQUEST` split -- removed entirely from `domain`. Same pattern found (not flagged in the task brief) for `domain.CAP-FINANCIAL-RECORDS` (24 items, fully duplicated `analytics`' 3-capability split) and `domain.CAP-PROJECTS` (11 items, fully duplicated `workflow`'s `CAP-TASKS`/`CAP-CHECKLIST`) -- both removed entirely from `domain`.
  3. **Broad domain-module capability partially subsumed**: `domain.CAP-INVENTORY` (27 items) mostly duplicated `inventory_ops.CAP-MULTI-LOCATION-STOCK` (21 of 27 items) -- trimmed to the 6-item residual `inventory_ops` itself had deferred to `_module_common` (not flagged in the task brief).
  4. **Single-item specific-vs-specific conflicts requiring text-level judgment** (read `blueprint-architecture-items.json` item strings to decide): doc 16 `events_consumed[0]` ('order.delivered') awarded to `returns.CAP-RETURNS` over `warranty.CAP-WARRANTY`; doc 17 `events_consumed[0]` ('order.paid') awarded to `loyalty.CAP-LOYALTY-POINTS` over `reviews.CAP-REVIEW-REQUEST`; doc 22 `data_rules[2]` ('Currency rate source versioned') awarded to `globalization.CAP-MULTI-CURRENCY` over `analytics.CAP-FINANCIAL-STATEMENTS`; doc 42 (`search`/`merchandising`, task-flagged conflict #3) had 4 real overlapping items (`events_consumed[0,1,2]`, `data_rules[2]`) despite both agents reporting "zero overlap" -- awarded to `merchandising`'s finer split, trimmed from `search.CAP-SEARCH`; doc 08 (`files`/`content`) had 9 overlapping items -- awarded to `content.CAP-DAM` (doc-title-matching dedicated module), trimmed from `files` (`DER-FILE-INTEGRITY`/`DER-FILE-AUTHZ` end up with 0 items post-trim, honestly reported as zero-item capabilities rather than kept as empty duplicates).
- `capabilities_in_fine_grained_modules_with_zero_items` grew from 20 to 111 entries (39 modules now checked instead of 8); most are genuine content gaps already known from the 32-module mapping pass (e.g. `identity`/`tenant` only had 4 total items across both, from the same thin `02_Platform_Core` doc) or DER-* derived-requirement capabilities with no concrete doc item; a smaller subset (`CAP-UGC`, `CAP-FINANCIAL-RECORDS`, `CAP-PROJECTS`, `DER-FILE-INTEGRITY`, `DER-FILE-AUTHZ`) are zero specifically because this merge's conflict resolution deferred them entirely to a sibling module.
