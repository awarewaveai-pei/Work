- Deterministic (non-LLM) blueprint-content extraction: `generation/blueprint-doc-mapping.json` (40 business modules -> Commerce OS blueprint doc(s), 11 modules intentionally unmapped -- 7 platform-shape + 4 with no matching doc), `scripts/extract_blueprint_content.py` extracts Domain Objects/Service Contract/Events/Permissions/Data Rules/LEGO Test/DoD verbatim into `generation/blueprint-architecture-content.json` (42 docs, 38 with matched sections). `foundry_generate.py` writes `docs/modules/<mid>/BLUEPRINT_ARCHITECTURE.md` per selected mapped module with non-empty content only (no file, no placeholder, otherwise) -- real architecture content scoped to selection, on top of the existing generic 10-artifact governance package.
- Unit-level (per-capability) filtering of `BLUEPRINT_ARCHITECTURE.md`: `scripts/extract_blueprint_items.py` mechanically splits every extracted section into an ordered list of discrete items (`generation/blueprint-architecture-items.json`, 42 docs / 1,205 items -- one bullet, one code-block line, or one numbered LEGO-Test criterion per item). `scripts/build_capability_item_map.py` is the hand-curated (not string-matched) semantic mapping of each item to the capability ID it actually corresponds to, or to a `_module_common` bucket for module-wide items (generic LEGO-Test criteria, Definition of Done, invariants spanning 2+ capabilities) that are always included regardless of which capabilities are selected -- written to `generation/blueprint-capability-item-map.json`. 8 of 40 mapped modules got fine-grained per-capability item mapping this pass: `cross_border`, `b2b`, `customer_service`, `marketing`, `subscription_commerce`, `pos`, `oms`, `sales` (29 capability buckets incl. `_module_common`, 20 capabilities in those 8 modules legitimately have zero doc-specific items -- e.g. `CAP-MOQ`, `CAP-LANDED-COST`, `CAP-SLA-TRACKING` -- because the mechanically-extracted 8 sections never name that capability's specifics; selecting one of those alone yields `_module_common` items only, nothing fabricated). The remaining 32 mapped modules keep the pre-existing full-module fallback unchanged. `foundry_generate.py`'s `write_module_package`/`module_architecture_text` now filter each fine-grained-mapped doc's sections to the module's actually-*selected* capabilities (`plan['module_reasons'][mid]`, not "module selected/not selected") plus `_module_common`; selecting every capability in a fine-grained module reproduces the old full-module content byte-for-byte (verified: `cross_border` all-4-capabilities output identical to the pre-filtering extraction).

## Added (industry-pack selection layer, 2026-09-08)
- `industries/REGISTRY.json`: maps an industry key to its catalog/rules/generation relative paths. `default_industry: commerce`; commerce's registry entry points at the exact pre-existing top-level paths (`capabilities/catalog.json` etc, unmoved) -- zero regression for every caller that never passes `industry`.
- `configurator_engine.py`: `industry_paths(industry=None)`; `active_questions`/`validate_answers`/`capability_closure`/`resolve`/`questionnaire_digest` all take an optional trailing `industry=None` param (positional-safe, every existing call site is unaffected). `resolve()`'s returned plan dict gained no new key (`schemas/foundry-plan.schema.json` has `additionalProperties: false`); `industry` is a call parameter, not plan state.
- `resolve()` gained an optional module-rules extension: an industry's registry entry may point `module_rules` at a `{when_capability, require_modules[]}` rule file (commerce: `null`, no-op); when a listed capability is in the resolved closure, its extra modules are added to `modules`/`module_reasons` with the triggering capability recorded as the reason. This is how `construction-mep-contractor`'s `MEP-CAP-DISPATCH` correctly pulls in the `identity_authorization` module it has no direct capability.module tag for.
- `foundry_generate.py`: `cap_maps`/`blueprint_content_maps`/`blueprint_item_maps`/`write_requirements`/`generate` all take an optional trailing `industry=None`. `blueprint_content_maps` now also returns the content pack's own `source_pack` string (previously a hardcoded Commerce-only literal in `module_architecture_text`'s header); the Commerce JSON already carried an identical `source_pack` value, so output is byte-identical. `BP_SECTION_TITLES` gained two new keys, `state_machine`/`contract_schema`, additive only (Commerce docs never populate them).
- `scripts/serve_configurator.py`: new `GET /api/industries`; `GET /api/catalog` accepts `?industry=`; `POST /api/resolve` and `/api/generate` accept an `"industry"` body field (default: registry default).
- Second industry pack: `industries/construction-mep/` (registry key `construction-mep-contractor`), mechanically adapted from `agency-os/docs/Water_Electrical_MEP_ALL_LATEST_2026-09-03/Water_Electrical_MEP_Foundry_Delivery_v1.1` by `scripts/adapt_mep_industry_pack.py` (re-run after any source-pack change; do not hand-edit outputs). 66 capabilities (`MEP-CAP-*`, prefix kept, no collision with `CAP-`/`DER-`/`FOUND-`), 61 questions, 23 generation modules (16 from capability `module` tags + 6 introduced only via `module-rules.json` + `core`).
- Schema reconciliation: MEP's own `module` tag kept verbatim as the generation-module id (no capability remapping); `phase` kept as an additional, unread field (not dropped); `derivation-rules.json`/`conflict-rules.json` are genuinely empty (MEP source has no DER-* / cross-question-conflict concept -- `MEP-CAP-OFFLINE`'s dependency on `MEP-CAP-RWD-WEB` is already a `requires` edge); `baselines/production-baseline.json` has an empty `capabilities` list (MEP source defines no foundation/baseline layer).
- Module-level (not unit-level) blueprint content wiring for `dispatch`/`project`/`workforce`/`identity_authorization`/`notification`/`audit_observability`, mechanically extracted (`scripts/adapt_mep_industry_pack.py`) from the source pack's own module READMEs, `dispatch/state-machine.json`, `06_DISPATCH_STATE_MACHINE.md`, and `dispatch(-acknowledgement).schema.json` -- real content (state machine, invariants, JSON Schema contracts), not placeholders.
- `tests/test_industries.py` (8 tests): registry shape, unknown-industry rejection, commerce plan identical with/without explicit `industry='commerce'`, commerce golden ALL-NO/ALL-YES fixtures still reproduce exactly, MEP resolves in isolation with zero selections, `MEP-CAP-DISPATCH` closure/module-trace correctness, `MEP-CAP-DISPATCH` generates real traceable `BLUEPRINT_ARCHITECTURE.md` content through the actual engine, and every one of the 66 adapted MEP capabilities' `requires` chain closes without error.
