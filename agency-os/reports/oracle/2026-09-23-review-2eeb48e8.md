Do not ship yet: the plan still exposes ad-hoc Trigger deploy instructions, and step 10d can publish the token to Trigger before next-admin is actually updated if the compose patch fails or is interrupted.

Findings:
- [medium] Active task reference still permits a token-less Trigger deploy (lobster-factory/infra/trigger/TASK_REFERENCE.md:327-366)
  The claimed single entry point is not enforced: the active `TASK_REFERENCE.md` still instructs operators to export selected variables and run `npx trigger.dev@4.4.6 deploy` directly. That path does not read `/root/lobster-phase1/.env` and can deploy `site-watch-heartbeat` without `SITE_WATCH_INGEST_TOKEN`; the heartbeat then returns `{configured:false}` and silently does no monitoring. This is especially dangerous on a fresh project or after a failed/incomplete rollout where the token was never synced. Remove or explicitly retire this deploy section and make the agent/command route invoke the canonical script only.
  Recommendation: Replace the direct CLI deployment instructions with `scripts/lobster-trigger-deploy.ps1`, or add a mandatory preflight that reads and verifies `SITE_WATCH_INGEST_TOKEN` before allowing deployment.
- [medium] Step 10d is not atomic across `.env` and next-admin (agency-os/docs/operations/SITE_WATCH_MASTER_PLAN.md:197-198)
  Step 10d writes `SITE_WATCH_INGEST_TOKEN` to the VPS `.env` before invoking `safe-infra-patch.sh` to update/recreate next-admin. If the patch, health gate, or operator session fails after the `.env` write, the host retains the token while next-admin may still have no token. A later workflow push can invoke the post-push deploy hook, which reads that token and syncs it to Trigger; the heartbeat then runs against an unauthenticated next-admin endpoint and produces repeated 401 failures. The documented ordering therefore still has the exact partial-failure window it is intended to eliminate.
  Recommendation: Make 10d transactional: verify the next-admin container has the token before permitting Trigger deployment, and on compose-patch/health failure remove or quarantine the newly written token; alternatively have the canonical deploy script refuse to sync the token unless the host-side next-admin `printenv` check passes.
