# Codex Adversarial Review

Target: branch diff against 7b532056b
Verdict: needs-attention

No-ship: this diff marks major security decisions as resolved, but two of the new controls are still unenforceable prose and one newly-added dependency is internally inconsistent with the selected attestation path.

Findings:
- [high] SPIFFE deferral guardrail is not actually encoded in the policy (agency-os/docs/AI_LEGO_Cognitive_Engineering_OS/policies/security/zero-trust.policy.yaml:123-138)
  `zero_trust_decision_schema` requires `spiffe_reconsideration_triggers`, but this schema only enforces a non-empty array of arbitrary strings. Earlier in the same policy, the change explicitly says these triggers must be concrete and checkable; in practice, the only concrete examples live in fixtures, not in the source-of-truth policy. That means any free-text placeholder will validate, so the supposed gate preventing indefinite SPIFFE deferral can silently rot. One of the fixture triggers also depends on threshold `N`, which is not defined anywhere else in the repo.
  Recommendation: Encode the trigger set in the policy itself instead of allowing free-form strings, and define any numeric threshold such as `N` in-repo so validation can fail when the deferral criteria are missing or weakened.
- [high] EPSS re-scan requirement is still only prose, not an actionable schedule (agency-os/docs/AI_LEGO_Cognitive_Engineering_OS/policies/security/supply-chain-security.policy.yaml:176-181)
  The new supply-chain policy claims risk 8 is resolved by requiring a scheduled re-scan of already-approved artifacts, but the policy only stores that as a constant sentence. There is no machine-readable interval, cron, owner, or workflow reference anywhere else in the repo to make the scan happen. As written, future implementations can satisfy the policy without ever running a re-scan, so approved artifacts can become newly risky over time with no control actually firing.
  Recommendation: Replace the prose-only cadence with a concrete schedule/trigger and responsible executor, or keep the gap/risk open until that external scheduling dependency is defined in the repo.
- [medium] The new risk model ties CI signing to the wrong identity decision (agency-os/docs/AI_LEGO_Cognitive_Engineering_OS/.ai/research/phase-1/RISK_REGISTER.yaml:30-38)
  This risk entry says the keyless signing path depends on resolving `zero-trust.policy.yaml`'s `idp_provider`, but the same diff selects GitHub Artifact Attestations on GitHub-hosted runners as the immediate attestation path. Those are different trust domains: the application/customer IdP choice should not be the gate for CI provenance on GitHub-hosted runners. Keeping this dependency in the risk register can either block supply-chain hardening on an unrelated vendor decision or push implementation toward coupling CI signing to the app IdP, widening the blast radius across trust boundaries.
  Recommendation: Model CI signing identity separately from the application IdP decision, and move any real attestation dependency to the supply-chain policy/ADR using the actual CI trust root or OIDC issuer.

Next steps:
- Tighten `zero-trust.policy.yaml` so SPIFFE reconsideration triggers are enumerated or otherwise machine-checkable, with any threshold values defined in-repo.
- Make the approved-artifact re-scan control executable by adding a concrete schedule/owner or reopen the gap until that dependency exists.
- Correct the risk/dependency model so CI attestation is not blocked on the application `idp_provider` decision.
