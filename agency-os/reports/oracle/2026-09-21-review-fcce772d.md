Do not ship the plan yet. The revised invariants still leave a concrete recovery/notification race, and the daily cursor silently drops missed windows after multi-day heartbeat outages.

Findings:
- [high] Pending alert can be sent after recovery has already suppressed the episode (agency-os/handoffs/2026-09-21-site-watch-plan.md:58-63)
  C8 treats `alert_state='pending'` as suppressible when a success arrives, resolving/clearing the episode and requiring zero alert messages. However, sending Telegram is an external side effect performed before the fenced `alert_state='sent'` write. A concurrent or stale task can pass the pending check, send after the recovery path clears/resolves the episode, and then have its state write rejected by the lease fence. The result is a user-visible alert for an episode the contract says must produce zero messages; I1 fences database writes but cannot fence an already-started Telegram send. Add an atomic notification-claim/state with an episode-generation check that recovery invalidates, and define behavior for sends already in flight (or serialize recovery and notification through a durable outbox/claim protocol).
  Recommendation: Specify and implement a durable send claim tied to episode_id/lease_gen, with recovery atomically invalidating pending claims; do not rely on the post-send fenced update to suppress an external send.
- [medium] Daily cursor drops all but the newest missed 24-hour windows (agency-os/handoffs/2026-09-21-site-watch-plan.md:52)
  C2 stores only `last_completed_run_key` and considers the target due when the current bucket differs from that single value. If the hourly heartbeat is unavailable for multiple daily boundaries, the next heartbeat sees only the newest bucket, runs once, and advances the cursor directly to it; intermediate 24-hour buckets are never represented or executed. Therefore the formula does not provide exactly one run per elapsed 24-hour window under prolonged outage, despite the catch-up wording. The plan must explicitly choose at-most-one-current-window semantics or track/iterate a durable due bucket (and define the bounded catch-up policy).
  Recommendation: Define the missed-window contract explicitly; if every window must run, calculate the next bucket after last_completed_run_key and process buckets sequentially with an outage/backlog cap.
