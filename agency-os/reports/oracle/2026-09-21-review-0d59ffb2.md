- [high] Daily frequency is not deduplicated by the proposed run key (agency-os/handoffs/2026-09-21-site-watch-plan.md:50)
  C2 defines the run key as `sw-<org8>-<UTC YYYYMMDDHH 桶>` for every frequency. A daily target therefore gets a new key every hour; C3's lease only prevents concurrent execution and does not enforce once-per-day semantics. A heartbeat can run the same daily URL repeatedly throughout the day, producing duplicate results, comparisons, and failures. Define frequency-aware due/uniqueness semantics (for example a UTC-day key for daily, with a database uniqueness constraint) before implementation.
  Recommendation: Specify and enforce a frequency-specific idempotency key and database uniqueness rule, then add an acceptance test covering multiple heartbeats during one UTC day.
- [high] Lease expiry duration is unspecified, so retries can duplicate or suppress work (agency-os/handoffs/2026-09-21-site-watch-plan.md:51)
  C3 requires `lease_until` and a conditional UPDATE but never defines how long the lease lasts, how it is renewed, or how a crashed Trigger task is recovered. If the lease is shorter than the task/retry window, concurrent heartbeats can both run a page; if it is too long, a crash can suppress the target until an arbitrary delay. The existing route timeout cited in C4 does not establish a lease policy for the new Trigger task.
  Recommendation: Define lease duration, renewal, crash recovery, and the relationship to Trigger.dev retry/backoff; test a crash and overlapping heartbeat scenario.
- [high] The notification contract does not guarantee one alert per incident (agency-os/handoffs/2026-09-21-site-watch-plan.md:56)
  C8 says failures at `failure_streak >=2` open an incident and gives a fingerprint, but it does not require an atomic open-if-absent operation, a unique constraint, or a persisted notification state. A retry or later heartbeat after the threshold can dispatch another `new` event for the same fingerprint, violating the acceptance case of exactly one Telegram for two failures. The plan also does not define whether a resolve is emitted only when an incident was actually open.
  Recommendation: Specify incident state transitions and idempotency explicitly: atomically create one open incident per fingerprint, record notification delivery state, make retries safe, and emit resolve only for an existing open incident.
