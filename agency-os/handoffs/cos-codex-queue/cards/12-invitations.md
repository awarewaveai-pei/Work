# Card 12 — invitations: the only way into a group (foundation F3, AUTH: review debt needs two reviewers)

## Decision
Required reading: `STEP34_SHARED_RULES.md` §4. No open signup exists or is built. A person joins a group only by a one-time link a member copies and sends themselves. This touches authentication: write it the slow, boring way.

## Constraints
- Reuse, do not copy: the one-time-token pattern of `password_reset_token` and `handoff_code` in `COS/ai_lego/platform/identity/store.py` (read both; token hashed with sha256, constant-time comparison, single use inside the same transaction that changes state). Accepting for a visitor creates the identity through the EXISTING `IdentityStore.create_identity` (password rules unchanged) in the SAME transaction as marking the invite used and adding the member. Same tenant only.
- Token: `secrets.token_urlsafe(32)`, only `sha256` stored, shown once in the create response, never logged, never in an error message. Expiry 7 days, single use, revocable by the inviter or a convener, at most 25 open invitations per group, at most 10 created per identity per 24 hours. Those three limits live in a ruleset (`platform/rulesets/govern.py`, a new versioned `Ruleset("govern.invites", ...)` with the HISTORY fingerprint mechanism: read `platform/rulesets/__init__.py`), not as constants in the route.
- Who may invite: a convener always; a facilitator for `class` and `workshop` groups; a participant never (state it in a docstring and test it).
- Routes in `apps/api/blocks/groups.py` (card 10's router): `POST /groups/{id}/invites` (role defaults to participant), `GET /groups/{id}/invites` (convener: open ones, never the token), `DELETE /groups/{id}/invites/{invite_id}`, `POST /invites/accept` (body: token; logged-in same-tenant identity joins; a visitor sends email, display name, password and creates the identity). Every refusal of `accept` (unknown, used, expired, revoked, wrong tenant, group closed or erased) returns ONE identical 404 body; timing: do the same work path (hash + lookup) for all.
- Account flooding rule (§4): store `invited_by` on the identity (migration `0003_identity_invited_by.py`); more than 5 identities accepted from one inviter's invitations inside 24 hours are marked `pending_review`; they cannot read other members' records (card 11 already honours the state) and are excluded from card 21's agreement; the convener clears each in a route `POST /groups/{id}/members/{identity_id}/confirm`. Deterministic, no model, no real-name check. The held state is written in plain Chinese to the convener and to the held person.
- Never put a token or its hash in a URL query, a log line, an exception text or a test failure message.

## Acceptance
`tests/unit/test_group_invites.py`: single use (second accept 404); expiry (freeze time); revoked; wrong tenant; closed group; a participant cannot create one; the token is absent from list responses and from every response except the create response; the stored value is not the token; an identical body and status for all refusals; the visitor path creates the identity and the membership atomically (inject a failure after `create_identity`: nothing exists afterwards, the invite is unused); limits (26th open invite refused, 11th in a day refused) read from the ruleset; the ruleset change without a new version fails the existing HISTORY test; flooding: 6 accepts from one inviter in 24 hours -> the 6th is `pending_review`, cannot read others' records, is excluded from the member list used by agreement, confirm clears it; a tenant A identity cannot accept a tenant B token. Mutations to report: store the raw token -> red; skip the same-transaction marking -> red; different 404 body for expired -> red; remove the participant check -> red; remove the pending_review rule -> red; compare tokens with `==` instead of the constant-time call -> a source-scan test red (add one).
