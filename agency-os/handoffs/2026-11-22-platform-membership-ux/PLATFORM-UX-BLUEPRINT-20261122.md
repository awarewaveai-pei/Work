### 最終十點

1. **首頁**：在 WordPress，開放註冊時做，規格已定（§3）。會員從 aware-wave.com「我的帳號」就能看到自己的產品與點數、按一下進入（§2A）。
2. **工具怎麼分類展示**：用「功能分類＋使用情境＋想完成的任務」三個維度，登記表新增 `catalog` 欄位（§4.3）；現在 11 產品用卡片網格，100／300 個時只換一個容器（`ToolGrid`→`FacetedList`），卡片與搜尋不重做（§4.7）。
3. **登入會員看到什麼**：「我的工作台」＝已開通的產品在最上面，旁邊是點數與合約；沒開通的收成一組在下面。
4. **最快找到自己的工具**：登入後第一屏就是自己的產品，不必再搜尋；「開啟」一鍵進產品。
5. **訂閱與點數放哪**：頂列常駐一個「點數 N」；完整內容在「點數與合約」一頁；儲值與付款一律回 aware-wave.com（WordPress 收錢）。
6. **操作頁怎麼排**：同一個外框；左欄只放這個產品的頁面，不再放不能點的「功能」清單；付費按鈕上直接寫狀態與預估點數。
7. **導覽**：頂列（搜尋、點數、帳號）＋左欄（本產品頁面；員工再加客戶欄）＋手機底列。app 與每個產品子網域共用。
8. **最該先做**：外框合併＋客戶欄（接 K4/K5）、權益詞表單一來源、工作台改版、內容入口重排。
9. **核心原則**：一個外框；一個詞對一種權益；員工與會員看同一套頁面，差別只在「目前客戶」；狀態要看得見也要有下一步按鈕。
10. **為什麼適合**：三扇門、`can()`、`heldDoors`、`OrgPicker` 都已存在，這份藍圖多半是合併與改名，不是新蓋（§17.4 列出刪併清單）。

## 1. 核心策略（§2 第 1 項）與六根骨架

**策略：一個外框、一個權益詞表、一個「目前客戶」。** 會員與員工看同一套頁面；會員的「目前客戶」永遠是自己的單位（單位固定，現況報告 §4），員工的「目前客戶」由客戶欄決定。

本平台特有的六點就是骨架，每一章都套用：

| 骨架 | 落在哪 |
|---|---|
| ① 三種使用者：訪客／會員（單位＋被授權的人）／員工替客戶操作 | §2 矩陣、§6、§9 |
| ② 以客戶 vs 以功能：兩個入口分開、共用元件 | §9.2 |
| ③ 單位與人：付費的是單位，管理者與被授權的人看到的不同 | §7.3、§8 |
| ④ 身分三層（角色／方式／產品） | 客戶欄類別 §9.3 |
| ⑤ 多網域：同一外框、主機由伺服器算，不寫死網域 | §9.4、CLIENT-CONTEXT-PLAN 3a／3c |
| ⑥ 每個功能分開買或贈送 | §7、§8（權益逐功能顯示） |

## 2A. 會員從 aware-wave.com 登入後，怎麼進到工具（外掛怎麼包）

**一句話**：WordPress 只做登入、付款、看摘要、按「進入」。摘要由 app 算好，外掛只負責畫；完整工作台與所有工具留在 app 與各產品子網域，**不嵌進 WordPress**（iframe 會被瀏覽器擋登入狀態，ADR 018 `:70`；也不共用 cookie，`:71`）。

```
 aware-wave.com（WordPress＋我們的店外掛 aware-wave-store）
 ┌────────────────────────────────────────────────────┐
 │ 我的帳號（WooCommerce 原本的）：訂單、付款方式、email │
 │ ┌ 我的 AwareWave 產品（外掛畫，內容由 app 給）────┐ │
 │ │ 單位：Soulful Expression      點數 1,240        │ │
 │ │ 內容行銷  方案內 9｜扣點 4        [進入]        │ │
 │ │ 社群發文  試用中，到 12/01        [進入]        │ │
 │ │ 影片製作  未開通                  [了解]        │ │
 │ │ [進入我的工作台]                                │ │
 │ └─────────────────────────────────────────────────┘ │
 └────────┬─────────────────────────────┬─────────────┘
 ①畫面載入時               ②按「進入」時
 外掛→app 讀摘要           外掛→app 換一次性連結
 （伺服器對伺服器、簽章、   （既有 POST /api/auth/wp-handoff）
  快取 60 秒）                         │
          ▼                            ▼
   app（next-admin）：算「持有哪些產品、各功能狀態、點數」
                                       │ 瀏覽器被送到
                    portal 工作台 或 <產品>.aware-wave.com（不用第二組密碼）
```

### 2A.1 唯一做法與取捨

| 選項 | 內容 | 結論 |
|---|---|---|
| A 只放「進入我的工作區」一顆按鈕 | 最省，但會員在 WordPress 看不到自己有什麼、點數多少 | 不選：與操作者「登入後就看到自己可用的產品」不符 |
| **B 外掛畫「我的產品」摘要，內容由 app 以簽章讀取（選這個）** | WordPress 的「我的帳號」直接顯示與工作台同一份清單與點數；每列一顆「進入」；另有「進入我的工作台」 | **選**：判斷全在 app（`heldDoors`＋`RightBadge`），外掛只畫，沒有第二份真相 |
| C 在 WordPress 重做整個工作台 | 要在 PHP 複製權益判斷、功能清單、點數紀錄 | 不選：兩份邏輯一定漂移；WordPress 讀不到權益 |
| D 把產品或工作台 iframe 進 WordPress | — | 排除（ADR 018 `:70`） |

B 的代價：①「我的帳號」多一個對 app 的依賴（讀不到就用退場畫面，§2A.4）；②畫面最多落後 60 秒（快取）；③app 要新增一支簽章讀取路由（High，與 `wp-handoff` 同一個攻擊面）；④外掛現在停用、密鑰已刪（G8），要先重開才跑得動。

| 按鈕掛在 WooCommerce「我的帳號」首頁 | `aware-wave-store-plugin/includes/MyAccountDoors.php:105`（`woocommerce_account_dashboard`） |
| 畫面＝「我的 AwareWave 產品」＋第一顆「我的工作區」＋每個買過的產品一顆「進入」 | `MyAccountDoors.php:133-142`、`doors()` `:42-45` |
| 按下後外掛伺服器簽章呼叫 `POST /api/auth/wp-handoff`，拿一次性連結送瀏覽器 | `MyAccountDoors.php:5-8,159-164` |
| **缺口**：按鈕清單來自 WooCommerce 訂單（`heldProducts()`），不是 app 權益 | `MyAccountDoors.php:109-121` |
| 後果：贈送、員工建立的合約、代操客戶（例 Soulful）持有的產品沒有按鈕，只有「我的工作區」；能不能進由 app 判定（403 `product_not_held`） | `MyAccountDoors.php:5-8` 註解；現況報告 §2 |
| 未驗證 email 不列按鈕 | `MyAccountDoors.php:129-132` |
| 外掛正式站停用、兩把密鑰已刪、`seller_sites` disabled | 現況報告 §2 開關表 |

這個缺口應記為 **ADR 021 新缺口 G13**：「進入」清單來自訂單而非權益。

### 2A.3 外掛畫什麼、app 留什麼

| 在 WordPress（外掛畫） | 在 app（portal／產品子網域） |
|---|---|
| 單位名稱、點數餘額（唯讀） | 完整點數與合約、使用紀錄（`/wallet`） |
| 每個產品一列：名稱、權益標籤（方案內／贈送／扣點／試用／未開通）、「進入」或「了解」 | 每個功能的權益標籤、功能清單（`我的工具`） |
| 「進入我的工作台」 | 工作台、繼續上次、最近、收藏 |
| 儲值／續約連結（WooCommerce 商品頁） | 成員授權（被授權的人不是 WordPress 會員，ADR 021 D2） |
| 讀不到時的退場畫面 | 所有工具操作頁（各產品子網域） |

文案與標籤文字**全部由 app 在 JSON 裡給**，PHP 裡不放第二份字典（對應 §8 的 `RightBadge`）。

### 2A.4 外掛要做的事（工程契約）

**新路由（app）**：`POST <app>/api/auth/wp-summary`，驗簽方式與 `wp-handoff` 完全相同（同一把登入鑰匙、`ts` ±60 秒、nonce、email 已驗證才回，`lib/auth/sources/awarewave-wp.ts:63-88`）。

- 請求：`{wp_user_id, ts, nonce, key_id?}`。
- 回應：`{ok:true, unit:{name}, wallet:{balance, frozen}, products:[{key, name, right:{kind:"contract|comp|credits|trial|none", label, until?, counts:{covered,gift,credits,locked}}, can_enter}], fetched_at}`。
- 錯誤：`not_a_member`（404，WordPress 顯示「尚未連結，請聯絡我們」）、`email_unverified`、`source_disabled`、`unavailable`。
- 計算：持有判斷用 `heldDoors`（`lib/portal/held-doors.ts`），權益標籤用 §8 的 `RightBadge` 純函式，餘額用 `createEntitlementStore().getCreditBalance`。不新增判斷。

**外掛**：
1. `Summary` 用戶端：簽章 POST、逾時 2 秒、成功後存 transient 60 秒（鍵＝WordPress 使用者 id；與門的持有快取 60 秒一致，`lib/portal/door-access.ts:13`）；外掛自己送出付款事件時（`PaymentSender`）立刻清掉該會員的快取。
2. `MyAccountDoors::render()`：清單改讀 `Summary`，刪除訂單版 `heldProducts()` 對 aware-wave.com 會員的使用（經銷站分支保留到摘要支援 `key_id`）。
3. `MyAccountDoors::handle()`：驗證「這顆按鈕是否在清單內」改對 `Summary`（不信任表單送來的 key）；伺服器端最終仍由 app 判定。
4. 退場畫面：app 逾時或 5xx →「暫時讀不到你的產品清單。」＋「進入我的工作台」＋「重新整理」；**不回頭用訂單清單**（會顯示錯的東西）。
5. 手機：用 class 與一小段 CSS 取代現有行內樣式（`MyAccountDoors.php:133,136`），按鈕高度 ≥ 44px。

## 3. 訪客與公開面（§2 第 3 項；**開放註冊時做**，現在先定規格避免日後重工）

前提（事實）：公開首頁、商品頁在 aware-wave.com 的 WordPress；註冊兩邊都關著；沒有真錢付款（現況報告 §0、§5）。所有工具要登入，沒有免費不登入的工具（只有 social 的 `/smartlink`，`products.ts:48`）。文案正式版走既有流程（操作者慣例：文案由 GPT 撰寫、看渲染結果），以下文案是**示意**。

### 3.0 資料從哪來（WordPress 不另維護工具清單）
工具清單、分類、一句話、圖示、任務、新上架**只存在產品登記表**（`lib/portal/products.ts`，新增欄位見 §4.3）。WordPress 頁面是模板，內容由登記表輸出：

| 做法 | 說明 | 取捨 |
|---|---|---|
| **推（建議）** | `scripts/export-catalog.mjs` 把登記表輸出成 `catalog.json`（只含公開欄位），部署時經既有簽章通道 wp-bridge 推到 WordPress；WordPress 以自訂文章類型 `aw_tool` 存，頁面模板讀它 | 沒有新增匿名 API；先例：ADR 017 §0b 第 7 條的 `sync-foundry-catalog.mjs`＋測試 diff（`ADR 017 :54`） |
| 拉 | WordPress 外掛每小時從 app 的靜態 `catalog.json` 讀 | 要新增一個免登入的靜態路徑與 nginx 規則（走 `safe-infra-patch.sh`） |
| 手寫 | 11 個產品手寫在 WordPress | 現在可行；之後與登記表必漂移，只作 Phase 2 過渡 |

測試：`catalog.json` 必須等於登記表重新輸出的結果（同 ADR 017 第 7 條的 diff 閘）。價格不輸出：價格只在 WooCommerce（ADR 017 §2 `:70`）；頁面上的「價格」區塊是 WooCommerce 商品的短碼。【假設 A13：wp-bridge 可推內容；實作前請 `wordpress-plugin-expert` 確認】

### 3.1 訪客首頁

| 順序 | 區塊 | 內容（示意） | 為什麼 |

| 1（首屏） | 一句話價值主張＋副標 | 「一個帳號，做完內容、影片、社群、客服」；副標寫給誰、能完成什麼 | 3–5 秒要知道「這是什麼、能幫我做什麼」 |

## 4. 為數百個工具設計：分類、搜尋、量級（§2 第 4 項）

### 4.1 「工具」是哪一層（先定義，避免日後重工）

| 層 | 登記表位置 | 現在的量 | 可否分開買 |
|---|---|---|---|
| 產品 | `PRODUCTS[]`（`products.ts:41-100`） | 11 | 是（門） |
| 功能 | `features[]`（`ProductFeature`，`products.ts:15-21`） | next-admin 49＋認知平台 300 | **是**（權利列逐功能，ADR 017 §3） |
| 頁面 | `door.nav`（`DoorNavItem`，`products.ts:11`） | 約 30 | 否 |

**卡片的單位＝使用者要「選一個去用」的那一層**：量少時＝產品；某產品的功能破百時，該產品內＝功能。其他層永遠是屬性或子項。這讓同一個 `ToolCard`（§5）可在任何量級使用。

### 4.2 三個維度（同時支援）

| 維度 | 回答 | 例（真實產品／功能） | 型別 |
|---|---|---|---|
| 功能分類 `category` | 這屬於哪一類東西 | 內容行銷＝內容；塔羅製圖＝設計；行銷開發信＝銷售開發 | 單選、封閉清單（≤ 12） |
| 使用情境 `contexts` | 在什麼場合、給誰用 | 電商、工作室、顧問、教育、創作者 | 多選、封閉清單（選填） |
| 想完成的任務 `tasks` | 我想做什麼（動詞＋對象） | 寫 SEO 文章、排社群貼文、做短影片、做商品圖、回客服問題、找潛在客戶 | 多選、詞表 key（≥ 1） |

一個工具＝1 個分類＋N 個任務＋（選填）N 個情境。任務是對外最重要的維度（人們不知道產品名，但知道要做什麼）；分類給「逛」；情境給「對號入座」。

### 4.3 產品登記表要新增的欄位（可開卡）

放在新檔 `lib/portal/catalog-vocab.ts`（詞表）與 `products.ts`（每列填值）。**不新增** `isNew`（由 `addedAt` 推算，一個事實一處）、**不放價格**（價格只在 WooCommerce，ADR 017 §2 `:70`）。

```ts
// lib/portal/catalog-vocab.ts（新增）
export const CATEGORIES = ["content","design","video","social","service","sales","research","insight"] as const;
export type CatalogCategory = (typeof CATEGORIES)[number];
export const CONTEXTS = ["ecommerce","studio","consulting","education","creator","general"] as const;
export type CatalogContext = (typeof CONTEXTS)[number];
export const TASKS: Readonly<Record<string, { name: string; synonyms: readonly string[] }>> = { /* 詞表：key → 顯示名＋同義詞 */ };
export const ICONS = [/* 封閉清單；不放 emoji、不放色碼 */] as const;

// products.ts（新增）
export interface CatalogMeta {
  category: CatalogCategory;          // 必填
  tasks: readonly string[];           // 必填 ≥1，值必須在 TASKS
  blurb: string;                      // 必填，一句話，≤ 28 個全形字
  icon: (typeof ICONS)[number];       // 必填
  addedAt: string;                    // 必填 YYYY-MM-DD；「新上架」＝距今 ≤ 60 天（衍生）
  contexts?: readonly CatalogContext[];   // 選填
  keywords?: readonly string[];       // 選填，搜尋同義詞，繁中／英文各自 ≤ 8
  featured?: number;                  // 選填，精選排序（1 最前），營運手動
  intro?: string;                     // 選填，aware-wave.com 介紹頁的 slug
}
// ProductDefinition 加：  catalog: CatalogMeta;
// ProductFeature 加：     catalog?: Partial<Pick<CatalogMeta, "tasks"|"blurb"|"keywords"|"icon"|"addedAt">>;  // 缺的欄位繼承產品；category 永遠繼承產品
```

| 欄位 | 必填 | 誰用 |
|---|---|---|
| `category` | 產品必填 | 分類頁、篩選鈕、客戶端 facet |
| `tasks` | 必填 | 「我想…」入口、搜尋、分類頁 |
| `blurb` | 必填 | 卡片、搜尋結果、介紹頁 |
| `icon` | 必填 | 卡片、左欄、搜尋結果 |
| `addedAt` | 必填 | 「新上架」徽章、排序 |
| `contexts`、`keywords`、`featured`、`intro` | 選填 | 情境篩選、搜尋、首頁精選、WordPress 連結 |

## 6. 登入後首頁（§2 第 6 項）：現有 launcher 的去留

**答案：付費會員登入後先看「我的工作台」（自己的產品），不是 Dashboard 圖表，也不是全部工具。** 原因：操作者原則「登入後不該再重新找已付費的工具」；而且目前 11 個產品全標 `coming_soon`、會員實際只持有 1–2 個，全部工具會把 9 個用不到的擺在前面。

**launcher 去留：留在 portal 子網域、路徑 `/launcher` 不變、改名「我的工作台」。** 理由：登入 cookie 每個網址各一份、不跨子網域（ADR 018 `:46`、`lib/supabase/auth-cookie-options.ts:4`），完整工作台必須讀會員的權益，只能在 app 側。WordPress「我的帳號」不自己判斷權益，但由外掛畫出**同一份**「我的產品＋點數」摘要（資料由 app 簽章提供），每列一顆「進入」（現有外掛 `includes/MyAccountDoors.php:133-142`，目前停用，G8；做法與取捨見 §2A）。

### 8.1 操作前與操作後
- 操作前：扣點按鈕上直接寫預估（「生成 · 約 12 點」），不跳確認窗；預估 ≥ 50 點或批次（多張、多段）才跳一次確認，內容＝「約 {N} 點，你有 {M} 點。確定嗎？」（門檻為假設 A5）。
- 失敗：整個沒產出＝全額退回，「這次沒有產出，點數已退回」（`Hold.settle(0)`、卡住的保留 2 小時後自動退，`can.ts:111-113`、`ledger.ts` 的 `HOLD_EXPIRY`）。部分完成：「已完成 3 張，扣 18 點；2 張失敗，已退回 12 點」。錢包不夠付已產出的結果：「結果已產出，但點數不夠付完整費用，已扣到 0（差 {N} 點）。請儲值後再繼續。」（`can.ts:177-181`）
- 金額：點數一律寫「點」並括號 NT$（1 點＝NT$1）。

## 12. 視覺方向（§2 第 12 項）：不另立色彩，只定版面與層級規則

外觀由 `app/globals.css` token 與 DB 主題決定（`tools/theme/THEME_ARCHITECTURE_APPEARANCE.md`）；這裡不新增色票。目標語氣：**現代、專業、簡潔、可信、久用不累、承載大量工具不亂**，用以下規則達成：

| 目標 | 規則 |
|---|---|
| 簡潔 | 一個畫面一個主要按鈕（`.btn-primary`），其餘 `.btn-secondary`；卡片內最多 3 層資訊（名稱、一句話、標籤＋按鈕） |
| 久用不累 | 內文 14px、行高 ≥ 1.5；對比 ≥ 4.5（§19.4 修正）；不用大面積飽和色塊；動畫只用 `transition .15s`（沿用 `globals.css:882-897`、`:1671-1685` 的 `transition`） |
| 可信 | 數字（點數、日期）用 `--font-family-mono` 或等寬數字；狀態一律「字＋形狀＋色」；金額一律 NT$ |
| 承載量大 | 密度三級（card／row／compact）；表格用 row；分組標題黏頂（sticky） |

### 可借鑑的模式（通用做法，附用處與限制）

| 模式 | 用在哪 | 不適合照搬的地方 |
