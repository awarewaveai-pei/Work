# 會議服務網路版 — 安裝手冊（待觸發，2026-08-20 建檔）

> **狀態：未開始。這份是規格書，不是已完成的功能。**
> 觸發方式：使用者說「網路版繼續」或等義詞，AI 讀本檔案依序執行，不用重述背景。
> 現況（本機版）：見 [`README.md`](README.md)，已上線可用，客戶端無 GPU 時無法直接安裝。

## 為什麼需要這份（觸發情境）

2026-08-20 確認客戶筆電**沒有 NVIDIA GPU**。CPU 路線比 GPU 慢 20-27 倍（README 實測數字，
60 分鐘會議 CPU 轉錄要 3.6 小時），等於不能用。網路版把運算搬到有 GPU 的伺服器，客戶端只需
瀏覽器。

## ⚠️ 動工前必須先拿到的三個答案（不是技術問題，是決策）

**這三題沒答案就不要開始寫程式**，寫了也是白工或方向錯:

1. **客戶是否同意錄音上傳到你的伺服器？**
   本機版的設計核心是「音檔不外流」（見 `README.md:3`）。網路版直接推翻這個前提——
   客戶的錄音會離開他的電腦，傳到你控制的伺服器。這是要客戶知情同意的事，不是你單方
   決定「反正比較方便」。**沒有客戶明確同意前不要上線。**
2. **GPU 伺服器要用哪個方案？**（決定成本與可行性，見下方「方案比較」）
3. **一台 GPU 伺服器要服務幾個客戶？**
   只服務這一個客戶 → 可以簡化（單一 job 佇列、不用真正的多租戶隔離）。
   未來要服務多個客戶 → 現在就要做帳號隔離、資料保留期限、per-tenant 儲存上限，
   不然是重工。**問使用者這題再動工。**

## 方案比較（GPU 伺服器要放哪）

| 方案 | 說明 | 成本 | 推薦度 |
|---|---|---|---|
| **A. 租雲端 GPU instance**（RunPod / Vast.ai / Lambda Labs） | 按小時計費，不用時可關機不計費；`faster-whisper large-v3` 建議 RTX 4090 級或以上（16GB+ VRAM，同時跑 whisper+pyannote） | 約 US$0.3–0.8/小時（依供應商與 GPU 型號浮動，**部署前務必重新查詢當時報價，不要用這裡的舊數字下結論**） | 推薦，起步成本最低、彈性最高 |
| B. 買一台常駐 GPU 伺服器（自己機房或 colo） | 一次性硬體成本高，但長期用量大時單位成本更低 | 硬體 + 電費 + 機房費，前期投入大 | 只有確定長期高用量才考慮 |
| C. 用操作者自己的遊戲筆電/桌機常開常連 | 零額外硬體成本 | 電費 + 你的機器要一直開機、網路要固定可達（動態 IP 需搭 DDNS 或 Cloudflare Tunnel） | 不推薦——你的機器關機/重開/睡眠客戶就斷線，不是給客戶用的穩定服務該有的樣子 |
| D. SG/EU 既有 VPS 加 GPU | AwareWave 現有兩台 VPS **都沒 GPU**（SG 4GB、EU CPX32 純 CPU，見 `README.md:7`），得整台換或另開一台 | 等同重新開一台，多一筆固定月租 | 只有計畫長期多客戶使用才考慮，且需另評估 Hetzner GPU 機型與月租 |

**目前建議方案 A**：先用一個客戶驗證整條鏈能不能動，成本最低、隨時可以砍掉重練或升級。
方案 B/D 是驗證過有穩定多客戶需求後才轉。

## 架構變動（相對於現有本機版）

現有本機版（`apps/meeting-service/`，見 `README.md` §架構）：
- `app.py` 只 bind `127.0.0.1`，單機單使用者，無認證
- 一次一個 job，背景 thread 跑 `pipeline.run_pipeline_phase1()`，狀態存本機 `jobs/<job_id>/status.json`
- 摘要階段人工回路（貼上）或本機 `.settings.json` 存單一 API key（`lib/settings.py`）
- 無使用者帳號概念，`jobs/` 沒有保留期限機制

網路版要動的地方：

| 項目 | 現況 | 網路版要改成 |
|---|---|---|
| 網路曝露 | `host="127.0.0.1"`（`app.py:157`） | 要嘛放在 reverse proxy（nginx + Let's Encrypt）後面走 HTTPS，要嘛用有內建 TLS 的雲端 GPU 平台自帶的 endpoint |
| 認證 | 無 | 至少要有簡單 token-based 認證（每個客戶一組上傳 token），**不可裸奔** |
| 併發 | 單一背景 thread，若同時兩人上傳會搶同一張 GPU 卡，記憶體可能爆 | 改成真正的 job 佇列（單一 worker process 依序處理，不是每個上傳各開一個 thread） |
| 儲存 | `jobs/<job_id>/` 永久留在本機磁碟，無清理機制 | 加保留期限（例如完成後 N 天自動刪除音檔+逐字稿），因為現在音檔在別人的伺服器上，長期留著是額外的資料外洩風險面 |
| API key | `lib/settings.py` 單一全域 key，存 `.settings.json` | 若多客戶共用一台伺服器，key 要嘛每客戶自己填（沿用現有設計，`GET/POST /api/settings` 加 tenant 維度）、要嘛操作者統一用一把 key 但要有用量上限（避免某個客戶把你的額度用爆） |
| Google Drive 同步 | `MEETING_DRIVE_BASE` 單一路徑（`lib/archive.py`） | 多租戶情境下要嘛關掉這功能、要嘛每租戶自己的目的地路徑，不能繼續寫死單一路徑 |
| `lib/` 底下的核心邏輯 | — | **幾乎不用動**——`transcribe.py`/`diarize.py`/`summarize.py`/`deck.py`/`excel.py`/`speaker_notes.py`/`minutes_md.py` 是純函式庫，跟本機/網路無關，原封不動搬過去（README 已預留這個假設，見 `README.md:16`） |

## 施工步驟（依序，每步都要驗證才進下一步）

### T1 — 選定並開通 GPU 伺服器（方案 A 為例）
1. 到 RunPod/Vast.ai 開一個帳號，選 RTX 4090 或以上機型的 pod
2. 裝 CUDA 驅動 + Python 3.12（多數 GPU 雲端範本已內建）
3. `git clone` 這個 repo 的 `apps/meeting-service/` 到伺服器
4. 照 `README.md` §安裝細節走一遍（CUDA torch、HuggingFace 3 個 gated repo、`requirements.txt`）
5. **驗證**：跑一次 `python -c "from lib.transcribe import pick_device; print(pick_device())"`，確認真的抓到 GPU 而不是靜默退回 CPU

### T2 — 加認證層
1. `app.py` 加一個簡單的 middleware 或 dependency，檢查 request header 帶的 token 是否在允許清單
2. token 存哪裡：沿用 `lib/settings.py` 的模式（本機檔案，不進版本控制），或用環境變數
3. **驗證**：沒帶 token 打 `/api/upload` 要回 401，帶對的 token 要能正常上傳

### T3 — 加反向代理 + HTTPS
1. nginx（或雲端平台內建的 HTTPS endpoint）擋在 `app.py` 前面
2. `app.py` 繼續只 bind `127.0.0.1`（不要直接對外開 uvicorn 的 port），對外只走 nginx 的 443
3. **驗證**：`curl -I https://<domain>/` 拿到合法憑證回應；直接打 uvicorn 的內部 port 從外部連不到

### T4 — 改成真正的 job 佇列
1. 現有 `threading.Thread` 每個上傳各開一條的模式（`app.py:79`）在單客戶低併發下堪用，但
   不能保證兩個人同時上傳不會搶 GPU——改成單一 worker loop 依序處理佇列（可以先用最簡單的
   檔案系統佇列：`jobs/` 目錄裡按建立時間排序，一個 worker process 每次只處理一個）
2. **驗證**：連續丟兩個上傳，觀察 GPU 記憶體用量與 log，確認不是同時兩個 whisper model 一起載入

### T5 — 加資料保留期限
1. 排程（cron 或簡單的背景迴圈）掃 `jobs/`，完成超過 N 天（先抓 7 天，跟客戶談好期限）的
   job 目錄，刪除音檔與逐字稿（PPT/Excel/md 這些已下載的產出可以留久一點或一起刪，看客戶要求）
2. **驗證**：手動把某個 job 目錄的建立時間改到 N+1 天前，跑一次清理腳本，確認被刪

### T6 — 客戶端測試
1. 找一台**沒有 GPU** 的機器（例如客戶那台筆電，或隨便一台一般筆電），瀏覽器連到網路版網址
2. 走一次完整流程：上傳 → 轉錄 → 講者分離 → 摘要（人工回路或 API 皆可）→ 下載 PPT/Excel
3. **驗證**：全程只用瀏覽器，客戶端沒有安裝任何 Python/CUDA 依賴

### T7 — 告知客戶並取得同意（回到最上面「動工前的三個答案」第 1 題）
上線前最後一步，不是形式——把「錄音會傳到伺服器」講清楚，等客戶明確說可以再正式提供網址。

## 已知風險 / 不要漏看

- **上傳頻寬**：客戶端上傳一份 60 分鐘會議錄音（估計數百 MB）靠客戶端的上傳頻寬，比本機版
  （檔案本來就在同一台機器，不用傳）慢——這是網路版的隱性成本，先設定合理的使用者期待。
- **GPU 費用失控**：方案 A 是按時計費，若佇列/worker 邏輯寫錯導致 GPU pod 一直開著沒關，
  帳單會爆——T4 做完後務必加一個「閒置 N 分鐘自動關機」的機制（多數雲端 GPU 平台有內建選項）。
- **`MAX_UPLOAD_MB = 500`**（`app.py:27`）在網路版可能要重新評估——客戶端網路較慢時，
  500MB 上傳可能逾時，也可能要考慮分段上傳，但這是進階優化，先不用在 T1-T7 做。
