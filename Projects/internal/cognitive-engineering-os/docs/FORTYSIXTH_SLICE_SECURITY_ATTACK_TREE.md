# Forty-sixth Method Atlas slice: `security.attack_tree`

Status: **LANDED (2026-09-06)**. THIRD member of the `security` family (F20), after `security.stride` (44th) and `security.linddun` (45th) -- the FIRST to structurally diverge from the two siblings' shared shape, and the first F20 `genuine_compute` method.

## What was built

Atlas gives this method three citations of its own -- the F20 tool table's Attack Tree row (L883: "root goal→AND/OR subgoals→cost/skill/detectability"); a dedicated §12.38 section (L3046-3062: a worked Mermaid AND/OR tree example); the §10 Security recipe row (L1112, shared with STRIDE/LINDDUN) -- plus §13.11 Security Review Recipe (L3472-3487), a §28 scenario-routing table row (L4483: Attack Tree as STRIDE's own recommended secondary method for security reviews), and a load-bearing sixth citation shared with both siblings: Execution Contract §32 (L1231-1260), which names Attack Tree as an acceptable method.

Atlas's own Attack Tree formula names a recursive goal TREE, not a DFD substrate -- unlike STRIDE's/LINDDUN's explicit "DFD→..." formulas. This record keeps `assets`/`trust_boundaries`/`entry_points` identically shaped to the two siblings (EC §32's framing fields genuinely are method-agnostic), but replaces the flat `threats[]` list with a genuine recursive `attack_node` tree: internal nodes (`name`/`node_type` in {AND,OR}/`children`) and leaf nodes (`name`/`cost`/`skill`/`detectability`/`control`/`residual_risk`/`test_evidence`, mapping EC §32's remaining triple onto the atomic, actually-controllable attacker technique). `root_aggregate` is this session's first F20 `genuine_compute` result: a real bottom-up AND/OR aggregation (AND: sum cost, worst-case skill/detectability; OR: cheapest cost, best-case skill/detectability, each attribute independently) implemented in a new compute module.

## Critic round: FAIL on first draft -- no logic bug, but claims that outran their own evidence

A `critic` subagent review (independent re-verification of every citation, hand-traced AND/OR semantics, 8 real mutations including one specifically targeting the "OR field-coupling" bug class) returned **FAIL**. The runtime was the strongest part: the aggregation algorithm is correct as specified, the field-coupling trap was already avoided AND already regression-guarded before the critic looked, and 8/8 mutations died on the exact named tests. Every finding was about claims outrunning their evidence:

1. **Major, fixed** -- the slice's own headline claim, "this closes `OQ-STRIDE-4`/`OQ-LINDDUN-4`", was a non-sequitur that settled a live design question backwards. `OQ-STRIDE-4`'s own literal text asks about the three EC §32 FRAMING fields (assets/trust_boundaries/entry_points); this contract keeps those THREE-FOR-THREE identically shaped across STRIDE/LINDDUN/Attack Tree -- that is evidence FOR eventually factoring them out, not a reason to declare "never, ever" as this contract's first draft did. Only `OQ-LINDDUN-4` (the DFD-substrate question) is genuinely closed by Attack Tree's real divergence. Corrected throughout the contract, schema, and module docstrings to separate the two questions.
2. **Major, fixed** -- `OQ-STRIDE-4` (`security.stride.contract.yaml`) and `OQ-LINDDUN-4` (`security.linddun.contract.yaml`) both still read as open in their own SSOT files while this contract declared them closed -- a split-brain. Added a `resolved_by` note to each, in the same commit, recording the actual finding without silently drifting out of sync.
3. **Major, fixed** -- `architecture.adr.contract.yaml`'s own "Threat Model has TWO machine_ids" claim (written during the STRIDE/LINDDUN slices) became stale the moment this slice shipped a third. This is the THIRD time this exact stale-neighbor-count class has recurred this session (44th slice: fixed a "no machine_id" claim; 45th slice: fixed "one machine_id" to "two"; 46th: "two" to "three") -- fixed in the same commit as this slice, not deferred.
4. **Major, fixed** -- the OR-aggregate result was described as identifying a single realisable "attack chain", but the code (correctly) minimizes cost/skill/detectability INDEPENDENTLY across children -- the cheapest child and the stealthiest child may be different children, making the result a per-attribute BOUND, not a chain. This was already true of the shipped code and already regression-guarded by a test (`test_or_does_not_mix_cheapest_cost_with_a_different_childs_skill`), but never disclosed in prose. Reworded throughout; added `OQ-ATTACKTREE-5` naming the real harder problem (joint/Pareto-efficient selection) this record does not solve.
5. **Major, fixed** -- both the contract ("recursively, to unbounded depth") and the gate's own docstring ("fails closed, not crashes") were falsified by a tree deeper than ~332 levels, which raised Python's own `RecursionError`. Added `MAX_TREE_DEPTH=100` (Atlas's own worked example is 3 levels; a real attack tree is shallow), threaded a `depth` parameter through the recursive validator, and added tests at exactly the boundary (legal) and far past it (refused, not crashed) -- at BOTH the construction and gate layers. **A second, more subtle bug surfaced by the fix's own test**: the error message for an invalid root still called Python's recursive `repr()` on the full, still-deeply-nested caller input to describe the failure, which itself raised `RecursionError` even after the validity check safely stopped recursing. Fixed with a `_shallow_describe()` helper that never recurses more than one level deep -- caught by running the very test written to prove the first fix, not by the critic (who did not specifically probe the error-message path).
6. **Major, fixed** -- the per-slice documentation deliverables (this file, the WORKLOG entry) were missing from the first draft, breaking the unbroken 45-slice chain.

Minor findings, fixed: `_is_nonnegative_number` accepted `cost=float('inf')` end-to-end (a bare `>= 0` comparison is `True` for infinity), making "cheapest path" meaningless and producing invalid RFC 8259 JSON -- added an explicit `math.isfinite()` check; the "Fault Tree grep found it named ONLY in the two method-inventory.yaml files" claim was inaccurate (missed a real prose mention in `docs/adr/ADR-002-...md:42`) -- corrected, conclusion (no typed object implements it) unaffected; "§13.9 places Threat Model directly before ADR" was false for §13.9 specifically (one step -- Data/Migration Review -- intervenes; only the F18 chain, L836-837, is direct) -- corrected.

Nits, fixed: the module docstring's "sum/min/max are commutative and associative" claim is not strictly true for general IEEE-754 floats -- corrected to cite the actual reason order-independence holds on this package's pinned Python >=3.12 runtime (Neumaier-compensated `sum()`), with a note that `math.fsum` would make the guarantee portable; "root branching via OR" was presented as if Atlas's own Mermaid diagram carried the label, when the diagram itself has no AND/OR edge labels at all -- corrected to disclose this as a sound inference from the surrounding prose, not a literal transcription.
