## Round 2 hardening (2026-09-03): what an independent adversarial review found and how it was closed

5 lens agents (correctness, security, spec-semantics, architecture/docs, test-quality) read the whole product root in full against the spec root and produced 47 findings; every one was fixed in this same round (not deferred). The headline classes, since they say more about the design than any individual line number:

- **Gate FAIL had no consequence.** The five gates were evaluated but nothing read their status — manifest, audit, step_status and the CLI exit code were literals. Fixed structurally: a FAIL now raises immediately, before the artifact is published or any result/manifest file is written. There is no longer a code path that can report PASS for a failing gate.
- **Two real crypto/timing bugs, not hypothetical.** (a) The restore-replay gate compared `destroyed_at` as raw ISO strings; a destruction half a second after an integer-second snapshot sorted *before* it lexicographically (`.` < `Z`) and was silently skipped, leaving a restored vault able to re-serve a crypto-shredded subject's plaintext. Fixed by comparing parsed instants (`parse_timestamp`), with a regression test that exercises exactly that boundary. (b) The vault persisted raw, unwrapped DEK material — the tenant KEK was decorative (`kek_ref`/`dek_wrapped` were write-only). Fixed: only wrapped DEKs are ever persisted; decrypt unwraps via the tenant KEK and checks `kek_ref` against the record before touching ciphertext.
- **The interactive review path could leak PII into the ledger.** It passed the raw transcript (not the PII-free `quote` field) as the code's quote, which the ledger then stored permanently. Fixed at the call site (only the source's own `quote` field is ever shown to a reviewer or written to an event) **and** structurally, with a ledger-wide `PiiLedgerGuard` that refuses any event payload containing a registered detected-PII value, for any subject, regardless of which code path produced it.
- **Several gates could not fail for the reason their contract names.** Citation quantified over sentence-provenance records instead of Claims (an uncited Claim passed); Authorship never checked the `locked` axis or validated Category/Theme/Claim provenance, only Code; Methodology compared a constant the producer always wrote the same way. All rewritten as real structural checks — the mutation tests in `tests/unit/test_gates.py` and the honesty checks in `tests/unit/test_key_vault.py` prove each one can now fail for its own stated reason.
- **The runtime-dir guard could delete an unrelated directory.** `--reset` defaulted to true and `shutil.rmtree`'d whatever path it was pointed at, with no ownership check. Fixed: every runtime directory this code creates is marked (`.ai-lego-runtime-marker`); a pre-existing, non-empty, unmarked directory is refused (`RUNTIME_DIR_NOT_OWNED`), never wiped.
- **Criterion 2 (rollback) and criterion 3 (locked fact survives) were not actually exercised** — no v12 ever ran, no competing AI suggestion ever arrived. Both are now real: a genuine over-merged v12 theme set is produced and rolled back with a golden-hash check; a real `AISuggestionProposed` event targets the locked code and the projection asserts it stays unchanged and the suggestion surfaces separately.

Full finding-by-finding detail lives in the round-2 review transcript (not committed — session-local); the fixes themselves are the durable record, verified by the 99 real, passing tests above plus 25 new/rewritten tests added specifically because a prior test could not fail for the property it claimed to check (`test_p2_deletion_unlinks_…`, `test_destruction_scope_honestly_reports_…`, `test_gate_failure_aborts_before_…`, `test_terminal_state_guard_actually_refuses_…`, `test_locked_fact_rewrite_is_refused_…`, `test_replay_compares_real_instants_…`, `test_envelope_encryption_is_real_not_decorative`, among others).

## Round 13 (2026-09-04): OQ-P5-10 decided by citation, not by matching either model — and a self-correction along the way

- Decision: round 11's axial category map merged `emotional_exhaustion` and `withdrawal_from_others` into one "depletion" category with no citation — an ad hoc call. Two independent grounds, neither read off what either eval model produced, say that was wrong: (1) the SLICE'S OWN precedent — `synthetic_fixtures.CATEGORY_OF_LABEL`, in place since round 8 and asserted by `GC-AX-001` — already keeps `emotional_exhaustion` as its own category, never merged with anything; (2) the Maslach Burnout Inventory (Maslach & Jackson 1981; Maslach, Schaufeli & Leiter 2001, *Annual Review of Psychology*) treats Emotional Exhaustion and Depersonalization — of which social withdrawal is a behavioural marker — as two distinct dimensions. `withdrawal_from_others` now gets its own category (`social_withdrawal`); `EVAL_CATEGORY_OF_LABEL` and its docstring carry the citations. `late_night_rumination` and `sleep_disruption` stay together under `night_intrusion`: the Perseverative Cognition Hypothesis (Brosschot, Gerin & Thayer 2006) and the Effort-Recovery Model's "unwinding failure" construct (Meijman & Mulder 1998) treat work rumination and disrupted sleep as one recovery-failure phenomenon — this is independent of, and does not reverse to match, `llama3.1:8b`'s round-11b split of that same pair (that FAIL stands as a real model finding, `GC-AX-003`).
- New assertion type `must_not_share_group` (mirrors `must_share_group`) makes the decided distinction a positive, checkable claim — the old "depletion" merge is not silently dropped, it is replaced by an explicit negative assertion (`eval_fixtures.EVAL_MUST_NOT_SHARE_PAIRS`). Dataset → 1.3.0 (`99efb4bc0fb8`).
- **Self-correction caught by the real run, not by re-reading the code**: the first attempt also raised `min_groups` (2 → 4 on `GC-AX-002`, 2 → 3 on `GC-AX-004`) to match what looked like "the fully correct 4-category structure." The real `gemma3:4b` run immediately falsified that as an assertion: the model correctly separated `withdrawal_from_others` (satisfying the new `must_not_share_group`) and correctly kept rumination+sleep together, but folded `emotional_exhaustion` into the boundary-erosion cluster rather than leaving it a singleton — a defensible axial-coding choice that simply uses fewer categories. The theoretical argument (MBI, perseverative cognition) supports the two PAIRWISE claims (share / not-share); it says nothing about how many categories a coder must produce, and category count is legitimate coder discretion. Raising `min_groups` was over-specification invented post-hoc, not part of the decision — reverted to the original loose "not one blob" floor (2) for both cases, `must_share_group`/`must_not_share_group` carry the actual invariant.

## Round 14 (2026-09-04): a definition locks as a DECISION, not a spec-root question after all

- Round 12 left one thing undone: "the definition is not part of the `HumanCodeLocked` event... whether a definition should itself be a `LOCKED_FACT` is a spec-root question." That framing was wrong on inspection, not right-but-deferred: the machinery already exists in `core/domain/provenance.py` — `EPISTEMIC_TYPES` already includes `DECISION`, `LOCK_REQUIRES` already maps `LOCKED_DECISION → DECISION` — applied to the spec-root Execution Contract by `.ai/proposals/022-locked-decision-definition-ec` on 2026-08-30, *before* round 12 was ever written. No spec-root proposal was needed; round 12 just hadn't checked whether the concept it wanted already existed before deferring it.
- The substantive question `LOCKED_FACT` would have gotten wrong: a definition is the reviewer's own analytic decision about what a label COVERS, not a claim about what is IN the source (that is what the code's own `SOURCE_FACT` lock already asserts, in the same review). `LOCKED_DECISION` / `epistemic_type: DECISION` is the correct pairing — `review.locked_definition_from_review` mirrors `locked_code_from_review` and returns `None` when the reviewer gave no definition or the review has no kept label (a REJECTed review never asks). A new ledger event, `CodebookDefinitionLocked`, fires whenever either review record (P1 or P2, whichever review typed a definition) carries one — independently of whether the underlying code ended up locked, edited, or accepted; a typed definition is always a decision, regardless of the code's own fate. `event_type` in `emit()` is a free string with no closed enum (`SecondCoderApplied`, `AxialCodingSuggested`, `SelectiveCodingSuggested` already establish this), so this follows an existing low-blast-radius pattern rather than creating a new one.
- Real run (`--transcription fixture --coding local-llm`, `gemma3:4b`): `all gates PASS`; ledger carries one `CodebookDefinitionLocked` (`definition_id: DEF-P2-001`, the fixture reviewer's own edited label, `provenance: {epistemic_type: DECISION, authorship_state: HUMAN_APPROVED, locked: LOCKED_DECISION}`) — the P1 label this run was the model's own novel suggestion, so `DEF-P1-001` correctly did not fire (same "only what the human authored" rule round 12 established for `reviewed_codebook_definitions`).
