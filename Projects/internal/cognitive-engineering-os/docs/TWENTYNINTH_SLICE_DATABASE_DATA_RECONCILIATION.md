## Critic round: two Criticals in a slice that "learned from" four prior rounds

This slice explicitly tried to apply every lesson from the four prior critic rounds this session (shared predicates, full recomputation, careful citation verification, mandatory duplicate-concept grep). A `critic` subagent review found the two most severe findings of the session so far -- both directly falsifying the Atlas benefit this slice exists to deliver ("migration 後可證明完整性"):

1. **Critical, fixed** -- `float()` parsing of COUNT values silently loses precision above 2^53 (real row-count magnitude) and above ~1e14 (money-scale sums), producing a FALSE `matches:true` for two genuinely different values with **zero tampering required** (e.g. `float("9007199254740993") == float("9007199254740992")`). Because the builder and the gate call the *same* compute function, both layers "independently" agreed on the wrong answer -- the exact "shared predicate is itself wrong" failure class `database_data.data_lineage`'s own critic round already taught this session, repeated here in a new function. Fixed by switching to `decimal.Decimal` (exact at any magnitude) and, on further reflection, dropping the original 10-decimal-place rounding entirely rather than reintroducing a different fixed tolerance -- Atlas's own formula states no tolerance, and a caller who knows a specific discrepancy is expected now records that via the check's own `resolution` field instead of a silent numeric guess.
2. **Critical, fixed** -- `generate_reconciliation_record` never actually recomputed `matches`/`diff` for its input checks; it validated shape/duplicates/status and then stored whatever a hand-built check dict supplied verbatim. A caller bypassing the per-check `check()` builder function could freely assert `{"matches": true, "diff": 0}` over a real, large mismatch and have the lie certified `overall_status: reconciled`, contradicting four separate places in the codebase that claimed this was impossible. Fixed by recomputing `compute_check_result` for every check and rebuilding a fresh check dict from the computed values -- mirroring `database_data.data_lineage`'s own rebuild-from-computed-values pattern, which this slice had cited as precedent without actually replicating.

Five Major findings, also fixed: (1) a resolution's own `resolved_as_expected:false` was silently overridden by `matches:true` -- fixed so resolution, when present, is authoritative in either direction; (2)-(4) the citation due-diligence repeated the exact grep-scope-understatement class `data_lineage`'s own review already caught in this same session, and separately misclassified the reason for deferring `database_data.expand_contract_migration` (claimed "no dedicated Atlas section" when it has two, plus an active 15-step recipe) -- both corrected with the wider Execution Contract corpus now cited; (5) a shared-file bug in `modules/research/gates.py`'s own `evaluate_statistical_gate` (`.get("provenance", {})` only substitutes on a MISSING key, so an explicit `provenance: null` crashed instead of failing closed) -- fixed for all six reusers of that gate this session, not just this one.

Five Minor findings also fixed: an unhashable `check_type` could raise a raw `TypeError` instead of failing closed; a stored-list aliasing bug (fixed automatically by the C2 rebuild); missing validation of `record_id`/`source_ref`/`target_ref`/`check_type` for hand-built input; the contract-backlog registration this contract's own text claimed had happened, but hadn't; and a non-boolean `resolved_as_expected` was accepted at construction instead of refused.

The broader lesson this round adds to the session's own running list: "we proactively checked for the four known failure classes" is not the same claim as "we are free of new ones" -- a genuinely new compute-layer precision bug and a genuinely new never-recomputes bug both survived a first draft that explicitly set out to avoid repeating prior mistakes. There is no slice tier thin enough, and no amount of proactive discipline, that makes a real critic round optional.
