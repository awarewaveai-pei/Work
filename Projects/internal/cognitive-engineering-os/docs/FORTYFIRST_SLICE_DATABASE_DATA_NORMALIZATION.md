## Critic round: `FAIL` on the first draft -- a genuine mathematical bug, not a disclosure gap

A `critic` subagent review (independent re-derivation of the relational algebra, hand-constructed counterexamples, real mutation testing, and full execution) returned **FAIL** -- two Critical findings, both real:

1. **Critical, fixed** -- **non-minimal declared keys silently OVER-REPORTED the achieved normal form.** The first draft's own contract claimed the single-declared-key design "will never over-report" the normal form. The critic constructed a direct counterexample: `PK=[A,B]`, `NK=[C]`, FDs `A→B` and `C→B`. Since `A` alone (via the explicit FD, chained with the key's own defining closure) already reaches every attribute, `B` is not really a *prime* attribute in real relational theory -- it only looked prime because the declared key was needlessly large. The first draft's code returned `THIRD_NF`; the textbook-correct answer (relative to the true minimal key `{A}`) is `SECOND_NF`. A second counterexample (`PK=[A,B,C]`) produced `THIRD_NF` where the correct answer is `FIRST_NF`. Fixed by adding `primary_key_is_minimal` (removing any single attribute from the declared key and testing whether the remainder is still a superkey -- provably sufficient by the standard monotonicity argument), checked as a real, fail-closed precondition at **both** the builder and the gate. A non-minimal declared key is now refused outright, not silently miscomputed.
2. **Critical, fixed** -- the schema's own example #1 would **FAIL its own real integrity gate.** Root cause: `transitive_dependency_violations` double-counted every 2NF (partial-dependency) violation as a 3NF violation too -- formally accurate under 3NF's bare definition, but it meant order_items's own two partial dependencies also showed up in the "transitive" list, when they aren't transitive (a chain through an intermediate non-key attribute) in the textbook sense. Fixed by excluding any FD already present in `partial_dependency_violations` from `transitive_dependency_violations` -- classification (`achieved_normal_form`) is unchanged (the FIRST_NF branch already short-circuits before the transitive list is consulted), only the evidence lists became mutually exclusive and honestly named. This automatically made the schema's own example self-consistent again.

Six Major findings, all fixed: `version` had zero runtime enforcement at either layer despite the module's own docstring claiming it had applied `database_data.data_contract`'s own id/version lesson in full (only `id` was actually covered) -- added at both layers; the citation-count paragraph claimed a grep "returns ONLY" L900 when a re-run actually returns six lines (the other five confirmed distinct: MCDA/TOPSIS score normalization, a zero-rework "Normalize Once" pipeline concept) -- corrected to state the real grep output plus the disambiguation, not just the intended conclusion; mutation testing found the closure algorithm itself was under-tested (five specific mutants survived, including dropping the fixed-point loop entirely and dropping the implicit key axiom) -- four targeted regression tests added, each constructed to require the specific mechanism (multi-round convergence, axiom chaining, order-independence with 3+ FDs) to pass; a `dict(fd)` shallow copy left every violation entry's own `determinant` list **aliased** to the same list object stored in `functional_dependencies`, contradicting the builder's own "rebuilds every nested object" claim -- fixed to rebuild the nested list too, with a pinning test; a missing per-slice doc (this file); no test anywhere validates a typed-object schema's own `examples` block against the schema **and** its real gates (a repo-wide gap this schema's own example #1 fell into) -- closed for this slice's own schema directly, and a broader follow-up flagged separately (see below).

Minor findings: a tie-breaking edge case in the violation-list sort key (resolved as an automatic side effect of also fixing the duplicate-FD gap below, since the sort key and the duplicate-detection key are identical); `functional_dependencies` had no `uniqueItems` and no runtime dedup, allowing two entries describing the identical dependency with a differently-ordered determinant list -- added a real invariant (`NORMALIZATION_DUPLICATE_FUNCTIONAL_DEPENDENCY`) at both layers plus schema-layer `uniqueItems: true`; the "five textbook examples" verification claim undercounted (a sixth, the two-hop closure chain, existed in the contract's own verification note but had no regression test) -- added.
