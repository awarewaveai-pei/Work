## What was built

THREE sources name this method, across TWO different mother documents: (1) Atlas's own F20 tool table row (L887: "subject/workload/resource→authn/authz→short-lived credential→audit" -- a real ordered four-position chain whose FIRST position is itself "/"-joined, three parallel entities under simultaneous verification, not a sub-sequence); (2) Atlas's OWN dedicated §12.37 (L3027-3042, a deliberately UNORDERED six-item checklist -- Strong identity/Workload identity/Short-lived credentials/Least privilege/Explicit policy decision/Continuous logging-audit, no arrows anywhere); (3) Master Plan's own §62 (L2636-2657, a DIFFERENT document, a real ORDERED six-step chain -- Identity→Workload Identity→Mutual Authentication→Short-lived Credentials→Policy Decision→Resource Access -- PLUS an explicit "禁止" forbidden-credential list: Shared Password/Long-lived API Key/Hard-coded Secret, L2652-2656).

**Stage-shape decision, the mirror image of `security.dpia_pia`'s own table-row-vs-dedicated-section precedent**: Atlas's own F20 table row is authoritative for `stages`' four-position shape, NOT because it is richer (Master Plan §62's six-step chain is objectively richer) but because it is the ONLY genuinely ordered source living in the SAME document/table that defines this method's own F20 membership -- Atlas's own dedicated §12.37 drops all sequencing, making it less useful for staging than its own table row, the opposite of DPIA/PIA's own case. Master Plan §62's and Atlas §12.37's own distinctive content (Mutual Authentication, Resource Access, Least privilege, "continuous" logging/audit) are folded in as real per-stage field enrichment, not discarded and not promoted into extra top-level stages.

**A fifth structural sub-variant among F20 members**: a fixed-length, positionally-ordered four-stage pipeline (like PASTA's seven and DPIA/PIA's eight), but with a genuinely new twist -- position 1 (`identity_context`) is itself a REQUIRED SET of three distinct, parallel sub-entities (subject/workload/resource), not a single scalar/array field.

Grep-confirmed ZERO mentions of "Zero Trust"/"zero_trust"/"零信任" anywhere in the Execution Contract (case-insensitive, whole-document, not just §32) -- even stronger absence evidence than DPIA/PIA's own EC search. **A more nuanced non-membership than DPIA/PIA's own**, disclosed rather than copy-pasted: this method's own subject matter (authn/authz, credentials) genuinely overlaps EC §32's own trigger vocabulary (unlike DPIA/PIA's orthogonal privacy trigger), but EC §32's own closing sentence is a closed, four-method list that never names this method -- a Zero Trust Review of an authn/authz-touching change is real, complementary security work, but does NOT substitute for the EC §32 gate itself.

Two real invariants, both enforced at construction AND the independent gate layer:

1. **Stage-1 required set** -- `identity_context` must carry all three of subject/workload/resource, each independently well-shaped. Atlas's own F20 table row (L887).
2. **Forbidden credential-type denylist** -- `credential_issuance.credential_type` may never be `shared_password`/`long_lived_api_key`/`hardcoded_secret`, transcribed verbatim from Master Plan §62's own explicit "禁止" list (L2652-2656). Unlike DPIA/PIA's own two cross-array invariants (schema-inexpressible), this ONE is a single-field denylist -- enforced at BOTH the schema layer (`not: {enum: [...]}`) AND the runtime construction/gate layer, defense in depth.

Three optional, nullable, free-text (deliberately NOT `const`) soft references cite `docs/adr/ADR-016-zero-trust-workload-identity-and-pdp-selection.md` / `policies/security/zero-trust.policy.yaml`'s own REAL ratified singleton values -- `identity_context.subject.idp_ref` (Zitadel), `identity_context.workload.workload_identity_strategy_ref` ("cloud-native workload identity + short-lived-credential mTLS"), `access_decision.pdp_engine_ref` (Cedar). Free text, not `const`, because a review record's entire purpose is to be able to represent a NON-compliant finding without being schema-blocked. No hard `$ref` into the policy file: independently re-verified by direct read of `ai_lego/core/contracts/schema_contracts.py:23-36` that `SchemaContracts.__init__` only walks `spec_root/specs/**/*.yaml`, and `policies/security/zero-trust.policy.yaml` lives outside that walk.

**No real deployed instance exists in this repository to model a CLI demo on**, disclosed honestly rather than overclaiming DPIA/PIA's own genuine ADR-002 precedent: ADR-016's own Migration section states the actual infrastructure build-out is future work, independent of the ADR itself, which approves only the decision. This slice's own CLI demo and schema example are explicitly ILLUSTRATIVE of a compliant record once ADR-016's ratified infrastructure is deployed, grounded in the real ratified values (Zitadel/Cedar/mTLS strategy string verbatim), not a claim that a real access path was reviewed -- the same disclosed-gap class `security.pasta.contract.yaml`'s own "no real-world usage instance exists" already establishes, for a different underlying reason.
