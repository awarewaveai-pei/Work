## What was built

Atlas gives this method exactly ONE citation, its own F20 tool table row (L891: "Threat→Control→Evidence", usage "每個威脅對應 preventive/detective/recovery control", benefit "控制可稽核、可測") -- the THINNEST of all ten F20 rows, no dedicated section exists anywhere in the document (grep-confirmed across §11.x/§12.x/§13.x).

**Central design question, investigated seriously before any field was written**: should this method be a genuine DOWNSTREAM CONSUMER of an already-built sibling threat-model record, or a STANDALONE record with its own from-scratch `threats[]`/`controls[]`? Three real, independent citations grounded the CONSUMER choice: (1) Atlas's own row (L891) reads "每個威脅對應" -- grammatically presupposing threats that already exist; (2) Atlas §13.11 Security Review Recipe (L3472-3487) sequences "...→ STRIDE → LINDDUN → Attack Tree → Secret/Identity Review → Supply Chain Review → **Control Mapping** → Adversarial Test →..." -- Control Mapping's own recipe position is immediately after the threat-producing methods; (3) `security.stride.contract.yaml`'s own `compilation_decisions` (fourth entry) explicitly declined to build this traceability structure itself, naming Security Control Mapping BY NAME as the dedicated future home, and its own `OQ-STRIDE-5` explicitly anticipated a `control_mapping_ref` soft link -- this slice directly resolves it.

Reading both candidate sibling schemas in full confirmed `security.stride` and `security.linddun` share an IDENTICAL flat `threats[]` shape (`required: [element_name, category, description, control, residual_risk, test_evidence]`, verbatim in both), while `security.attack_tree` (a recursive AND/OR tree, no flat list) and `security.pasta` (a single fixed-length pipeline with one terminal risk verdict) are structurally incompatible -- `source_record_type` is therefore a closed two-value enum (`stride`/`linddun`), a disclosed evidence-based scope limit, not an oversight.

**Structurally NEW among every F20 member and every `ai_lego` module built this session** (confirmed by grep across every `ai_lego/modules/*/*.py` gate signature -- zero prior hits of an extra parameter): this is the FIRST method whose own core invariant is a reference to a DIFFERENT record's raw content, not a self-contained analysis. Two real invariants, both two-layer:

1. **WITHIN-RECORD referential integrity** -- every `control_mappings[]` entry's own `control_id` must name a real `controls[].control_id` (the same class STRIDE's own `threats[].element_name` -> `data_flow_elements[].name` check already establishes).
2. **CROSS-RECORD referential integrity** (the genuinely new class) -- every `control_mappings[]` entry's own `source_threat_index`/`source_threat_element_name`/`source_threat_category` must genuinely match the REAL external source record's own `threats[]` at that index. The BUILDER always performs this fully (it requires the real, raw `source_record` as an argument -- there is no other way to construct this record). The GATE performs it fully too when the same raw record is passed to its own OPTIONAL `source_record` keyword; when omitted, it still re-derives a real, weaker, fully self-contained invariant instead of skipping silently -- that `control_mappings[]`'s own covered indices and `source_threats_with_no_control_mapping`'s own indices together cover exactly `0..source_threat_count-1` with no overlap and no gap. `source_threat_count` is a third field this slice's own author added after finding, while writing the fallback check, that without an independently-stored total, deleting the LAST unmapped entry could leave the remaining indices looking accidentally contiguous -- a real gap closed before it shipped, not merely asserted safe.

`source_threats_with_no_control_mapping` is GENUINE, RE-DERIVED evidence (never caller-supplied) -- the same "surfaced as information, not enforced" discipline STRIDE's own `elements_with_no_recorded_threats` already establishes, applied here to CONTROL coverage instead of THREAT coverage, directly satisfying Atlas's own "控制可稽核、可測" benefit as a measurable signal.

`evidence` is a STRUCTURED `{description, verified_by, verified_date}` object, a deliberate departure from every sibling F20 threat's own flat `test_evidence` string -- Atlas's own benefit line for THIS method specifically ("auditable AND testable") is not concretely checkable from bare prose alone.
