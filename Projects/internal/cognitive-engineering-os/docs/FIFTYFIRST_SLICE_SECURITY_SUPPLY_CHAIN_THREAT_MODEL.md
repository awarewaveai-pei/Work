## What was built

Atlas gives this method exactly ONE structural citation anywhere in this spec root -- the F20 tool table's own row (L889: `source→dependency→CI→artifact→registry→deploy→sign/verify`), no dedicated section (broad grep for "supply chain"/"供應鏈" across the full Atlas document found exactly two other, non-structural mentions: §13.11's Security Review Recipe naming "Supply Chain Review" as one step in a 12-step recipe, L3482; and §27's gate table naming supply chain as one of three areas needing "controls and tests", L4378). This row is transcribed verbatim, in Atlas's own literal order, as `stages[].stage_id` -- a fixed-length-seven, positionally-ordered pipeline, the same structural class `security.pasta`/`security.dpia_pia` already establish. `sign/verify`'s own internal slash becomes the compound stage_id `sign_verify`, the same treatment `dpia_pia`'s `necessity_proportionality` already gives a slash-compound Atlas word.

Grep-confirmed EC §32 (L1231-1260) never mentions supply chain, dependencies, CI/CD, or build in its own ten-item trigger list, and its own closing sentence names exactly four methods, not this one -- this record carries NONE of `assets`/`trust_boundaries`/`entry_points`/`test_evidence`, the second F20 typed object to omit that triplet entirely (after `dpia_pia`), directly updating `security.stride.contract.yaml`'s own `OQ-STRIDE-4` (see Honest limits below for the proposed verbatim addition).

**Three mother-document citations for the same underlying flow, with genuinely different stage counts/wording -- disclosed, not silently reconciled**: Atlas's F20 row (7 stages), Master Plan §66 "Supply Chain Security" (L2740-2758, 7 stages, different words, ends in "Verified Deployment"), and Execution Contract §34 "Supply Chain Contract" (L1304-1343, 9 stages, Sign at position 7 of 9, before Registry/Deploy). Atlas's own row was chosen as authoritative for stage identity/order (the same family-wide convention every prior F20 member follows: stage taxonomy always comes from Atlas, never Master Plan or EC); Master Plan §66 and EC §34 are used only to ground two additional invariants, never to reorder the stage list. Atlas's own literal word order places `sign_verify` AFTER `deploy` (the last word) -- read as real-time pipeline causality this would contradict both other documents' own orderings, but is NOT silently "fixed" here; this record is disclosed as documenting a retrospective review's own account (the same category every other F20 Threat Model record already is), and the terminal invariant is deliberately field-local to the single `sign_verify` stage object for exactly this reason.

Two invariants beyond stage completeness-and-order, BOTH grounded in real Execution Contract / Master Plan citations, NEITHER from Atlas and NEITHER from the ADR-015 tooling-selection layer:

1. **Dependency-consideration completeness** (EC §34 L1334-1342, "新增 dependency 要考慮") -- the `dependency` stage's own `dependency_entries[]` must have at least one entry, and every entry's own `considerations` object must carry all SEVEN named dimensions (`maintenance`/`license`/`vulnerability_history`/`replaceability`/`transitive_dependencies`/`size_performance`/`long_term_support`), each non-empty. This is the one stage this record gives richer structure than a bare `stage_id`/`summary` -- a real, disclosed consequence of EC §34 actually naming further detail for it (unlike `source`/`ci`/`artifact`/`registry`/`deploy`, which stay minimal because no mother document names any further sub-structure for them).
2. **Production-verified-artifact gate** (EC §34 L1328-1332 "Production 只部署：verified artifact", independently converging with Master Plan §66 L2758 "Production 只接受 Signed Artifact") -- the terminal `sign_verify` stage's `production_deployment_occurred` may not be `true` while `artifact_verified` is `false`. Enforced at the runtime layer only (construction + independent gate), by a deliberate compilation decision disclosed as genuinely different from `dpia_pia`'s own reasoning: this rule COULD be written as a same-object JSON Schema `if`/`then` (both fields live in one `sign_verify` object, unlike DPIA/PIA's own cross-`prefixItems` escalation rule), but is kept runtime-only to avoid the same business rule existing in two independently-maintained places that could drift apart over this record's own 30-year evolution horizon.
